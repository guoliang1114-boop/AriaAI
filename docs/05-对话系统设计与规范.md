# 对话系统设计与规范

> 更新日期：2026-08-30
> 关联文档：[06-HITAS设计](./06-Human-in-the-Loop%20Tool%20Approval%20设计.md)、[02-Skill体系](./02-Skill体系.md)

## 1. 文档定位

本文是 AriaAI 对话系统的设计规范。目标是把对话行为从“散落的 if-else 和 prompt 约束”收敛为可解释、可测试、可审计的执行契约。

核心原则：

- Mode 决定对话剧本。
- ActionPolicy 决定副作用权限。
- ToolAccessPolicy 决定工具可见性。
- P0-P4 phase 负责执行。
- HITAS 负责高风险工具调用确认。
- ChatTrace 负责可观测和回归分析。
- Conversation Capsule 负责跨轮目标、约束、工具结果、阻塞和下一目标续接。
- Instruction Manifest 负责显式指令优先级与冲突裁决。
- Durable Run Input 负责跨 Worker 的取消与运行中追加意图。
- Turn Recovery Contract 负责用持久 checkpoint、effect 事实和当前项目状态创建新的审计 Run。

## 3. 三个核心枚举

### 3.1 ChatMode

`ChatMode` 表示这轮对话的剧本。

```python
class ChatMode(str, Enum):
    STANDALONE_QA = "standalone_qa"
    PROJECT_DEEP_DIVE = "project_deep_dive"
    CROSS_PROJECT_PORTFOLIO = "cross_project_portfolio"
    WORKSPACE_INVENTORY = "workspace_inventory"
    SKILL_EXECUTION = "skill_execution"
    TASK_ORCHESTRATION = "task_orchestration"
```

| Mode | 触发场景 | 说明 |
|---|---|---|
| `STANDALONE_QA` | 无项目、无 Skill 的普通问答 | 不注入项目上下文 |
| `PROJECT_DEEP_DIVE` | 单项目内问答、分析、文件处理 | 注入项目结构化上下文 |
| `CROSS_PROJECT_PORTFOLIO` | 客户所有项目汇总 | 使用客户/项目组合上下文 |
| `WORKSPACE_INVENTORY` | 工作台项目清单或组合盘点 | 使用工作台项目上下文 |
| `SKILL_EXECUTION` | 用户显式选择或强制运行 Skill | 注入 Skill prompt 和工具 |
| `TASK_ORCHESTRATION` | 结构化交付物或 durable task | 移交 task orchestrator |

### 3.2 ActionPolicy

`ActionPolicy` 表示这轮对话允许产生什么副作用。

```python
class ActionPolicy(str, Enum):
    DIRECT_ANSWER = "direct_answer"
    READ_ONLY_TOOL = "read_only_tool"
    WRITE_ARTIFACT = "write_artifact"
    MODIFY_EXISTING_FILE = "modify_existing_file"
    DURABLE_TASK = "durable_task"
    DESTRUCTIVE_ACTION = "destructive_action"
```

| Policy | 说明 | 典型请求 |
|---|---|---|
| `DIRECT_ANSWER` | 只回答，不调工具 | “总结这个项目风险” |
| `READ_ONLY_TOOL` | 可读文件或上下文 | “读取 risk.md 并总结” |
| `WRITE_ARTIFACT` | 可新建交付物 | “生成一份 PPT” |
| `MODIFY_EXISTING_FILE` | 可修改现有文件，需确认 | “把这个文档改一下” |
| `DURABLE_TASK` | 交给 task orchestrator | “生成完整咨询提案” |
| `DESTRUCTIVE_ACTION` | 删除或破坏性动作，需确认 | “删除这些文件” |

### 3.3 ToolAccessPolicy

`ToolAccessPolicy` 表示模型能看到哪些工具。

```python
class ToolAccessPolicy(str, Enum):
    NONE = "none"
    INJECTED_CONTEXT_ONLY = "injected_context_only"
    READ_ON_DEMAND = "read_on_demand"
    EXPLICIT_FILE_READ = "explicit_file_read"
    WRITE_ALLOWED = "write_allowed"
```

| ToolAccessPolicy | 工具可见性 |
|---|---|
| `NONE` | 不暴露工具 |
| `INJECTED_CONTEXT_ONLY` | 不暴露工具，只使用已注入上下文 |
| `READ_ON_DEMAND` | 暴露只读工具 |
| `EXPLICIT_FILE_READ` | 用户明确读文件时暴露只读工具 |
| `WRITE_ALLOWED` | 根据 ActionPolicy 暴露读/写/改/删工具 |

重要规则：普通项目分析默认是 `INJECTED_CONTEXT_ONLY`，不是 `READ_ON_DEMAND`。只有用户明确要求读取具体文件或列出文件时，才暴露只读工具。

- `MODE_CONFIG` 已存在。

## 5. 意图路由

意图路由由两层组成：

1. `policy_guards.py`：确定性规则，识别身份请求、问题、读文件、写文件、修改、删除、项目分析、组合查询等。
2. `intent_router.py`：在规则基础上调用 LLM router 或 task router，并做策略夹紧，避免 LLM 把权限升级得过高。

路由输出：

```python
IntentDecision(
    chat_mode=...,
    action_policy=...,
    tool_access_policy=...,
    confidence=...,
    reason=...,
    method=...,
)
```

安全原则：

- 默认从严。
- 规则优先处理高确定性场景。
- LLM router 可帮助分类，但不能越过策略上限。
- destructive intent 必须包含明确删除动词和对象类型，避免误判。
- 修改、删除和长任务必须进入明确 policy。

### 5.1 Skill 是本轮能力，不是会话永久模式

`Conversation.skill_id` 只保存最近可续接的 Skill，不代表后续每轮都自动注入该 Skill。Runtime 每轮重新裁决：

- 用户显式选择或强制运行：本轮启用；
- 高置信、唯一候选：本轮自动启用；
- “继续、沿用刚才格式、补充行动项”等相关追问：续用最近 Skill；
- 普通无关问题、换话题或显式要求停用：释放最近 Skill；
- 新工作流命中另一 Skill：切换到新的有效 Skill。

本轮实际生效的 Skill ID、名称和来源由后端 `ChatRuntime` 决定，并通过 `run_started.skill` 回传。前端选择框只是用户输入，不能冒充实际执行结果。完整设计与评测矩阵见 [22-项目对话与Skill交互全量优化方案](./22-项目对话与Skill交互全量优化方案.md)。

### 5.2 Conversation Capsule 与指令优先级

Runtime 不再把自由文本 Working Memory 直接当成模型续接事实，而是每轮构建 `Conversation Capsule v1`。Capsule 保留目标、Turn 模式、当前 Artifact/Task、有效用户约束、完成决策、工具结果、未解除阻塞和下一目标，并通过以下边界防止串线：

- 同时绑定 `conversation_id` 与 `project_id`，跨项目历史 Capsule 不继承；
- 记录 `source_message_ids`、`previous_capsule_sha256` 和自身 `capsule_sha256`；
- 只保留安全、有界字段，不保存工具输入、完整输出、服务器路径或隐藏推理；
- 工具失败只有被后续成功通过 call ID 显式声明为 retry/recovery 时才解除阻塞；
- P4 把本轮工具结果与 Assistant 摘要写入消息元数据，下一轮再从数据库权威状态重建。

约束采用“保留为默认、显式重述才撤销”的规则。用户当前轮明确重述语气、详略、格式、语言或写入策略时，系统撤销同维度历史约束；“不用、不要、无需、取消、改为”等否定/切换表达也适用。普通“继续”不会清空其他要求。当前用户要求始终高于历史 Capsule、长期偏好和 Skill 默认值。

`InstructionManifest v1` 固定优先级如下：

1. 平台安全、权限和本轮产品策略；
2. 本轮用户明确要求；
3. 项目作用域与访问边界；
4. 当前交付物和任务状态；
5. 本轮有效 Skill；
6. 用户长期偏好；
7. 工作区/RAG 证据；
8. 历史 Conversation Capsule。

项目上下文、RAG、工具结果和历史摘要是数据，不是可执行指令。持久 Manifest 只包含层 ID、优先级、作用域、字符数和内容 SHA-256；原始 Prompt 仍只在本轮模型请求内存在。Capsule 与 Manifest 均进入 Context Assembly、ChatTrace 和 Run Evaluation 完整性校验。

Agent Loop 在领取耐久 Steering 前，先将基础 `ContextAssemblyManifest` 与精确的初始 Provider 请求校验。如果已通过身份、ACL、Message metadata 和内容 SHA-256 复核的 Steering 在 Assembly 后改变了本次请求，系统会产生不含正文的派生 Manifest：它绑定基础 Manifest SHA-256、耐久输入的 Run/序号/Message 身份与内容摘要，以及经工具 transcript 规范化和上下文预算后的精确 system/messages/tools 指纹。基础 Manifest 缺失或失配、输入身份非法、派生指纹失配都会在调用 Provider 前失败关闭；派生记录最多保留 24 个有界输入身份。

### 5.3 耐久 Run 控制与中断恢复

`POST /chat/runs/{run_id}/steer` 与 `POST /chat/runs/{run_id}/cancel` 不以当前 ASGI 进程的内存注册表为事实源。服务端先根据 `ChatRun` 解析 Conversation 并复检写权限，再把控制意图写入 `ChatRunInput`：

- Steering 正文仍只保存在普通 `Message(role=user)`；邮箱只保存 Run/Message 身份、序号和 SHA-256。
- Agent Loop 在模型请求或工具批次边界原子领取。取消优先：同批 Steering 转为 `unapplied`，不再注入当前 Run。
- Durable Task 路径只领取 cancel，不消费它不支持的 Steering；已创建的 `TaskRun` 进入 Aria 原生取消与终态收口边界。
- `applied` 只表示邮箱已被 at-most-once 领取，不证明 Provider 已收到正文。邮箱故障时运行失败关闭，不在忽略取消/纠偏后继续调模型或提交工具。

中断或失败后，前端先 GET 服务端重建的 `TurnRecoveryContract v2`，用户明确确认后才发送新 Turn。契约绑定来源 `ChatRun`、来源 Assistant Message、Rollout checkpoint、内容安全的 effect ledger、未应用/已领取输入身份与当前 Project World State，并由 `contract_sha256` 防止用旧预览启动新执行。
当前只允许通过同步 SSE `/chat/send` 启动恢复；`/chat/send-async` 会在创建 Message、子 Run 或后台 TaskRun 之前返回 409，避免绕过恢复预留和活化边界。

恢复不是旧 Run 的原地续跑：

- 新请求必须原子预留唯一的子 `ChatRun`，再启动 SSE。流尚未开始的 `reserved` 预留可在 TTL 后审计失效并重试；流已激活的 Run 不会被该 TTL 误回收。
- 只有来源 Run/会话/项目、`GeneratedFile`/`ProjectFile`、output identity、受控路径与实际文件字节 SHA-256 均仍精确匹配的已完成写入，才能返回 `already_completed`，不再调用工具。
- 该已验证结果会作为恢复子 Run 的可下载交付卡片和完成证据展示，但不会再次进入产物写入队列，也不会把来源 `GeneratedFile` 改挂到子 Run。用户会明确看到“已核验原任务已有附件、本次未重复生成”。
- 恢复中的任何新非只读动作都不能直接执行，必须先生成带恢复身份的签名 HITAS 供人工审阅。确认时会再次核对当前写权限与 Project World State，但确认结果固定失败关闭：包括项目 Office 创建/编辑和结构化 Markdown 三个 final-authorized writer 在内，全部保持零业务调用、零 `ProjectFile`，并要求用户人工核对后从 fresh non-recovery 新轮重新发起。原因是 Project World State 包含里程碑、待办、文件夹、文件等多个可独立变化的子资源，当前不能把全量状态 CAS 与任意业务写事务严格线性化。文件夹与文件的 `folder_id` 也属于状态事实；已观测到的状态改变、旧版记录、未知工具或不可验证结果同样转为人工核对。
- 恢复守卫不允许通过 HITAS 批量执行绕过该边界：只要一个多动作批次含有恢复守卫，整批会在任何工具注册表或业务写入前失败关闭；首项落 `failed`，其余仍在执行代的动作落 `skipped`。单动作同样只能审阅，不能成为恢复写入通道。
- 普通非恢复审批中，项目作用域且会变更状态的工具也只有项目 Office 创建/编辑和结构化 Markdown 三个 final-authorized writer 可以执行；它们在最终业务事务内重验 Actor、项目成员、签名和动作代。项目 scope 必须在 server runtime、审批动作和工具输入三处都是精确相等的正整数；`bool`、字符串、浮点数、零和负数全部拒绝。其他项目文件/文件夹及 legacy/external registry writer 在 registry 前失败关闭。项目会话中的非项目作用域全局工具不受这条特定边界误拦截，仍遵循自身签名、HITAS 与权限策略；但其 `tool_input` 顶层不得出现 `project_id` 键，无论值为 `None`、布尔、字符串、整数或浮点数都失败关闭。final-authorized prepare 后若最终授权或 CAS 失败，控制面只会对完全相同且仍 `executing` 的动作代 CAS 为 `failed`，不写业务数据；已有终态或已换代动作保持原状，批次剩余执行代收口为 `skipped`，不会遗留旧 generation 的 `executing` 悬挂项。
- 来源 Run 尚有待确认审批时一律进入人工核对，不能让仍可确认的旧动作与自动重新规划同时存在。普通 Agent Loop 的模型、工具、确认和持久化边界会在同一事务中领取邮箱并关闭 phase；最终持久化后不再接受“已取消”的假成功回执。
- `retry_read_step` 只允许重新规划只读步骤；任何写工具在执行器硬拦截。新的高风险操作仍需经过当前 Aria ACL 与 HITAS。

恢复前端不将 HTTP 200 或 legacy `done` 单独当作成功。它只在服务端发出激活后才可能出现的 `conversation_id` 或 `run_started` 后显示恢复用户气泡，并且只在同一 `run_id` 的 `run_started`→`run_done(final_status=completed|waiting_confirmation)` 完整收口后报告恢复已创建。用户停止、`run_done(cancelled)`、`run_failed`、空流、缺失启动身份或终态身份不一致均会拒绝成功回执；激活前停止也不会生成本地 Assistant 幽灵消息。

服务端也不在数据库终态成功前对外宣告完成：P4 先持久化 Assistant Message/交付证据，再原子收口 Rollout/`ChatRun` 终态；只有该终态事务提交成功后才释放 legacy `done` 和 Product `run_done`。终态提交失败只发送 `run_failed(PERSISTENCE_ERROR)`，不发送成功收口。

该机制不恢复 Provider 私有 transcript，不把 Prompt 建议当作幂等性，也不声称自动修复任意进程级崩溃。当前没有 active `ChatRun` 的 worker lease、heartbeat 或通用 reaper；TTL 只能审计失效尚未激活且没有 Assistant Message 的 `reserved` 恢复子 Run。active Run lease/reaper 属于 Phase 3O，不在本阶段实现范围。所有项目、任务、权限、审批和审计状态仍属于 Aria 原生服务。

## 6. 工具过滤

工具过滤分两步：

1. `filter_tools_for_access()` 根据 ToolAccessPolicy 决定模型能不能看到工具。
2. `policy_allows_tool()` 根据 ActionPolicy 与工具所需权限做 rank 比较。

工具所需权限来自：

- `services/tool_descriptions.py` 中的配置。
- `policy_guards._required_policy_for_tool()` 中的兜底规则。

示例：

- `read_project_file`：`READ_ONLY_TOOL`
- `write_project_office_document`：`WRITE_ARTIFACT`
- `update_project_markdown_document` replace/append：`MODIFY_EXISTING_FILE`
- `manage_project_files delete`：`DESTRUCTIVE_ACTION`

## 7. Consulting Turn Frame

`Consulting Turn Frame` 是对话系统的业务理解层。它不替代 IntentRouter，而是在 mode/policy 之上补充“这轮对话到底是在服务哪个咨询场景”。

当前支持的 `job_type`：

| job_type | 典型场景 | 输出倾向 |
|---|---|---|
| `pre_meeting_brief` | 会前 30 秒、见客户、客户会议准备 | 开场话术、客户优先级、避雷点、推进建议、会后动作 |
| `proposal_or_business_case` | 提案、建议书、SOW、报价、商业案例 | why now、诊断、方案、路线图、价值、风险、下一步 |
| `client_ready_presentation` | PPT、汇报材料、Deck | 结论先行 storyline、页标题、页面计划或交付物 |
| `meeting_intelligence` | 会议纪要、转写、行动项、决策 | 摘要、决策、行动项、风险、跟进信息 |
| `project_risk_diagnosis` | 风险、阻塞、延期 | 风险优先级、根因、影响、缓解动作、需决策事项 |
| `stakeholder_intelligence` | 干系人、决策人、客户偏好 | 干系人地图、可能立场、沟通策略、话术、风险 |
| `project_deep_dive` | 普通项目分析 | 结论、依据、影响、下一步 |

这一层解决两个问题：

- 用户说法经常很口语化，例如“30 秒后见客户”“这个客户怎么推进”“明天汇报怎么讲”。系统需要把它翻译成咨询工作类型，而不是只做关键词问答。
- Skill 和工具不应该为了“显得智能”而乱调；是否调用工具应由 Intent Frame 的权限和 Consulting Turn Frame 的业务目标共同约束。

Prompt 中会同时注入：

- `Intent Frame`：mode、policy、工具访问、response contract。
- `Consulting Turn Frame`：job_type、client_moment、memory_focus、response_shape、agent_protocol。

工程原则：学 Codex 的 observe -> reason -> act -> verify 执行循环，但输出形态必须服务咨询业务：客户关系判断、项目交付控制、会前决策、交付物质量和组织记忆沉淀。

## 8. P0-P4 Phase

| Phase | 文件 | 责任 |
|---|---|---|
| P0 | `p0_durable_task.py` | 判断是否升级为 durable task / task orchestrator |
| P1 | `p1_planning.py` | 模型规划和流式输出，收集 tool_use |
| P2 | `p2_tools.py` | 执行工具、做 policy 检查、生成 HITAS payload |
| P3 | `p3_followup.py` | 工具结果回注，让模型生成 follow-up |
| P4 | `p4_persist.py` | 持久化消息、生成物、Trace、PendingToolAction |

### P0

P0 判断用户请求是否需要结构化长任务，例如完整 PPT、报告、提案、复杂文档生成。如果是，则交给 `task_orchestrator`。

### P1

P1 调用 provider 生成回答或工具调用。此时模型只能看到 runtime 过滤后的工具。

### P2

P2 遍历 tool_use：

- 先判断工具是否被当前 policy 允许。
- 再判断是否需要 HITAS 确认。
- 可直接执行的工具立即执行。
- 需确认的工具生成 pending action payload，不执行。

### P3

工具执行完成后，P3 把工具结果重新注入模型，让模型生成面向用户的总结。若 P3 再次触发修改或删除工具，也应进入 HITAS。

### P4

P4 负责持久化：

- user/assistant message。
- artifacts。
- pending tool actions。
- chat trace。
- legacy confirmation fallback cleanup。
- 特定场景的 deterministic cleanup confirmation。

## 9. HITAS 接入点

HITAS 只处理需要用户确认的高风险工具动作：

- 修改现有文件。
- 删除文件或文件夹。
- 其他被配置为 destructive 或 modify 的工具。

流程：

```text
P2/P3 发现需确认工具
  ↓
构造 pending action payload
  ↓
P4 写入 PendingToolAction
  ↓
前端显示 Action Preview
  ↓
用户 confirm/reject
  ↓
后端确定性执行或拒绝
```

详细设计见 [06-Human-in-the-Loop Tool Approval 设计](./06-Human-in-the-Loop%20Tool%20Approval%20设计.md)。

## 10. ChatTrace

`ChatTrace` 是单轮对话的机器可读记录。

关键字段：

| 字段 | 说明 |
|---|---|
| `trace_id` | 单轮请求追踪 ID |
| `conversation_id` | 对话 ID |
| `chat_mode` | 最终 Mode |
| `action_policy` | 最终 ActionPolicy |
| `intent_method` | 路由方法 |
| `intent_reason` | 路由原因 |
| `model_used` | 实际模型 |
| `prompt_layers_json` | prompt 层 |
| `tool_decisions_json` | 工具过滤和执行决策 |
| `artifacts_json` | 生成物 |
| `stage_timings_json` | 阶段耗时 |
| `fallback_events_json` | fallback 事件 |

Trace 的用途：

- 解释为什么某轮对话没有调用工具。
- 解释为什么工具被拦截或进入 HITAS。
- 分析模型和 token 策略。
- 建立 golden set 防回归。

## 12. 设计约束

- 不在 prompt 中堆叠权限规则，权限应在 policy 和工具过滤层执行。
- 不让 LLM 在确认后重新规划高风险工具，确认后执行冻结参数。
- 不把普通分析请求升级为读文件工具，除非用户明确要求。
- 不让 Skill 隐式接管所有交付物请求。
- 不让低置信度 router 决策提高副作用权限。
- 不把 task orchestration 和普通 chat follow-up 混在同一职责里。
- 不用 Prompt 中的“不要重复”代替 effect 验证、项目状态 CAS 或 HITAS。
- 不将未启动恢复预留的 TTL 回收扩大为任意运行中 Run 的自动接管。
