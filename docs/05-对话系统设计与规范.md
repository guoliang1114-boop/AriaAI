# 对话系统设计与规范

> 更新日期：2026-08-24
> 关联文档：[06-HITAS设计](./06-Human-in-the-Loop%20Tool%20Approval%20设计.md)、[02-Skill体系](./02-Skill体系.md)

## 1. 文档定位

本文是 AriaAI 对话系统的设计规范。目标是把对话行为从“散落的 if-else 和 prompt 约束”收敛为可解释、可测试、可审计的执行契约。

核心原则：

- Mode 决定对话剧本。
- ActionPolicy 决定副作用权限。
- ToolAccessPolicy 决定工具可见性。
- P0-P4 phase 负责执行。
- HITAS 负责高风险工具调用确认。
- ChatTrace 负责可观测和回归分析。

## 2. 总体架构

```text
User Message
  ↓
Policy Guards
  ↓
IntentRouter
  ↓
ChatMode + ActionPolicy + ToolAccessPolicy
  ↓
Consulting Turn Frame
  ↓
Runtime Preparation
  ↓
Context Builder + Prompt Assembler + Tool Filter
  ↓
P0 Durable Task
  ↓
P1 Planning
  ↓
P2 Tool Execution
  ↓
P3 Follow-up
  ↓
P4 Persist
  ↓
ChatTrace / Message / Artifact / PendingToolAction
```

关键文件：

| 文件 | 责任 |
|---|---|
| `services/chat/mode_registry.py` | ChatMode、ActionPolicy、ToolAccessPolicy、ModeConfig |
| `services/policy_guards.py` | 规则分类、工具权限、工具可见性过滤 |
| `services/intent_router.py` | Rule-first + LLM router + task router 协调 |
| `services/consulting_intelligence.py` | 识别会前简报、提案、风险、干系人等咨询工作类型 |
| `services/chat/runtime.py` | 构造不可变 ChatRuntime |
| `services/chat/phases/` | P0-P4 执行阶段 |
| `services/context_builder/` | 项目、客户、RAG、Skill、工作台上下文 |
| `services/chat/trace.py` | Trace 记录 |

## 3. 三个核心枚举

### 3.1 ChatMode

`ChatMode` 表示这轮对话的剧本。

```python
class ChatMode(str, Enum):
    STANDALONE_QA = "standalone_qa"
    PROJECT_DEEP_DIVE = "project_deep_dive"
    CROSS_PROJECT_PORTFOLIO = "cross_project_portfolio"
    WORKSPACE_INVENTORY = "workspace_inventory"
    SKILL_EXECUTION = "skill_execution"
    TASK_ORCHESTRATION = "task_orchestration"
```

| Mode | 触发场景 | 说明 |
|---|---|---|
| `STANDALONE_QA` | 无项目、无 Skill 的普通问答 | 不注入项目上下文 |
| `PROJECT_DEEP_DIVE` | 单项目内问答、分析、文件处理 | 注入项目结构化上下文 |
| `CROSS_PROJECT_PORTFOLIO` | 客户所有项目汇总 | 使用客户/项目组合上下文 |
| `WORKSPACE_INVENTORY` | 工作台项目清单或组合盘点 | 使用工作台项目上下文 |
| `SKILL_EXECUTION` | 用户显式选择或强制运行 Skill | 注入 Skill prompt 和工具 |
| `TASK_ORCHESTRATION` | 结构化交付物或 durable task | 移交 task orchestrator |

### 3.2 ActionPolicy

`ActionPolicy` 表示这轮对话允许产生什么副作用。

```python
class ActionPolicy(str, Enum):
    DIRECT_ANSWER = "direct_answer"
    READ_ONLY_TOOL = "read_only_tool"
    WRITE_ARTIFACT = "write_artifact"
    MODIFY_EXISTING_FILE = "modify_existing_file"
    DURABLE_TASK = "durable_task"
    DESTRUCTIVE_ACTION = "destructive_action"
```

| Policy | 说明 | 典型请求 |
|---|---|---|
| `DIRECT_ANSWER` | 只回答，不调工具 | “总结这个项目风险” |
| `READ_ONLY_TOOL` | 可读文件或上下文 | “读取 risk.md 并总结” |
| `WRITE_ARTIFACT` | 可新建交付物 | “生成一份 PPT” |
| `MODIFY_EXISTING_FILE` | 可修改现有文件，需确认 | “把这个文档改一下” |
| `DURABLE_TASK` | 交给 task orchestrator | “生成完整咨询提案” |
| `DESTRUCTIVE_ACTION` | 删除或破坏性动作，需确认 | “删除这些文件” |

### 3.3 ToolAccessPolicy

`ToolAccessPolicy` 表示模型能看到哪些工具。

```python
class ToolAccessPolicy(str, Enum):
    NONE = "none"
    INJECTED_CONTEXT_ONLY = "injected_context_only"
    READ_ON_DEMAND = "read_on_demand"
    EXPLICIT_FILE_READ = "explicit_file_read"
    WRITE_ALLOWED = "write_allowed"
```

| ToolAccessPolicy | 工具可见性 |
|---|---|
| `NONE` | 不暴露工具 |
| `INJECTED_CONTEXT_ONLY` | 不暴露工具，只使用已注入上下文 |
| `READ_ON_DEMAND` | 暴露只读工具 |
| `EXPLICIT_FILE_READ` | 用户明确读文件时暴露只读工具 |
| `WRITE_ALLOWED` | 根据 ActionPolicy 暴露读/写/改/删工具 |

重要规则：普通项目分析默认是 `INJECTED_CONTEXT_ONLY`，不是 `READ_ON_DEMAND`。只有用户明确要求读取具体文件或列出文件时，才暴露只读工具。

## 4. Mode 配置

`MODE_CONFIG` 位于 `services/chat/mode_registry.py`。

| Mode | Prompt | max_tokens | 历史窗口 | 工具池 |
|---|---|---:|---:|---|
| `STANDALONE_QA` | `modes/standalone_qa.md` | 2048 | 24 | 无 |
| `PROJECT_DEEP_DIVE` | `modes/project_deep_dive.md` | 8192 | 24 | read/update/write/manage 项目工具 |

| `SKILL_EXECUTION` | `modes/skill_execution.md` | 8192 | 24 | Skill 工具 |
| `TASK_ORCHESTRATION` | 无 | 8192 | 0 | task step 自带 |

当前状态：

- `MODE_CONFIG` 已存在。
- runtime 已使用 mode/policy/tool_access 参与模型、token、上下文和工具过滤。
- 仍有部分 provider 和 task 编排逻辑保留历史判断，后续应继续收敛到配置表。

## 5. 意图路由

意图路由由两层组成：

1. `policy_guards.py`：确定性规则，识别身份请求、问题、读文件、写文件、修改、删除、项目分析、组合查询等。
2. `intent_router.py`：在规则基础上调用 LLM router 或 task router，并做策略夹紧，避免 LLM 把权限升级得过高。

路由输出：

```python
IntentDecision(
    chat_mode=...,
    action_policy=...,
    tool_access_policy=...,
    confidence=...,
    reason=...,
    method=...,
)
```

安全原则：

- 默认从严。
- 规则优先处理高确定性场景。
- LLM router 可帮助分类，但不能越过策略上限。
- destructive intent 必须包含明确删除动词和对象类型，避免误判。
- 修改、删除和长任务必须进入明确 policy。

### 5.1 Skill 是本轮能力，不是会话永久模式

`Conversation.skill_id` 只保存最近可续接的 Skill，不代表后续每轮都自动注入该 Skill。Runtime 每轮重新裁决：

- 用户显式选择或强制运行：本轮启用；
- 高置信、唯一候选：本轮自动启用；
- “继续、沿用刚才格式、补充行动项”等相关追问：续用最近 Skill；
- 普通无关问题、换话题或显式要求停用：释放最近 Skill；
- 新工作流命中另一 Skill：切换到新的有效 Skill。

本轮实际生效的 Skill ID、名称和来源由后端 `ChatRuntime` 决定，并通过 `run_started.skill` 回传。前端选择框只是用户输入，不能冒充实际执行结果。完整设计与评测矩阵见 [22-项目对话与Skill交互全量优化方案](./22-项目对话与Skill交互全量优化方案.md)。

## 6. 工具过滤

工具过滤分两步：

1. `filter_tools_for_access()` 根据 ToolAccessPolicy 决定模型能不能看到工具。
2. `policy_allows_tool()` 根据 ActionPolicy 与工具所需权限做 rank 比较。

工具所需权限来自：

- `services/tool_descriptions.py` 中的配置。
- `policy_guards._required_policy_for_tool()` 中的兜底规则。

示例：

- `read_project_file`：`READ_ONLY_TOOL`
- `write_project_office_document`：`WRITE_ARTIFACT`
- `update_project_markdown_document` replace/append：`MODIFY_EXISTING_FILE`
- `manage_project_files delete`：`DESTRUCTIVE_ACTION`

## 7. Consulting Turn Frame

`Consulting Turn Frame` 是对话系统的业务理解层。它不替代 IntentRouter，而是在 mode/policy 之上补充“这轮对话到底是在服务哪个咨询场景”。

当前支持的 `job_type`：

| job_type | 典型场景 | 输出倾向 |
|---|---|---|
| `pre_meeting_brief` | 会前 30 秒、见客户、客户会议准备 | 开场话术、客户优先级、避雷点、推进建议、会后动作 |
| `proposal_or_business_case` | 提案、建议书、SOW、报价、商业案例 | why now、诊断、方案、路线图、价值、风险、下一步 |
| `client_ready_presentation` | PPT、汇报材料、Deck | 结论先行 storyline、页标题、页面计划或交付物 |
| `meeting_intelligence` | 会议纪要、转写、行动项、决策 | 摘要、决策、行动项、风险、跟进信息 |
| `project_risk_diagnosis` | 风险、阻塞、延期 | 风险优先级、根因、影响、缓解动作、需决策事项 |
| `stakeholder_intelligence` | 干系人、决策人、客户偏好 | 干系人地图、可能立场、沟通策略、话术、风险 |
| `project_deep_dive` | 普通项目分析 | 结论、依据、影响、下一步 |

这一层解决两个问题：

- 用户说法经常很口语化，例如“30 秒后见客户”“这个客户怎么推进”“明天汇报怎么讲”。系统需要把它翻译成咨询工作类型，而不是只做关键词问答。
- Skill 和工具不应该为了“显得智能”而乱调；是否调用工具应由 Intent Frame 的权限和 Consulting Turn Frame 的业务目标共同约束。

Prompt 中会同时注入：

- `Intent Frame`：mode、policy、工具访问、response contract。
- `Consulting Turn Frame`：job_type、client_moment、memory_focus、response_shape、agent_protocol。

工程原则：学 Codex 的 observe -> reason -> act -> verify 执行循环，但输出形态必须服务咨询业务：客户关系判断、项目交付控制、会前决策、交付物质量和组织记忆沉淀。

## 8. P0-P4 Phase

| Phase | 文件 | 责任 |
|---|---|---|
| P0 | `p0_durable_task.py` | 判断是否升级为 durable task / task orchestrator |
| P1 | `p1_planning.py` | 模型规划和流式输出，收集 tool_use |
| P2 | `p2_tools.py` | 执行工具、做 policy 检查、生成 HITAS payload |
| P3 | `p3_followup.py` | 工具结果回注，让模型生成 follow-up |
| P4 | `p4_persist.py` | 持久化消息、生成物、Trace、PendingToolAction |

### P0

P0 判断用户请求是否需要结构化长任务，例如完整 PPT、报告、提案、复杂文档生成。如果是，则交给 `task_orchestrator`。

### P1

P1 调用 provider 生成回答或工具调用。此时模型只能看到 runtime 过滤后的工具。

### P2

P2 遍历 tool_use：

- 先判断工具是否被当前 policy 允许。
- 再判断是否需要 HITAS 确认。
- 可直接执行的工具立即执行。
- 需确认的工具生成 pending action payload，不执行。

### P3

工具执行完成后，P3 把工具结果重新注入模型，让模型生成面向用户的总结。若 P3 再次触发修改或删除工具，也应进入 HITAS。

### P4

P4 负责持久化：

- user/assistant message。
- artifacts。
- pending tool actions。
- chat trace。
- legacy confirmation fallback cleanup。
- 特定场景的 deterministic cleanup confirmation。

## 9. HITAS 接入点

HITAS 只处理需要用户确认的高风险工具动作：

- 修改现有文件。
- 删除文件或文件夹。
- 其他被配置为 destructive 或 modify 的工具。

流程：

```text
P2/P3 发现需确认工具
  ↓
构造 pending action payload
  ↓
P4 写入 PendingToolAction
  ↓
前端显示 Action Preview
  ↓
用户 confirm/reject
  ↓
后端确定性执行或拒绝
```

详细设计见 [06-Human-in-the-Loop Tool Approval 设计](./06-Human-in-the-Loop%20Tool%20Approval%20设计.md)。

## 10. ChatTrace

`ChatTrace` 是单轮对话的机器可读记录。

关键字段：

| 字段 | 说明 |
|---|---|
| `trace_id` | 单轮请求追踪 ID |
| `conversation_id` | 对话 ID |
| `chat_mode` | 最终 Mode |
| `action_policy` | 最终 ActionPolicy |
| `intent_method` | 路由方法 |
| `intent_reason` | 路由原因 |
| `model_used` | 实际模型 |
| `prompt_layers_json` | prompt 层 |
| `tool_decisions_json` | 工具过滤和执行决策 |
| `artifacts_json` | 生成物 |
| `stage_timings_json` | 阶段耗时 |
| `fallback_events_json` | fallback 事件 |

Trace 的用途：

- 解释为什么某轮对话没有调用工具。
- 解释为什么工具被拦截或进入 HITAS。
- 分析模型和 token 策略。
- 建立 golden set 防回归。

## 12. 设计约束

- 不在 prompt 中堆叠权限规则，权限应在 policy 和工具过滤层执行。
- 不让 LLM 在确认后重新规划高风险工具，确认后执行冻结参数。
- 不把普通分析请求升级为读文件工具，除非用户明确要求。
- 不让 Skill 隐式接管所有交付物请求。
- 不让低置信度 router 决策提高副作用权限。
- 不把 task orchestration 和普通 chat follow-up 混在同一职责里。
