# 对话系统设计与规范

> 更新日期：2026-08-30
> 关联文档：[06-HITAS设计](./06-Human-in-the-Loop%20Tool%20Approval%20设计.md)、[02-Skill体系](./02-Skill体系.md)

## 1. 文档定位

本文是 AriaAI 对话系统的设计规范。目标是把对话行为从“散落的 if-else 和 prompt 约束”收敛为可解释、可测试、可审计的执行契约。

核心原则：

- Mode 决定对话剧本。
- ActionPolicy 决定副作用权限。
- ToolAccessPolicy 决定工具可见性。
- P0-P4 phase 负责执行。
- HITAS 负责高风险工具调用确认。
- ChatTrace 负责可观测和回归分析。
- Conversation Capsule 负责跨轮目标、约束、工具结果、阻塞和下一目标续接。
- Instruction Manifest 负责显式指令优先级与冲突裁决。
- Durable Run Input 负责跨 Worker 的取消与运行中追加意图。
- Turn Recovery Contract 负责用持久 checkpoint、effect 事实和当前项目状态创建新的审计 Run。

## 3. 三个核心枚举

### 3.1 ChatMode

`ChatMode` 表示这轮对话的剧本。

```python
class ChatMode(str, Enum):
    STANDALONE_QA = "standalone_qa"
    PROJECT_DEEP_DIVE = "project_deep_dive"
    CROSS_PROJECT_PORTFOLIO = "cross_project_portfolio"
    WORKSPACE_INVENTORY = "workspace_inventory"
    SKILL_EXECUTION = "skill_execution"
    TASK_ORCHESTRATION = "task_orchestration"
```

| Mode | 触发场景 | 说明 |
|---|---|---|
| `STANDALONE_QA` | 无项目、无 Skill 的普通问答 | 不注入项目上下文 |
| `PROJECT_DEEP_DIVE` | 单项目内问答、分析、文件处理 | 注入项目结构化上下文 |
| `CROSS_PROJECT_PORTFOLIO` | 客户所有项目汇总 | 使用客户/项目组合上下文 |
| `WORKSPACE_INVENTORY` | 工作台项目清单或组合盘点 | 使用工作台项目上下文 |
| `SKILL_EXECUTION` | 用户显式选择或强制运行 Skill | 注入 Skill prompt 和工具 |
| `TASK_ORCHESTRATION` | 结构化交付物或 durable task | 移交 task orchestrator |

### 3.2 ActionPolicy

`ActionPolicy` 表示这轮对话允许产生什么副作用。

```python
class ActionPolicy(str, Enum):
    DIRECT_ANSWER = "direct_answer"
    READ_ONLY_TOOL = "read_only_tool"
    WRITE_ARTIFACT = "write_artifact"
    MODIFY_EXISTING_FILE = "modify_existing_file"
    DURABLE_TASK = "durable_task"
    DESTRUCTIVE_ACTION = "destructive_action"
```

| Policy | 说明 | 典型请求 |
|---|---|---|
| `DIRECT_ANSWER` | 只回答，不调工具 | “总结这个项目风险” |
| `READ_ONLY_TOOL` | 可读文件或上下文 | “读取 risk.md 并总结” |
| `WRITE_ARTIFACT` | 可新建交付物 | “生成一份 PPT” |
| `MODIFY_EXISTING_FILE` | 可修改现有文件，需确认 | “把这个文档改一下” |
| `DURABLE_TASK` | 交给 task orchestrator | “生成完整咨询提案” |
| `DESTRUCTIVE_ACTION` | 删除或破坏性动作，需确认 | “删除这些文件” |

### 3.3 ToolAccessPolicy

`ToolAccessPolicy` 表示模型能看到哪些工具。

```python
class ToolAccessPolicy(str, Enum):
    NONE = "none"
    INJECTED_CONTEXT_ONLY = "injected_context_only"
    READ_ON_DEMAND = "read_on_demand"
    EXPLICIT_FILE_READ = "explicit_file_read"
    WRITE_ALLOWED = "write_allowed"
```

| ToolAccessPolicy | 工具可见性 |
|---|---|
| `NONE` | 不暴露工具 |
| `INJECTED_CONTEXT_ONLY` | 不暴露工具，只使用已注入上下文 |
| `READ_ON_DEMAND` | 暴露只读工具 |
| `EXPLICIT_FILE_READ` | 用户明确读文件时暴露只读工具 |
| `WRITE_ALLOWED` | 根据 ActionPolicy 暴露读/写/改/删工具 |

重要规则：普通项目分析默认是 `INJECTED_CONTEXT_ONLY`，不是 `READ_ON_DEMAND`。只有用户明确要求读取具体文件或列出文件时，才暴露只读工具。

- `MODE_CONFIG` 已存在。
- runtime 已使用 mode/policy/tool_access 参与模型、token、上下文和工具过滤。

## 5. 意图路由

意图路由由两层组成：

1. `policy_guards.py`：确定性规则，识别身份请求、问题、读文件、写文件、修改、删除、项目分析、组合查询等。
2. `intent_router.py`：在规则基础上调用 LLM router 或 task router，并做策略夹紧，避免 LLM 把权限升级得过高。

路由输出：

```python
IntentDecision(
    chat_mode=...,
    action_policy=...,
    tool_access_policy=...,
    confidence=...,
    reason=...,
    method=...,
)
```

安全原则：

- 默认从严。
- 规则优先处理高确定性场景。
- LLM router 可帮助分类，但不能越过策略上限。
- destructive intent 必须包含明确删除动词和对象类型，避免误判。
- 修改、删除和长任务必须进入明确 policy。

### 5.1 Skill 是本轮能力，不是会话永久模式

`Conversation.skill_id` 只保存最近可续接的 Skill，不代表后续每轮都自动注入该 Skill。Runtime 每轮重新裁决：

- 用户显式选择或强制运行：本轮启用；
- 高置信、唯一候选：本轮自动启用；
- “继续、沿用刚才格式、补充行动项”等相关追问：续用最近 Skill；
- 普通无关问题、换话题或显式要求停用：释放最近 Skill；
- 新工作流命中另一 Skill：切换到新的有效 Skill。

本轮实际生效的 Skill ID、名称和来源由后端 `ChatRuntime` 决定，并通过 `run_started.skill` 回传。前端选择框只是用户输入，不能冒充实际执行结果。完整设计与评测矩阵见 [22-项目对话与Skill交互全量优化方案](./22-项目对话与Skill交互全量优化方案.md)。

### 5.2 Conversation Capsule 与指令优先级

Runtime 不再把自由文本 Working Memory 直接当成模型续接事实，而是每轮构建 `Conversation Capsule v1`。Capsule 保留目标、Turn 模式、当前 Artifact/Task、有效用户约束、完成决策、工具结果、未解除阻塞和下一目标，并通过以下边界防止串线：

- 同时绑定 `conversation_id` 与 `project_id`，跨项目历史 Capsule 不继承；
- 记录 `source_message_ids`、`previous_capsule_sha256` 和自身 `capsule_sha256`；
- 只保留安全、有界字段，不保存工具输入、完整输出、服务器路径或隐藏推理；
- 工具失败只有被后续成功通过 call ID 显式声明为 retry/recovery 时才解除阻塞；
- P4 把本轮工具结果与 Assistant 摘要写入消息元数据，下一轮再从数据库权威状态重建。

约束采用“保留为默认、显式重述才撤销”的规则。用户当前轮明确重述语气、详略、格式、语言或写入策略时，系统撤销同维度历史约束；“不用、不要、无需、取消、改为”等否定/切换表达也适用。普通“继续”不会清空其他要求。当前用户要求始终高于历史 Capsule、长期偏好和 Skill 默认值。

`InstructionManifest v1` 固定优先级如下：

1. 平台安全、权限和本轮产品策略；
2. 本轮用户明确要求；
3. 项目作用域与访问边界；
4. 当前交付物和任务状态；
5. 本轮有效 Skill；
6. 用户长期偏好；
7. 工作区/RAG 证据；
8. 历史 Conversation Capsule。

项目上下文、RAG、工具结果和历史摘要是数据，不是可执行指令。持久 Manifest 只包含层 ID、优先级、作用域、字符数和内容 SHA-256；原始 Prompt 仍只在本轮模型请求内存在。Capsule 与 Manifest 均进入 Context Assembly、ChatTrace 和 Run Evaluation 完整性校验。

Agent Loop 在领取耐久 Steering 前，先将基础 `ContextAssemblyManifest` 与精确的初始 Provider 请求校验。如果已通过身份、ACL、Message metadata 和内容 SHA-256 复核的 Steering 在 Assembly 后改变了本次请求，系统会产生不含正文的派生 Manifest：它绑定基础 Manifest SHA-256、耐久输入的 Run/序号/Message 身份与内容摘要，以及经工具 transcript 规范化和上下文预算后的精确 system/messages/tools 指纹。基础 Manifest 缺失或失配、输入身份非法、派生指纹失配都会在调用 Provider 前失败关闭；派生记录最多保留 24 个有界输入身份。

### 5.3 耐久 Run 控制与中断恢复

`POST /chat/runs/{run_id}/steer` 与 `POST /chat/runs/{run_id}/cancel` 不以当前 ASGI 进程的内存注册表为事实源。服务端先根据 `ChatRun` 解析 Conversation 并复检写权限，再把控制意图写入 `ChatRunInput`：

- Steering 正文仍只保存在普通 `Message(role=user)`；邮箱只保存 Run/Message 身份、序号和 SHA-256。
- Agent Loop 在模型请求或工具批次边界原子领取。取消优先：同批 Steering 转为 `unapplied`，不再注入当前 Run。
- Durable Task 路径只领取 cancel，不消费它不支持的 Steering；已创建的 `TaskRun` 进入 Aria 原生取消与终态收口边界。
- `applied` 只表示邮箱已被 at-most-once 领取，不证明 Provider 已收到正文。邮箱故障时运行失败关闭，不在忽略取消/纠偏后继续调模型或提交工具。

中断或失败后，前端先 GET 服务端重建的 `TurnRecoveryContract v2`，用户明确确认后才发送新 Turn。契约绑定来源 `ChatRun`、来源 Assistant Message、Rollout checkpoint、内容安全的 effect ledger、未应用/已领取输入身份与当前 Project World State，并由 `contract_sha256` 防止用旧预览启动新执行。
当前只允许通过同步 SSE `/chat/send` 启动恢复；`/chat/send-async` 会在创建 Message、子 Run 或后台 TaskRun 之前返回 409，避免绕过恢复预留和活化边界。

恢复不是旧 Run 的原地续跑：

- 新请求必须原子预留唯一的子 `ChatRun`，再启动 SSE。流尚未开始的 `reserved` 预留可在 TTL 后审计失效并重试；流已激活的 Run 不会被该 TTL 误回收。
- 只有来源 Run/会话/项目、`GeneratedFile`/`ProjectFile`、output identity、受控路径与实际文件字节 SHA-256 均仍精确匹配的已完成写入，才能返回 `already_completed`，不再调用工具。
- 该已验证结果会作为恢复子 Run 的可下载交付卡片和完成证据展示，但不会再次进入产物写入队列，也不会把来源 `GeneratedFile` 改挂到子 Run。用户会明确看到“已核验原任务已有附件、本次未重复生成”。
- 恢复中的任何新非只读动作都不能直接执行，必须先生成带恢复身份的签名 HITAS 供人工审阅。确认时会再次核对当前写权限与 Project World State，但确认结果固定失败关闭：包括项目 Office 创建/编辑和结构化 Markdown 三个 final-authorized writer 在内，全部保持零业务调用、零 `ProjectFile`，并要求用户人工核对后从 fresh non-recovery 新轮重新发起。原因是 Project World State 包含里程碑、待办、文件夹、文件等多个可独立变化的子资源，当前不能把全量状态 CAS 与任意业务写事务严格线性化。文件夹与文件的 `folder_id` 也属于状态事实；已观测到的状态改变、旧版记录、未知工具或不可验证结果同样转为人工核对。
- 恢复守卫不允许通过 HITAS 批量执行绕过该边界：只要一个多动作批次含有恢复守卫，整批会在任何工具注册表或业务写入前失败关闭；首项落 `failed`，其余仍在执行代的动作落 `skipped`。单动作同样只能审阅，不能成为恢复写入通道。
- 普通非恢复审批中，项目作用域且会变更状态的工具也只有项目 Office 创建/编辑和结构化 Markdown 三个 final-authorized writer 可以执行；它们在最终业务事务内重验 Actor、项目成员、签名和动作代。项目 scope 必须在 server runtime、审批动作和工具输入三处都是精确相等的正整数；`bool`、字符串、浮点数、零和负数全部拒绝。其他项目文件/文件夹及 legacy/external registry writer 在 registry 前失败关闭。项目会话中的非项目作用域全局工具不受这条特定边界误拦截，仍遵循自身签名、HITAS 与权限策略；但其 `tool_input` 顶层不得出现 `project_id` 键，无论值为 `None`、布尔、字符串、整数或浮点数都失败关闭。final-authorized prepare 后若最终授权或 CAS 失败，控制面只会对完全相同且仍 `executing` 的动作代 CAS 为 `failed`，不写业务数据；已有终态或已换代动作保持原状，批次剩余执行代收口为 `skipped`，不会遗留旧 generation 的 `executing` 悬挂项。
- 来源 Run 尚有待确认审批时一律进入人工核对，不能让仍可确认的旧动作与自动重新规划同时存在。普通 Agent Loop 的模型、工具、确认和持久化边界会在同一事务中领取邮箱并关闭 phase；最终持久化后不再接受“已取消”的假成功回执。
- `retry_read_step` 只允许重新规划只读步骤；任何写工具在执行器硬拦截。新的高风险操作仍需经过当前 Aria ACL 与 HITAS。

恢复前端不将 HTTP 200 或 legacy `done` 单独当作成功。它只在服务端发出激活后才可能出现的 `conversation_id` 或 `run_started` 后显示恢复用户气泡，并且只在同一 `run_id` 的 `run_started`→`run_done(final_status=completed|waiting_confirmation)` 完整收口后报告恢复已创建。用户停止、`run_done(cancelled)`、`run_failed`、空流、缺失启动身份或终态身份不一致均会拒绝成功回执；激活前停止也不会生成本地 Assistant 幽灵消息。

服务端也不在数据库终态成功前对外宣告完成：P4 先持久化 Assistant Message/交付证据，再原子收口 Rollout/`ChatRun` 终态；只有该终态事务提交成功后才释放 legacy `done` 和 Product `run_done`。终态提交失败只发送 `run_failed(PERSISTENCE_ERROR)`，不发送成功收口。

Phase 3O 已为激活后的 `ChatRun` 增加数据库 worker lease、fencing token、generation、heartbeat 与通用 reaper。同步 SSE 和异步后台聊天在启动/激活时绑定唯一运行代；邮箱领取、工具批次、checkpoint、Assistant Message 投影、Persist 和终态提交都必须匹配同一代且租约未过期。终态提交清除 owner/token/expiry，但保留 generation 与最后心跳作为无正文审计证据。

Scheduler 只把确定过期、缺失或结构损坏且超过保护期的活跃 Run 收口为 `interrupted`，同步写入 `run_interrupted`、失败的 `TaskRun` 投影和 `retryable=true`，并把未领取邮箱输入标为 `unapplied`。它不会接管旧 Run、重放 Provider、自动重试工具或业务写入；迟到 worker 在下一次工具、持久化或终态边界会因 token/generation 不匹配而失败关闭。若 Assistant Message 已先保存，它会在终态前以同一租约挂接到 `ChatRun`，因此回收后仍可按现有恢复合同核验；没有可核验 Assistant 投影时只能从 fresh Turn 重新发起。

`reserved` 恢复预留仍由独立 TTL 规则处理，通用 reaper 明确排除它，避免把“尚未激活的唯一预留”和“已经执行中的 worker 租约”混为一种接管语义。该机制不恢复 Provider 私有 transcript，不把 Prompt 建议当作幂等性。所有项目、任务、权限、审批和审计状态仍属于 Aria 原生服务。

Phase 3P 增加项目级“运行恢复”发现面。`GET /chat/projects/{project_id}/recovery-center` 只读聚合最近的 `cancelled` / `failed` / `interrupted` ChatRun，返回会话与消息身份、安全原因分类、Assistant 投影是否可验证、恢复子 Run、未应用 Steering 身份和有界窗口指标；不返回消息正文、Prompt、原始错误详情或 worker lease token。项目成员在对话左栏可看到待核对、未应用追问、已继续与缺少投影的轮次，并可定位到精确 Assistant Message。

恢复中心只是发现与审计投影，不生成合同、Message、TaskRun 或子 Run，也不回收预留。`ready` 只表示存在结构匹配的 Assistant Rollout 投影；用户点击“打开并核对”后仍必须调用既有 `recovery-preview v2`，重新验证当前 World State、effect ledger、输入身份和唯一恢复子 Run。`continued` 只链接既有后续运行，`projection_missing` 明确要求 fresh Turn，二者都不会触发自动重放。本阶段不新增数据库迁移。

Phase 3Q 增加对话级“当前协作状态”。`GET /chat/conversations/{conversation_id}/continuity` 先复用对话 ACL，再从最近有界 Assistant Message 中读取最新 `Conversation Capsule v1`；只有字段、版本、SHA-256、会话/项目范围和全部来源 Message 归属均通过校验时，才返回目标、下一步、Turn 模式、确认约束、决策摘要、阻塞和安全的当前 Artifact/Task 摘要。校验失败时 `state=null`，前端不会展示可疑内容；没有 Capsule 时明确返回 `unavailable`。接口不返回 Prompt、工具输入/输出、隐藏推理或 Assistant 内部摘要。

同一只读响应会独立读取当前项目记忆的 `open_questions` 槽位，并显式报告 missing/stale 状态；Capsule 无效不能污染项目记忆，项目记忆陈旧也不会冒充已确认事实。项目对话标题栏的“进展”面板只允许把当前目标、阻塞或待确认问题追加到输入框，保留已有草稿并要求用户核对后发送；当前 Run 执行中动作禁用，不自动发送、不创建 Run、不调用 Tool、不写项目状态。本阶段不新增数据库迁移。

Phase 3R 将该只读问题面升级为人工关单与复核闭环。Continuity Snapshot v2 返回 `open_questions` 独立槽位版本和最多 8 条最近解决记录；解决记录只含用户确认摘要、回答 Message/Conversation 身份、版本和复核状态，不返回回答正文。解决必须绑定当前对话内已持久化的 Assistant Message，且在同一事务中移除开放问题、退休事实、更新当前状态并追加不可覆盖的解决事件；记忆版本或槽位版本冲突时失败关闭。项目记忆后来发生变化时，旧结论显示“待复核”而不是由模型自动更新。重开必须由有写权限的用户填写原因，问题作为 pinned 锚点返回，每次再次解决也保留先前回答和说明。数据库契约由 `038_v1_38` 管理。

Phase 3S 在项目详情增加独立“问题”工作台，但不建立第二套问题事实。`open_questions` 仍决定哪些问题开放，`ProjectQuestionResolution` 仍决定解决/重开生命周期；`ProjectQuestionProfile` 只覆盖人工负责人、优先级和截止日期，并通过逐问题 revision 做 CAS。`GET /projects/{project_id}/questions` 在项目 ACL 后组合三类状态、项目成员和有界回答候选；只有可写成员且存在开放问题时才返回最多 40 条、每条最多 280 字的 Assistant 预览，不返回完整回答、Prompt、工具输入或隐藏推理。`POST /projects/{project_id}/questions/resolve` 允许用户从项目内任一对话选择已持久化回答，服务端再次核对 Message role、Conversation/Project scope，并复用 Phase 3R 的最终写锁和原子关单事务。责任变更由 `ProjectQuestionProfileEvent` 只追加记录，迁移契约为 `039_v1_39`。

Phase 3T 增加显式的“分析问题证据”，但不让自动评分决定问题真伪。无副作用的 `POST /projects/{project_id}/questions/{question_sha256}/evidence` 仅向项目可写成员开放，问题文本放在 JSON body 而不是 URL 日志中，并同时校验文本和 SHA-256 是否仍属于开放问题或解决账本。服务在当前项目权限下重新召回项目知识与 query-aware 项目记忆，以稳定 evidence identity 对齐最多 40 条已持久化 Assistant Message 的历史引用；最多返回 12 条排序候选、280 字预览和 8 条当前对齐来源。准备度由问题相关性、当前证据对齐、原 Run Evaluation 和已有人工反馈确定性计算；无效 manifest、跨项目记忆、无效引用、陈旧证据或低相关答案均失败关闭或降级提示。该分数明确 `is_correctness_verdict=false` 且始终 `requires_human_confirmation=true`，不会自动选择、解决或重开问题，也不返回检索正文、完整回答、Prompt、工具输入/输出或隐藏推理。本阶段复用消息 metadata 和现有证据账本，不新增数据库迁移。

Phase 3U 把 Phase 3T 的当前证据状态投影为确定性的补证草稿。`POST /projects/{project_id}/questions/{question_sha256}/remediation` 与证据分析使用相同的项目写权限和问题身份校验，并在生成前重新召回当前证据；规则引擎按确认、时间、数值、责任与一般问题五类识别目标证据，把陈旧记忆、仅上下文、无强候选、无效引用、当前来源不对齐等状态转为有界缺口，再生成追问、资料请求、内部核验、候选回答复核和最终人工确认五类动作。响应只包含问题正文、计数、缺口代码、草稿和基准 fingerprint，不包含候选回答预览、来源标题/正文、Prompt、工具输入/输出或隐藏推理。前端编辑、责任人选择、移除和自定义动作只存在于当前页面；接口和 UI 均不保存计划、不发消息、不调用工具、不改变问题状态，最终关单仍走 Phase 3R/3S 的人工授权与版本校验。本阶段不调用模型、不新增数据库迁移。

Phase 3V 为补证草稿增加 Aria 原生领域 HITAS，而不是复用 Conversation 绑定的工具审批。`prepare` 先在最终项目写锁内重新授权、核对当前问题/证据 basis 和来源动作，再持久化 24 小时有效的冻结预览；此时不会创建待办或沟通记录。独立 `confirm` 必须提交精确 snapshot 和 revision，再次授权并在同一项目锁内重新生成当前证据 basis，只有完全一致才原子创建 `ProjectTodo` 或 `ProjectCommunicationRequest`。后者由数据库 CHECK 固定为 `delivery_mode=manual_only`、`ready_for_manual_send`，系统不存在外发步骤；重复确认和相同 effect 通过幂等 key、action hash 与项目锁去重。拒绝、过期、证据漂移、负责人失效和快照完整性失败均写入只追加事件后失败关闭。迁移 `040_v1_40` 新增冻结预览、人工沟通请求和生命周期事件三表；确定性门禁扩展为 72 个场景、22 项指标。该流程不调用模型、工具或 Codex，也不能解决问题。

Phase 3W 将确认后的协作目标接入独立执行账本。项目“问题”页集中显示补证待办和人工沟通请求；沟通只允许用户证明“已在 Aria 外部人工发送”，产品没有发送 API，`delivered_by_aria` 永远为 false。每次附证和状态变化都在最终项目写锁内重新授权，提交 expected revision，并追加不可覆盖的 execution event。完成动作至少需要一条当前执行证据；项目文件和知识文档可作为当前项目直接来源，消息、外部链接和人工备注明确标为待复核。普通待办更新/删除不能绕过该生命周期。执行完成只改变原生待办或沟通请求状态，不自动解决问题；问题仍须走 Phase 3R/3S 的回答绑定、人工摘要和版本校验。`041_v1_41` 管理执行、证据附件和执行事件三表，并扩展人工沟通状态约束；确定性门禁为 75 个场景、23 项指标。该流程仍不调用模型、工具或 Codex。

Phase 3X 在整改执行中心为 `review_required` 证据增加显式“接受为人工支持/驳回证据”。浏览器提交附件自己的 expected review revision 和必填理由，后端在最终项目写锁内再次授权、锁定 execution/attachment/current review，并将每次实际变化写入按 review/revision 唯一的事件；直接项目文件/知识文档显示无需裁决，取消 execution 不允许新增裁决。接受只改变当前问题证据投影和补证 basis，不改变 execution revision，也不会写记忆事实、访问外链、发送消息、调用工具或解决问题。前端明确显示“人工接受（不等同事实）”以及最新裁决依据。`042_v1_42` 管理 current review/event 两表；门禁扩展为 78 个场景、24 项指标，仍不运行或连接 Codex。

## 6. 工具过滤

工具过滤分两步：

1. `filter_tools_for_access()` 根据 ToolAccessPolicy 决定模型能不能看到工具。
2. `policy_allows_tool()` 根据 ActionPolicy 与工具所需权限做 rank 比较。

工具所需权限来自：

- `services/tool_descriptions.py` 中的配置。
- `policy_guards._required_policy_for_tool()` 中的兜底规则。

示例：

- `read_project_file`：`READ_ONLY_TOOL`
- `write_project_office_document`：`WRITE_ARTIFACT`
- `update_project_markdown_document` replace/append：`MODIFY_EXISTING_FILE`
- `manage_project_files delete`：`DESTRUCTIVE_ACTION`

## 7. Consulting Turn Frame

`Consulting Turn Frame` 是对话系统的业务理解层。它不替代 IntentRouter，而是在 mode/policy 之上补充“这轮对话到底是在服务哪个咨询场景”。

当前支持的 `job_type`：

| job_type | 典型场景 | 输出倾向 |
|---|---|---|
| `pre_meeting_brief` | 会前 30 秒、见客户、客户会议准备 | 开场话术、客户优先级、避雷点、推进建议、会后动作 |
| `proposal_or_business_case` | 提案、建议书、SOW、报价、商业案例 | why now、诊断、方案、路线图、价值、风险、下一步 |
| `client_ready_presentation` | PPT、汇报材料、Deck | 结论先行 storyline、页标题、页面计划或交付物 |
| `meeting_intelligence` | 会议纪要、转写、行动项、决策 | 摘要、决策、行动项、风险、跟进信息 |
| `project_risk_diagnosis` | 风险、阻塞、延期 | 风险优先级、根因、影响、缓解动作、需决策事项 |
| `stakeholder_intelligence` | 干系人、决策人、客户偏好 | 干系人地图、可能立场、沟通策略、话术、风险 |
| `project_deep_dive` | 普通项目分析 | 结论、依据、影响、下一步 |

这一层解决两个问题：

- 用户说法经常很口语化，例如“30 秒后见客户”“这个客户怎么推进”“明天汇报怎么讲”。系统需要把它翻译成咨询工作类型，而不是只做关键词问答。
- Skill 和工具不应该为了“显得智能”而乱调；是否调用工具应由 Intent Frame 的权限和 Consulting Turn Frame 的业务目标共同约束。

Prompt 中会同时注入：

- `Intent Frame`：mode、policy、工具访问、response contract。
- `Consulting Turn Frame`：job_type、client_moment、memory_focus、response_shape、agent_protocol。

工程原则：学 Codex 的 observe -> reason -> act -> verify 执行循环，但输出形态必须服务咨询业务：客户关系判断、项目交付控制、会前决策、交付物质量和组织记忆沉淀。

## 8. P0-P4 Phase

| Phase | 文件 | 责任 |
|---|---|---|
| P0 | `p0_durable_task.py` | 判断是否升级为 durable task / task orchestrator |
| P1 | `p1_planning.py` | 模型规划和流式输出，收集 tool_use |
| P2 | `p2_tools.py` | 执行工具、做 policy 检查、生成 HITAS payload |
| P3 | `p3_followup.py` | 工具结果回注，让模型生成 follow-up |
| P4 | `p4_persist.py` | 持久化消息、生成物、Trace、PendingToolAction |

### P0

P0 判断用户请求是否需要结构化长任务，例如完整 PPT、报告、提案、复杂文档生成。如果是，则交给 `task_orchestrator`。

### P1

P1 调用 provider 生成回答或工具调用。此时模型只能看到 runtime 过滤后的工具。

### P2

P2 遍历 tool_use：

- 先判断工具是否被当前 policy 允许。
- 再判断是否需要 HITAS 确认。
- 可直接执行的工具立即执行。
- 需确认的工具生成 pending action payload，不执行。

### P3

工具执行完成后，P3 把工具结果重新注入模型，让模型生成面向用户的总结。若 P3 再次触发修改或删除工具，也应进入 HITAS。

### P4

P4 负责持久化：

- user/assistant message。
- artifacts。
- pending tool actions。
- chat trace。
- legacy confirmation fallback cleanup。
- 特定场景的 deterministic cleanup confirmation。

## 9. HITAS 接入点

HITAS 只处理需要用户确认的高风险工具动作：

- 修改现有文件。
- 删除文件或文件夹。
- 其他被配置为 destructive 或 modify 的工具。

流程：

```text
P2/P3 发现需确认工具
  ↓
构造 pending action payload
  ↓
P4 写入 PendingToolAction
  ↓
前端显示 Action Preview
  ↓
用户 confirm/reject
  ↓
后端确定性执行或拒绝
```

详细设计见 [06-Human-in-the-Loop Tool Approval 设计](./06-Human-in-the-Loop%20Tool%20Approval%20设计.md)。

## 12. 设计约束

- 不在 prompt 中堆叠权限规则，权限应在 policy 和工具过滤层执行。
- 不让 LLM 在确认后重新规划高风险工具，确认后执行冻结参数。
- 不把普通分析请求升级为读文件工具，除非用户明确要求。
- 不让 Skill 隐式接管所有交付物请求。
- 不让低置信度 router 决策提高副作用权限。
- 不把 task orchestration 和普通 chat follow-up 混在同一职责里。
- 不用 Prompt 中的“不要重复”代替 effect 验证、项目状态 CAS 或 HITAS。
- 不将未启动恢复预留的 TTL 回收扩大为任意运行中 Run 的自动接管。

## 14. Phase 3Y：核验证据驱动的重新回答（已实施）

问题工作台现在可以把当前 `direct` 或人工 `accepted` 的整改附件冻结为一次新的回答契约。准备接口只返回问题身份、附件身份、标题、审核版本、合同摘要和建议输入，不返回来源正文或审核理由；进入项目对话后，发送前会再次确认问题仍开放、记忆问题槽位仍 ready、附件未取消、审核仍接受，并按当前项目文件字节、知识文档 chunk、项目消息正文或人工记录重新计算来源摘要。任何漂移返回 409，且不会先持久化用户消息。

该 Turn 固定为 `answer_only / chat_only / write_allowed=false`，关闭 Skill 自动接管和全部工具，不写项目、记忆、消息外发或问题解决状态。最多 8 条来源作为不可信 workspace context 注入，每条使用稳定 `[A1]…[A8]` 键；外部引用只展示已保存定位符并明确“未访问”，不会自动抓取。Assistant Message 仅保存无正文 manifest、来源摘要和正文实际输出的合法 A 引用；没有输出的键不成为引用，无效键单独记录。前端只在服务端启动成功后显示受保护用户消息，证据漂移不会留下幽灵 Turn。用户仍须回到问题工作台重新分析并人工采用回答、填写摘要后才能关单。本阶段无数据库迁移。

## 15. Phase 4A：Skill 本轮加载与验证边界（已实施）

每个实际应用 Skill 的 Turn 现在都生成 `Skill Runtime Contract v1`。它从已经选定的不可变发布视图读取版本与 release SHA-256，只清点该发布 Prompt 中实际冻结的 bundled resources，并将 Skill 声明工具与 Aria 本轮策略过滤后的工具求交集。运行边界明确：Skill 仅对本轮生效；未列入发布快照的资源不注入；包内脚本永远不会因为被 Skill 文档引用而自动执行；最终业务写入仍由 Aria 权限、HITAS 和工具执行器决定。

Context Receipt 的 `skill.runtime` 只公开发布身份、加载/验证状态和计数，不公开 Prompt、schema、工具参数、路径、业务正文或模型推理。Provider 最终系统上下文必须仍包含完整 Skill body 才标记 `loaded`；预算压缩后降为 `compacted`，此时即使发布包声明过清单也不能宣称已经完成包级验证。Provider 会收到一段短边界说明：存在质量/验收清单时交付前应使用并披露未通过项；不存在或上下文不完整时不得声称已经完成包级验证。前端在历史消息“本轮依据”中显示同一份持久回执，旧 v1 消息缺少该可选字段时保持原展示。本阶段没有数据库迁移。

## 16. Phase 4B：交付物验证证据账本（已实施）

`Skill Runtime Contract v1` 现在对实际识别出的验收步骤和验收资源生成 `verification_plan_sha256`。交付物通过路径、项目文件与实际字节校验并写入 `GeneratedFile` 后，Aria 在同一事务中运行有界、只读、确定性的技术校验：文件存在、非空、扩展名、内容 SHA-256，以及 PPTX/DOCX/XLSX、PDF、PNG/JPEG、Markdown/文本/JSON/CSV/HTML 的格式完整性。校验器不读取业务正文到事件或日志，不运行 Skill 的 script、宏、嵌入代码或外部工具。

每次结果按 `GeneratedFile + content_sha256 + verifier_version + Skill release SHA-256` 幂等写入不可变 `ArtifactVerification`。状态严格区分：`passed` 仅表示已支持的技术检查通过且 Skill 未声明额外验收；`manual_required` 表示技术检查通过但 Skill 业务清单仍待人工确认；`partial` 表示格式不支持或完整 Skill 上下文未保留；`failed` 表示技术检查失败。`failed` 制品不能满足交付契约。`artifact_ready`、Assistant Message metadata、恢复附件和前端时间线只携带无正文摘要与证据 SHA-256；授权用户可读取同样无路径、无正文的逐项证据。迁移 `043_v1_43` 建表并保持单一 Alembic head。

## 17. Phase 4C：业务验收与最终交付门禁（已实施）

交付物预览现在把不可变技术证据与独立的人工业务验收合成为最终交付门禁。`failed` 或 `partial` 技术证据不能被人工覆盖；无 Skill 业务清单且技术通过的制品直接进入 `ready`；`manual_required` 制品必须由当前会话所有者或项目可写成员填写判断依据后接受或退回。每次判断都绑定精确 `verification_id + content_sha256 + evidence_sha256 + verification_plan_sha256`，使用 expected revision 防止并发覆盖，并同时维护当前态与 append-only 事件历史。接受只表示“允许最终交付”的人工判断，不是真值认证，不自动写记忆、不关闭项目问题、不发送外部消息。

Aria 同时提供自有声明式业务校验器注册表，当前仅允许对已验证的页数、幻灯片数、工作表数、段落数、文本行数、CSV 行数和图片尺寸执行有界阈值检查。未知规则一律 `skipped/partial`；Skill 包内 script、宏、shell、动态 callable 永远不可进入注册表执行。迁移 `044_v1_44` 创建验收当前态和审计事件两表并保持单一 Alembic head；确定性门禁扩展为 99 个场景、29 项指标。

## 18. Phase 4D：结构化交付物选择与制品绑定（已实施）

Aria 从当前不可变 `SkillRelease` 的 `Deliverable Catalog` Markdown 表格确定性解析结构化目录。目录项包含稳定 ID、适用场景、最低内容、规范化格式、阶段、允许的归档目标、人工复核要求，以及逐项 contract SHA-256；整个目录另有 catalog SHA-256，并绑定 Skill release SHA-256。`GET /skills/{skill_id}/deliverables` 只返回该活动发布的有界目录，不加载或执行 Skill 包脚本、宏、shell、动态 callable。

项目对话仅在用户明确指定 Skill 后显示交付物选择器。发送时客户端提交 `deliverable_id + catalog_sha256 + contract_sha256`，服务端针对本轮实际分配到的发布重新生成并核对目录；发布、目录或条目漂移一律 409，不能按名称降级匹配。通过核对的合同进入 Provider 边界、Message metadata、Context Receipt 与历史“本轮依据”，上下文压缩后仍保留精确身份，且明确保存、记忆更新、外部交付和业务验收仍是独立的 Aria 授权动作。

生成文件持久化时，`GeneratedFile` 同步保存交付物 ID、名称、条目合同、目录和 Skill 发布 SHA-256，流式附件与制品预览显示同一合同短摘要。用户可在技术校验通过后明确点击“保存到项目文档”；服务端在最终写入前重做项目写授权、锁定制品、核对请求 SHA-256 与实际文件字节，并将 `project_file_id`、操作者和时间回写到 `GeneratedFile`。同一制品重试复用项目文件，且该动作明确不写项目记忆、知识库或外部消息；新项目文档会仅将旧的派生记忆标为待重建，避免其继续声称已覆盖完整资料。迁移 `045_v1_45` 幂等增加字段、外键与索引并保持唯一 Alembic head；没有显式选择的历史/新制品以空字段兼容。目录已覆盖全部 48 个内置 Skill，共 311 个条目；确定性发布门禁扩展为 104 个场景、30 项指标。
