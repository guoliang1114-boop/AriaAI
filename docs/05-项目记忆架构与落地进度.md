# 项目记忆架构与落地进度

更新时间：2026-04-21

## 1. 目标

项目记忆体系的目标不是每次把全量上下文直接塞给模型，而是把业务事实沉淀为可复用、可缓存、可异步处理、可运营、可治理的长期资产。

当前体系包括：

- 项目级三层记忆：原始业务上下文 -> 结构化项目记忆 -> 多视角摘要。
- 客户级第四层记忆：跨项目沉淀客户经验、偏好、关系信号和交付经验。
- 客户侧结构化干系人：客户关系网络的独立实体，注入 AI 上下文。
- 后台任务治理：重建、预热、缓存、失败、重试、预算、告警。

## 1.5 客户侧干系人定义

在 AI 总结、项目记忆和客户记忆里，"干系人"专指**客户侧关系网络**，而不是内部项目成员。

分类：

- **联系人**：日常沟通对象、业务接口人、采购或商务接口。
- **决策人**：能影响预算、验收、采购、续约或项目方向的人。
- **使用方**：最终使用系统、服务或交付物的人。
- **影响方**：法务、财务、IT、安全、品牌等会影响推进节奏的人。

内部项目成员属于项目协作范围，放在项目设置和任务分配里，不作为干系人管理的核心对象。

为什么重要：

- 风险摘要的影响判断取决于面向的决策人和使用方。
- 客户视角摘要需要避开敏感点，贴近关键人的关注语言。
- 下一步建议往往是"找谁确认什么问题"，而不是通用推进建议。
- 跨项目复用的核心是客户的决策偏好和关系风险，而不是项目成员。

`ClientStakeholder` 字段：姓名、角色、组织层级、影响类型（决策/使用/验收/采购/财务/法务/IT/安全）、关系状态（supportive / neutral / blocked / unknown）、关注点、敏感点、沟通偏好、联系方式、最近动作、备注。

## 2. 分层架构

### 第一层：原始业务上下文

来源包括：

- 项目基础信息、阶段、客户、金额、状态。
- 项目成员、里程碑、待办、财务、笔记。
- 项目文档与知识库文档。
- 项目聊天与生成物。
- 客户资料与关联项目。

### 第二层：结构化项目记忆

存储位置：`Project.context_memory_json`

核心字段：

- `project_brief`
- `current_stage`
- `current_objective`
- `recent_progress`
- `key_risks`
- `open_questions`
- `next_actions`
- `important_documents`
- `financial_status`
- `delivery_signals`
- `stakeholder_notes`
- `memory_version`
- `last_updated_at`
- `stale`
- `rebuild_log`
- `_coverage`
- `_client_promotion`
- `_last_failure`

扩展能力：

- `key_risks / open_questions / stakeholder_notes` 支持 `ai + pinned` 双层结构。
- 支持 `memory_stale / memory_version / memory_updated_at`。
- 支持 `memory_rebuild_status / memory_rebuild_failed_at`。
- 支持槽位级增量更新。
- 支持手动提升到客户记忆。
- 支持 AI 记忆锚点独立治理页。
- 支持客户侧干系人固定提醒进入项目摘要和聊天上下文。

### 第三层：项目视角摘要

基于结构化项目记忆生成，并按 `project_id + memory_version + summary_type + language` 缓存。

已支持视角：

- `overview`
- `risk`
- `stakeholder`
- `delivery`
- `client-facing`
- `financial`
- `documents`

### 第四层：客户记忆

存储位置：`ClientRecord.client_memory_json`

核心字段：

- `client_profile`
- `decision_patterns`
- `key_contacts`
- `lessons_learned`
- `project_history`
- `sensitive_topics`
- `source_project_ids`
- `memory_version`
- `last_updated_at`
- `stale`
- `rebuild_log`
- `_last_failure`

已支持视角：

- `overview`
- `stakeholder`
- `lessons`
- `client-facing`
- `risk`
- `opportunity`
- `relationship`
- `delivery`

作用：

- 为客户范围聊天提供长期上下文。
- 为新项目提供更强起点。
- 沉淀跨项目客户经验。
- 支持客户空间复用交付洞察。
- 为项目干系人页提供客户关键联系人、决策模式和敏感议题。

## 5. 下一阶段建议

### Sprint 1：Skill 回流到记忆系统

1. 项目/客户空间显性启动 Skill。
2. Skill 自动带入项目/客户记忆。
3. Skill 结果保存为项目文档、项目笔记、客户记忆沉淀。
4. 保存后触发项目/客户记忆刷新或预热。

### Sprint 2：记忆版本化

1. 设计独立 memory 主表。
2. 保存历史版本和触发来源。
3. 支持查看 diff。
4. 支持回滚到历史版本。

### Sprint 3：任务治理策略化

1. 服务端聚合失败统计。
2. 批量重试和批量忽略。
3. 对 `database / data / unknown` 增加人工确认。
4. 预算与限流策略配置化。

## 6. 当前结论

项目记忆和客户记忆已经进入可用 V1，并且具备后台任务治理、失败重试、预算与告警的基础运营能力。下一版本的重点不应继续堆单点能力，而应围绕“Skill 工作流化”和“记忆治理产品化”推进。

## 7. 2026-04-21 摘要生成治理补充

- 多视角摘要已从“每个卡片独立触发”收敛为“同一项目/语言/记忆版本的生成全部请求前端合并”，减少同一用户动作带来的重复 LLM 调用。
- 后端仍保留项目级 summary lock 兜底，同一项目、摘要类型、语言、记忆版本会互斥生成，避免自动刷新和手动重新生成并发写缓存。
- 摘要缓存读取现在能表达两种状态：缓存不存在表示尚未生成；缓存存在但内容为空表示已生成但该维度缺少可总结信息。
- UTC 时间来源已统一到 `utc_now_naive()`，项目记忆、客户记忆、摘要缓存、任务调度和测试用例不再直接调用 `datetime.utcnow()`。
- 下一步建议把摘要任务状态进一步产品化：展示生成来源、是否命中缓存、最近生成时间、空内容原因和是否受限流影响。
