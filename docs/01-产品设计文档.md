## 1. 产品定义

AriaAI 的目标不是替代咨询顾问，而是把顾问的高频工作组织成 AI 原生工作台：

- 用项目承载长期上下文
- 用客户和知识库承载事实基础
- 用 Skill 承载方法论和任务模板
- 用聊天承载交互和生成
- 用模板与文件生成承载交付物输出

一句话产品主张：

> 让顾问在真实项目中，更快地产出可交付材料，而不是只获得一段聊天回答。

## 4. 产品核心对象

### 4.1 Project

产品主上下文载体，聚合：

- 基础信息
- 文件
- 里程碑
- 财务
- 笔记
- 上下文摘要
- 对话

### 4.2 Skill

Skill 是产品中最接近“方法论模板”的对象，包含：

- 名称
- 分类
- 描述
- `system_prompt`
- `user_template`
- `tools_definition_json`

### 4.3 Conversation

Conversation 是具体执行过程，可挂在：

- `project_id`
- `skill_id`

这使得产品支持两类入口：

- 从项目出发的长期工作流
- 从技能出发的快速任务流

## 5. 用户主链路

### 5.1 项目工作链路

```text
登录
-> 进入 Welcome / Projects
-> 打开项目
-> 查看项目上下文 / 文件 / 里程碑 / 财务
-> 在项目内发起聊天
-> AI 基于项目、技能、文档和文件生成输出
-> 生成物沉淀到 artifacts / uploads
```

### 5.2 快速技能链路

```text
登录
-> 进入 Skills 或 Chat
-> 选择 Skill
-> 载入 user_template
-> 发起任务
-> 执行工具 / 输出交付物
```

### 5.3 知识检索链路

```text
上传文档
-> 解析文本
-> 切块 + embedding
-> query top-k
-> 注入聊天上下文
```

## 6. 当前产品优势

- 数据模型已经覆盖咨询场景的主要对象
- 项目和会话已经形成基本闭环
- Web 与 macOS 双端并行
- 文件生成能力不是概念而是已接入工具链
- Skill 已经从静态 prompt 走向可挂工具的结构化能力

---

## 7. 当前产品短板

- 代码中仍有大量乱码，直接影响体验和开发效率
- Web API 地址配置分裂，设置页不能稳定影响所有请求
- RAG 仍是 baseline，解释性和规模性有限
- 调度任务链路有明显实现缺陷
- 仓库边界混乱，运行产物进入版本库

---

## 8. 设计原则建议

后续功能设计建议坚持四条原则：

1. 项目优先：所有高价值能力优先挂在项目上下文下，而不是新增孤立页面。
2. 生成可交付物优先：报告、PPT、纪要、总结比“回答更长”更重要。
3. 双端一致：Web 与 macOS 应共享对象模型、状态语义和 API 契约。
4. 配置单一来源：模型、API、服务器、语言配置都要有明确 source of truth。

---

## 9. 下一阶段产品重点

- 做深项目内聊天与沉淀闭环
- 统一服务器与模型配置来源
- 强化客户、项目、知识三者的联动
- 把技能市场从“配置页”升级成“工作流资产”
- 增强生成物的管理、预览、复用与回溯

---

## 10. 非目标

当前阶段不建议优先投入：

- 多租户复杂权限系统
- 高度通用的流程编排器
- 大规模 agent orchestration
- 过早的插件市场化

这些能力应建立在核心项目闭环稳定之后。
