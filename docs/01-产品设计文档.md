## 1. 产品定义

AriaAI 的目标不是替代顾问，而是把顾问团队高频、可结构化、可沉淀的工作组织成 AI 原生工作流：

- 用项目承载长期上下文
- 用客户和知识库承载事实基础
- 用 Skill 承载方法论与任务模板
- 用对话承载协作与生成
- 用文件生成与导出承载交付物

一句话总结：

> 让 AI 在真实项目里持续协作，并输出可交付成果，而不只是一次性聊天答案。

## 4. 核心对象模型

### 4.1 Project

项目是当前产品最核心的业务容器，聚合：

- 基础信息
- 文件与文件夹
- 里程碑
- 财务记录
- Markdown 笔记
- 待办事项
- 上下文摘要
- 对话

### 4.2 Conversation

Conversation 是一次具体协作过程，可挂接：

- `project_id`
- `skill_id`

这使产品既支持“项目内长期协作”，也支持“从 Skill 快速起任务”。

### 4.3 Skill

Skill 更像“可执行的方法论模板”，包含：

- 名称与分类
- 描述
- `system_prompt`
- `user_template`
- `tools_definition_json`

### 4.4 KnowledgeDocument

知识文档承担可检索资料来源，当前状态机为：

- `pending`
- `processing`
- `synced`
- `failed`

## 5. 核心链路

### 5.1 项目协作链路

```text
登录
-> 进入 Welcome / Projects
-> 打开项目
-> 查看概览 / 文件 / 里程碑 / 笔记 / 待办
-> 在项目内发起聊天
-> AI 基于项目上下文、技能、知识和文件生成输出
-> 结果沉淀为消息、导出文件或项目资料
```

### 5.2 Skill 快速任务链路

```text
登录
-> 进入 Skills 或 Chat
-> 选择 Skill
-> 填写 user_template
-> 发起任务
-> 工具调用 / 生成交付物
```

### 5.3 知识检索链路

```text
上传文档
-> 解析文本
-> 切块 + embedding
-> 检索 top-k
-> 注入聊天上下文
-> 返回结构化引用
```

## 6. 当前产品优势

- 项目、知识、聊天和文件生成已经形成基本闭环
- 双端共用同一后端 API，契约正在逐步统一
- 项目空间开始具备持续协作属性，而不是静态详情页
- 导出、引用、待办、笔记这些“交付辅助能力”已经落地

---

## 7. 当前产品短板

- 项目页复杂度偏高，体验与实现都在一个超大页面里
- 多处中文文案仍有乱码，直接影响专业感
- RAG 检索仍是 baseline，解释性和扩展性有限
- Welcome 与项目空间的闭环还没完全打通
- 自动化测试覆盖面与增长速度不匹配

---

## 8. 设计原则

1. 项目优先：高价值能力优先挂在项目上下文中。
2. 交付优先：让输出更接近邮件、摘要、PPT、报告，而不是更长的回答。
3. 契约优先：前后端状态值、枚举和配置来源必须一致。
4. 沉淀优先：对话结果要能回流到项目、知识或文件资产。
