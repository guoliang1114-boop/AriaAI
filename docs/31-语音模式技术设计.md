## 1. 背景

AriaAI（v3.4）是已上线的 agentic workspace：streaming agent chat、tool calls、RAG、三层记忆、Skill、定时任务、HITL 审批，模型默认 Claude。目标：在这套后端上长出一个 Muse-like 的个人助手 App——手机上能用、会说话、能办生活里的事。

原则：**后端复用，端侧与工具做加法**。不重写 agent。

## 2. 目标与非目标

目标（MVP）：
- 手机上可用的个人助手：对话 + 语音（见 §6）
- 生活类工具：邮件、日历、天气、提醒、网页搜索（见 §5）
- 个人记忆成为默认工作区（不挂靠项目）

非目标（v1 不做）：
- to-B 咨询能力的移动化（另一条线）
- 应用商店上架（先 TestFlight / PWA 验证）

## 3. 总体架构

```
[移动端] --HTTPS/WS--> [AriaAI 后端（复用）] --> [模型层 provider_selector]
   |                        |
 语音/聊天 UI          agent_harness / tools / RAG / memory / Skill / HITL / 定时
   |
 新增：生活类工具（email / calendar / weather / search / reminder）
```

## 4. 工作流一：移动端

### 4.1 选型对比

| 方案 | 优点 | 代价 | 结论 |
|---|---|---|---|
| PWA（移动 Web） | 最快；复用现有 React 前端；免上架 | iOS 推送/后台受限 | MVP 验证用 |
| React Native | 真原生；复用 TS/React 技能；可上架 | 新工程，中等工作量 | 正式版 |
| Flutter | 性能好 | Dart 栈不复用，团队技能分裂 | 不推荐 |

推荐路线：**PWA 先跑通 → React Native 正式版**。v1 不写原生。

### 4.2 范围

- 响应式聊天 UI（复用 web/）
- PWA：manifest、service worker（离线壳）、推送（APNs/FCM 经后端）
- 语音 UI（见 §6）

## 5. 工作流二：生活类工具

现有工具偏办公交付（PPT/Word/PDF）。新增（走现有 tool 注册机制）：

| 工具 | 说明 |
|---|---|
| email | 收发邮件（Gmail 起步） |
| calendar | 查 / 建日程 |
| weather | 天气查询 |
| reminder | 提醒 → 复用定时任务 |
| web_search | 网页搜索 |

每个工具独立 PR；HITL：发邮件、删日程等高风险操作走确认卡（见 06 设计）。

## 6. 工作流三：语音模式技术设计

核心原则：**语音是新的 I/O 模态，不是新的 agent**——STT/TTS 只负责"耳朵和嘴"，思考、工具、记忆、审批全部复用现有 pipeline。

### 6.1 总体架构

```
[麦克风] --音频帧--> [VAD] --语音段--> [流式 STT] --final文本--> [Agent Pipeline]
                                                                          |
                                                                    文本流（逐句）
                                                                          v
[扬声器] <--音频帧-- [流式 TTS] <--语音合成 <------------------ [打断控制]
   ^                                                        |
   └────────────── 用户说话（barge-in）──────────────────────┘
```

### 6.2 传输层：WebSocket

- 新增 `/ws/voice` 端点（或复用现有 WS 基础设施，需看代码确认）
- 二进制帧：音频（16kHz PCM；Opus 可选）
- JSON 控制消息：`session.start` / `session.stop` / `vad.speech_start` / `vad.speech_end` / `interrupt` / `state`
- v1 不用 WebRTC：复杂度高，WS 足够支撑半双工 + 打断

### 6.3 VAD（语音活动检测）

- 首选客户端 VAD（silero-vad ONNX 跑在浏览器）：省带宽、延迟低
- 服务端 VAD 兜底
- 输出 speech_start / speech_end 事件，驱动回合状态机

### 6.4 STT（流式语音识别）

- Provider 接口抽象（参考 provider_selector 模式）：alibaba / tencent / volcengine / deepgram
- 中文优先；首字延迟目标 < 500ms
- partial 结果只用于 UI 显示，不进 agent；final 结果进 pipeline

### 6.5 TTS（流式语音合成）

- Provider 接口抽象：minimax / volcengine / alibaba cosyvoice
- LLM 流式输出按句切分，逐句送 TTS，边合成边播放
- 首音延迟目标 < 1s

### 6.6 回合状态机与打断

- 状态：`idle → listening → thinking → speaking → idle`
- speaking 期间 VAD 检测到用户说话 → 发送 `interrupt`：
  1. 停 TTS 播放与合成
  2. 取消 LLM 流（复用 turn_retry 取消机制）
  3. 切回 listening
- 防误触：音量 + 最小时长双阈值，可配置

### 6.7 HITL 在语音模式下（硬性要求）

- 高风险 tool call 仍需**显式 UI 确认**，不接受纯语音确认
- 流程：语音触发审批 → TTS 播报"需要你在屏幕上确认" → 前端置顶确认卡 → 用户点击后继续
- 确认卡组件复用现有（见 06 设计）

### 6.8 前后端改动清单

后端（`backend/`）：
- `app/routers/voice.py`：`/ws/voice` 端点，音频帧 + 控制消息协议
- `app/services/stt.py`：STT provider 抽象 + 首个实现
- `app/services/tts.py`：TTS provider 抽象 + 首个实现
- `app/services/voice_turn.py`：回合状态机 + 打断控制
- 复用（不改）：agent_harness、provider_selector、HITL、memory、RAG

前端（`web/`）：
- `useVoiceChat` hook：麦克风采集（AudioWorklet）、播放队列、状态机
- 语音 UI：状态指示（听 / 想 / 说）、打断按钮、静音
- 语音模式下审批确认卡置顶

### 6.9 语音迭代路线

- Phase 1（MVP，半双工 / 按键说话）：WS 音频通道 + STT/TTS 各接一家 + 复用 pipeline；无打断
- Phase 2（全双工）：客户端 VAD + barge-in + 回合状态机 + 句级流式
- Phase 3（电话）：PSTN 网关（Twilio / 阿里云）→ 同一套 pipeline

## 7. Muse 功能对标（供 Aria 参考）

Muse（Meta 的个人 AI agent 产品）是本方案的对标对象。下表列出值得 Aria 参考的功能、Aria 现状与建议。

| Muse 功能 | 说明 | Aria 现状 | 参考建议 |
|---|---|---|---|
| 以用户为中心的长期记忆 | 记住用户本人、偏好、决策、关系；后台持续学习用户 | 三层记忆（用户/项目/客户），但核心抽象是项目 | 把 user scope 做成默认工作区；参考后台对齐学习机制 |
| 主动性 | 后台做研究，只在值得打扰时主动说；用户可配偏好 | 有定时任务（APScheduler） | 加上"是否值得打扰"的判断 + 用户偏好配置 |
| 目标跟踪 | Goals：用户目标 + 事项跟踪 + 进度简报 | 无个人目标维度 | 增加个人目标/事项跟踪 |
| 语音 | 语音消息、TTS、播客、实时语音通话 | 本方案 §6 | 按 §6 实施 |
| Artifacts | 可交互交付物（文档/网页/表格/演示），用户可打开使用 | PPT/Word/PDF 生成（文件为主） | 交付物做成可交互、可回看的形态 |
| Feed | 定时生成的个人简报流 | 无 | 每日简报（如晨间 agenda） |
| Ideas | 灵感卡片，用户点选即构建 | Skill 偏工程化 | 更轻量的"点子 → 构建"闭环 |
| 计划任务 | cron 定时 + hooks 事件触发 + reminders | APScheduler | 对标 cron/hook 语义 |
| 生活连接器 | 邮件、日历、浏览器、购物、支付、设备联动 | 缺生活类（本方案 §5） | 按 §5 补 |
| HITL 审批 | 审批卡，关键操作前让用户确认 | 有（06 设计） | 对标体验；语音下见 §6.7 |
| 多端 | iOS / Android / Web / Mac + 消息通道 | 无移动端（本方案 §4） | 按 §4 实施 |
| 聊天内交互卡片 | 选项、地图、列表等可点击 UI | 无 | 聊天 UI 组件化 |
| 子代理分工 | 后台子代理并行干活，主对话保持响应 | 有 agent_harness | 长任务拆分子代理并行 |
| Library | 文件/媒体/产物的统一收藏 | 知识库偏文档 | 个人文件的统一收藏 |

## 8. 数据与隐私

- 仓库公开：个人数据功能（记忆、邮件、日历）是否进私有 fork，待决策
- 密钥走 Setting / 环境变量，不进仓库（§6 同）
- 音频、邮件正文默认不落盘（用户记忆 / 知识库显式授权除外）

## 9. 迭代路线

- Phase 0（文档）：本方案（当前）
- Phase 1（MVP）：PWA 壳 + 生活类工具前 3 个 + 语音 Phase 1（半双工）
- Phase 2：React Native + 语音 Phase 2（全双工打断）+ 剩余工具
- Phase 3：电话网关；应用商店
