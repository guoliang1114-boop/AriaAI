## 1. 文档目的

本文用于把 AriaAI 从“模块化 AI 工作台”升级为“专业咨询顾问的 Agentic Workspace”。它不是战略讨论文档，而是面向后续产品升级、研发拆解、验收和优先级判断的功能设计说明书。

本文重点回答：

- 升级后的产品形态是什么。
- 用户从哪里发起 AI 工作。
- AI 如何组织上下文、执行 Skill、生成交付物、沉淀记忆。
- 前端页面需要如何变化。
- 后端需要补哪些核心对象和服务。
- 每个阶段做到什么程度才算完成。

## 2. 产品定调

AriaAI 的目标不是做通用 Agent 开发平台，也不是做单纯聊天助手，而是：

> 面向专业咨询顾问的 Agentic Workspace。它把客户、项目、联系人、知识库、Skill、交付物和记忆组织成一套可追踪、可复用、可沉淀的咨询交付 Agent 系统。

这个定调对应三个产品判断：

| 判断 | 含义 |
|---|---|
| 用户不是来搭 Agent | 用户来完成会前准备、方案建议、风险分析、项目复盘、客户机会判断等咨询工作 |
| Agent 不是一个聊天框 | Agent 是围绕项目和客户运转的一套工作循环 |
| 底层模型能力可以替换 | Aria 的长期价值在上下文、方法论、交付物标准和团队经验沉淀 |

## 3. 升级目标

### 3.1 产品目标

1. **让 AI 工作可追踪**：每一次复杂 AI 工作都能看到目标、阶段、产出、保存位置和失败状态。
2. **让 Skill 交付物化**：核心咨询 Skill 不只是提示词，而是能稳定产出可保存、可复用、可审查的交付物。
3. **让知识和记忆闭环**：知识库、项目文件、客户记忆、联系人信息和项目记忆可以共同支撑 AI 工作，并把高价值结论回流为记忆。
4. **让工作台任务化**：产品入口从“功能导航”逐步升级为“我要完成什么咨询任务”。
5. **让用户少感知系统复杂度**：普通问答保持安静；长任务和写入动作才展示进度、确认和结果。

### 3.2 工程目标

1. 建立统一 `Run` 模型，收口 Chat、Skill、Tool、Artifact、Memory Update 和 Approval。
2. 建立面向前端的 Product Run Event 协议，避免把底层工具日志直接展示给用户。
3. 建立 Skill Run、Artifact、Memory Candidate 和 Source Citation 的关联关系。
4. 建立核心工作流的测试和验收机制，降低项目对话、Skill、知识库和记忆的回归风险。

### 3.3 非目标

短期不做：

- 不做面向普通用户的 Agent 配置平台。
- 不做复杂多 Agent 编排界面。
- 不把 MCP、模型路由、工具市场作为用户主入口。
- 不默认展示底层 trace、工具日志和调试信息。
- 不为了外部 Agent 生态兼容而牺牲咨询交付体验。

## 4. 目标用户与核心场景

### 4.1 用户角色

| 角色 | 典型目标 | 对产品的要求 |
|---|---|---|
| 咨询顾问 | 快速准备会议、整理材料、生成初稿 | 低摩擦、高效率、结果可编辑 |
| 项目经理 | 跟踪项目进展、识别风险、沉淀复盘 | 可追踪、可复用、可管理 |
| 总监/合伙人 | 判断客户机会、复核方案质量、管理交付风险 | 可信、可解释、有证据 |
| 售前/交付团队 | 复用历史案例、准备方案和客户沟通材料 | 能检索团队经验，能产出结构化交付物 |

### 4.2 北极星场景

第一阶段最重要的北极星场景是：

> 顾问进入某个项目或客户页面，点击“会前准备 / 风险分析 / 方案建议 / 项目复盘”，Aria 自动读取项目、客户、联系人、历史对话、文件和知识库，生成可保存的交付物，并把重要结论沉淀为候选记忆。

### 4.3 关键用户故事

| 编号 | 用户故事 | 优先级 |
|---|---|---|
| US-01 | 作为顾问，我希望在项目页直接发起会前准备，并得到结构化简报 | P0 |
| US-02 | 作为顾问，我希望 AI 在回答项目问题时自动引用项目记忆和相关资料 | P0 |
| US-03 | 作为项目经理，我希望每次复杂 AI 工作都有状态、步骤和结果记录 | P0 |
| US-04 | 作为顾问，我希望 Skill 结果可以一键保存为项目文档或项目笔记 | P0 |
| US-05 | 作为总监，我希望重要结论能看到来源，而不是只看到模型判断 | P1 |
| US-06 | 作为团队成员，我希望历史项目经验能进入知识库并被后续项目复用 | P1 |
| US-07 | 作为顾问，我希望客户和联系人信息能影响会前准备和沟通建议 | P1 |
| US-08 | 作为管理员，我希望高风险写入、删除和记忆更新需要确认或可回滚 | P1 |

### 5.2 优先级范围

| 范围 | 必须做 | 可以延后 |
|---|---|---|
| Run 运行层 | 统一 Run、Step、Event、Artifact 关联 | 完整可视化 trace 调试台 |
| 项目对话 | 普通问答轻量 Run、长任务完整 Run | 多人协同编辑消息 |
| Skill | 核心 Skill 交付物化、Skill Run 记录 | 全量 Skill 一次性升级 |
| 知识库 | 来源引用、服务项目和 Skill | 复杂知识图谱 |
| 记忆 | 候选记忆、确认、来源 | 自动长期记忆全自动写入 |
| 页面 | 工作台/项目/客户的任务入口 | 完整重新设计所有页面 |

## 6. 核心概念设计

### 6.1 User Goal

用户目标是一次 AI 工作的业务起点。它不是用户输入的原始文本，而是系统识别后的任务意图。

| 字段 | 说明 |
|---|---|
| `goal_id` | 目标 ID，可选 |
| `goal_type` | `question`、`meeting_brief`、`risk_analysis`、`proposal`、`retrospective`、`opportunity_analysis`、`artifact_generation` |
| `source_surface` | 发起页面：`workspace`、`project`、`client`、`contact`、`skill`、`chat` |
| `raw_input` | 用户原始输入 |
| `normalized_goal` | 系统归一化后的目标 |
| `target_entity` | 关联项目、客户、联系人或知识库 |

### 6.2 AI Run

`Run` 是一次完整 AI 工作的产品状态机。

| 字段 | 说明 |
|---|---|
| `run_id` | 唯一 ID |
| `run_type` | `chat`、`skill`、`workflow`、`artifact`、`memory` |
| `display_mode` | `silent`、`compact`、`timeline`、`approval_required` |
| `status` | `queued`、`running`、`waiting_confirmation`、`completed`、`failed`、`cancelled` |
| `user_goal` | 本次 Run 要完成的目标 |
| `context_pack_id` | 本轮使用的上下文包 |
| `artifact_ids` | 生成或更新的交付物 |
| `memory_candidate_ids` | 产生的候选记忆 |
| `approval_ids` | 需要或已完成的确认动作 |
| `created_by` | 发起用户 |
| `created_at` / `completed_at` | 生命周期时间 |

设计原则：

- 普通聊天也创建 Run，但 `display_mode = silent` 或 `compact`。
- 复杂 Skill、文件生成、写入和长任务使用 `timeline`。
- 涉及删除、覆盖、对外发送、记忆写入等动作使用 `approval_required`。

### 6.3 Run Step

`Step` 是 Run 中用户可以理解的阶段，不等于所有底层工具调用。

| 字段 | 说明 |
|---|---|
| `step_id` | 步骤 ID |
| `run_id` | 所属 Run |
| `title` | 面向用户的步骤标题 |
| `description` | 简短说明 |
| `status` | `pending`、`running`、`completed`、`failed`、`skipped` |
| `started_at` / `completed_at` | 时间 |
| `visible_to_user` | 是否展示给用户 |

示例步骤：

- 理解需求与上下文。
- 读取项目资料。
- 检索相关知识。
- 生成会前简报。
- 整理风险与下一步行动。
- 保存到项目文档。

### 6.4 Context Pack

`Context Pack` 是一次 Run 使用的上下文快照，解决“AI 本轮到底看了什么”的问题。

| 上下文类型 | 来源 | 用途 |
|---|---|---|
| 项目上下文 | 项目基础信息、阶段、任务、财务、项目记忆 | 判断当前项目状态 |
| 客户上下文 | 客户档案、历史项目、客户记忆 | 判断客户背景和关系 |
| 联系人上下文 | 联系人角色、影响力、沟通偏好 | 生成沟通策略 |
| 知识库上下文 | 团队案例、方法论、历史材料 | 提供经验和证据 |
| 文件上下文 | PDF、PPT、Word、项目文件 | 支撑事实判断 |
| 用户偏好 | 用户语言、表达风格、工作习惯 | 优化呈现方式 |

设计要求：

- Context Pack 必须保留来源 ID 和版本信息。
- 权限过滤必须发生在构建 Context Pack 之前。
- 重要回答和交付物应能回溯到 Context Pack。

### 6.5 Artifact

`Artifact` 是 AI 工作生成或修改的项目资产。

| 类型 | 示例 |
|---|---|
| `message` | 聊天回复 |
| `project_note` | 项目笔记 |
| `project_document` | 项目文档 |
| `brief` | 会前简报 |
| `report` | 分析报告 |
| `ppt` | 演示文稿 |
| `word` | Word 文档 |
| `task` | 待办或下一步行动 |

设计要求：

- Artifact 需要关联 `run_id`。
- Artifact 需要保存生成来源和上下文版本。
- 用户应能看到保存位置、版本和后续动作。

### 6.6 Memory Candidate

`Memory Candidate` 是 AI 建议沉淀的记忆，不应默认自动写入正式记忆。

| 字段 | 说明 |
|---|---|
| `candidate_id` | 候选记忆 ID |
| `scope` | `user`、`project`、`client`、`contact` |
| `content` | 记忆内容 |
| `source_run_id` | 来源 Run |
| `source_refs` | 来源文件、消息、知识片段 |
| `confidence` | 置信度 |
| `status` | `pending`、`approved`、`rejected`、`expired` |

设计原则：

- 知识可以触发候选记忆，但不能直接污染正式记忆。
- 重要事实、客户偏好、项目风险、联系人关系应进入候选记忆。
- 用户确认后再写入正式记忆。

### 6.7 Source Citation

`Source Citation` 用于支撑 AI 回答和交付物中的关键判断。

| 字段 | 说明 |
|---|---|
| `source_type` | `knowledge_doc`、`project_file`、`project_memory`、`client_memory`、`chat_message` |
| `source_id` | 来源 ID |
| `title` | 来源标题 |
| `snippet` | 摘要片段 |
| `location` | 页码、段落、消息位置等 |
| `permission_scope` | 权限范围 |

设计要求：

- 引用用于解释关键结论，不需要每句话都引用。
- 引用必须经过权限过滤。
- 交付物保存时应保留引用关系。

## 7. 核心工作流设计

### 7.1 普通项目问答

适用场景：用户在项目对话里问一个短问题。

```text
用户提问
  -> 创建轻量 Run
  -> 构建项目/客户/记忆上下文
  -> 生成流式回复
  -> 保存消息
  -> 结束 Run
```

前端表现：

- 立即显示用户消息和 AI 回复占位。
- 不展示完整任务进度。
- 如读取了资料，可展示轻量状态，例如“正在整理项目上下文”。
- Markdown、表格和列表必须正常渲染。

验收标准：

- 用户发送消息后 300ms 内出现本地消息和 AI 状态。
- 普通问答不出现冗长“任务进度”面板。
- 回复内容不因工具事件刷新而闪现或消失。

### 7.2 项目会前准备

适用场景：顾问在项目页或项目对话中发起“会前准备”。

```text
用户点击会前准备
  -> 创建 workflow Run
  -> 读取项目状态
  -> 读取客户和联系人信息
  -> 检索相关历史项目和知识库
  -> 生成会前简报
  -> 给出待确认问题和会议议程
  -> 建议保存到项目文档
  -> 生成候选记忆
```

交付物结构：

1. 会议背景。
2. 客户与项目当前状态。
3. 关键联系人和关系判断。
4. 近期进展和未决事项。
5. 风险提醒。
6. 建议议程。
7. 待确认问题。
8. 可引用资料。

验收标准：

- 生成结果可保存为项目文档。
- 至少展示关键来源引用。
- 如果缺少联系人或会议目标，AI 应先提示补充或降级生成。

### 7.3 咨询 Skill 运行

适用场景：用户从 Skill 页、项目页或客户页发起核心 Skill。

```text
选择 Skill
  -> 系统识别目标实体
  -> 检查输入资料完整性
  -> 创建 Skill Run
  -> 构建 Context Pack
  -> 执行 Skill Steps
  -> 生成交付物
  -> QA checklist
  -> 保存或等待用户确认
  -> 生成候选记忆
```

核心 Skill 必须定义：

| 维度 | 要求 |
|---|---|
| 使用场景 | 明确什么任务适合使用 |
| 输入资料 | 列出必需和可选资料 |
| 分析框架 | 明确分析路径 |
| 输出结构 | 明确交付物格式 |
| QA 清单 | 明确检查项 |
| 保存位置 | 默认保存到哪里 |
| 失败策略 | 信息不足时如何处理 |

验收标准：

- Skill 输出不只是聊天内容，必须生成一个可保存 Artifact。
- Skill Run 可回溯输入、上下文和输出。
- 核心 Skill 至少有 golden case 测试样例。

### 7.4 知识库辅助回答

适用场景：用户要求 AI 基于历史案例、方法论或上传文档回答。

```text
用户提问
  -> 识别是否需要知识库
  -> 权限过滤
  -> 检索知识片段
  -> 合并项目/客户上下文
  -> 生成回答和引用
  -> 可选生成候选记忆
```

前端表现：

- 回答正文保持自然。
- 关键结论后展示来源。
- 不把检索日志暴露给普通用户。

验收标准：

- 不能引用用户无权限访问的资料。
- 来源标题、摘要和位置可展示。
- 无检索结果时明确说明“当前知识库未找到依据”，不能假装引用。

### 7.5 记忆沉淀

适用场景：AI 在会前准备、复盘、风险分析或普通对话中发现可沉淀信息。

```text
Run 产生重要结论
  -> 生成 Memory Candidate
  -> 判断 scope
  -> 展示给用户确认
  -> 用户批准
  -> 写入正式记忆
  -> 保留来源和回滚记录
```

候选记忆示例：

- 客户偏好直接、结论先行的沟通方式。
- 某联系人是实际决策影响人。
- 项目当前最大风险是客户侧数据提供延迟。
- 某类案例可复用于同业客户。

验收标准：

- 记忆写入前必须可确认。
- 记忆必须带来源。
- 用户可以拒绝候选记忆。

## 8. 页面级功能设计

### 8.1 工作台

定位：从“首页概览”升级为“今日咨询任务入口”。

新增/强化模块：

| 模块 | 功能 |
|---|---|
| 今日建议 | 根据项目、待办、会议、风险生成今日建议动作 |
| 常用咨询任务 | 会前准备、风险分析、方案建议、项目复盘 |
| 最近 Run | 展示最近 AI 工作结果和状态 |
| 待确认事项 | 记忆候选、保存确认、高风险动作 |
| 最近交付物 | 最近生成的简报、文档、PPT、笔记 |

交互要求：

- 用户可以从工作台一键进入项目或客户任务。
- 不要求用户先选择模型或工具。
- 今日建议应简短，不做复杂解释。

### 8.2 项目页

定位：一个项目的咨询 Agent 控制台。

新增/强化模块：

| 模块 | 功能 |
|---|---|
| 下一步建议 | 根据项目状态推荐会前准备、风险分析、方案生成等 |
| 项目 AI 任务入口 | 固定展示 3-5 个高频咨询任务 |
| Run Activity | 展示本项目最近复杂 AI 工作 |
| 交付物资产 | 聚合项目文档、简报、PPT、笔记 |
| 记忆候选 | 展示待确认项目记忆 |

交互要求：

- 项目对话仍是自然入口，但项目页必须能直接发起任务。
- 复杂任务应有 timeline，普通问答保持轻量。
- AI 生成结果默认建议保存到项目资产。

### 8.3 项目对话页

定位：项目上下文内的自然语言工作界面。

关键改造：

| 功能 | 设计 |
|---|---|
| 即时反馈 | 发送后立即出现用户消息、AI 状态和回复容器 |
| Markdown 渲染 | 表格、列表、标题、代码块正常展示 |
| 进度展示 | 普通问答隐藏内部进度，长任务展示 compact timeline |
| 工具事件 | 底层工具日志进入 trace，不直接进入正文 |
| 保存动作 | 回复可保存为项目笔记或项目文档 |
| 来源引用 | 需要时展示来源卡片 |

验收标准：

- 回复不会因为 tool event 更新而闪现或消失。
- 普通问答不展示“步骤 1/4”这类内部流程。
- 复杂任务能查看进度和结果。

### 8.4 客户页

定位：客户关系、历史项目和机会判断入口。

新增/强化模块：

| 模块 | 功能 |
|---|---|
| 客户机会分析 | 基于历史项目、行业、联系人和知识库给出机会判断 |
| 客户关系风险 | 识别关键联系人缺失、关系薄弱、近期无互动等 |
| 历史经验复用 | 展示可复用案例、交付物和方法论 |
| 客户记忆候选 | 从项目复盘和对话中沉淀客户级记忆 |

交互要求：

- 客户页不只是档案页，应成为客户级 Agent 入口。
- 联系人信息应影响客户机会和会前准备。

### 8.5 联系人页

定位：客户干系人信息展示和关系洞察来源。

功能要求：

| 模块 | 功能 |
|---|---|
| 联系人列表 | 展示联系人基础信息、所属客户、角色、最近互动 |
| 联系人详情 | 展示角色、影响力、关系状态、沟通偏好、相关项目 |
| 关系洞察 | 为会前准备、客户机会分析提供上下文 |
| 记忆来源 | 联系人相关事实可进入候选记忆 |

设计边界：

- 联系人页面以展示和洞察为主，不做复杂维护系统。
- 维护动作可以弱化，避免把它做成 CRM 表单产品。

### 8.6 Skill 页

定位：从“Skill 市场”升级为“咨询交付物能力库”。

新增/强化模块：

| 模块 | 功能 |
|---|---|
| Skill 分类 | 会前、方案、风险、复盘、财务、变革、PMO、售前 |
| 交付物说明 | 每个 Skill 明确可产出什么 |
| 使用前检查 | 展示需要哪些项目/客户/文件资料 |
| 最近使用 | 展示 Skill Run 历史 |
| 质量等级 | 标记是否已完成交付物化和 golden case |

验收标准：

- 用户能根据“我要产出什么”选择 Skill。
- 核心 Skill 详情页应展示输入、输出、流程、保存位置和示例。

### 8.7 知识库页

定位：团队经验资产，而不是独立文档聊天工具。

新增/强化模块：

| 模块 | 功能 |
|---|---|
| 知识源 | 管理客户案例、方法论、模板、项目资料 |
| 处理状态 | 上传、解析、切片、索引、失败重试 |
| 引用预览 | 查看知识片段如何被 AI 引用 |
| 关联对象 | 将资料关联到客户、项目、行业或 Skill |
| 使用记录 | 哪些 Run 使用过这份知识 |

验收标准：

- 知识库可服务项目对话和 Skill。
- 重要回答能展示知识来源。
- 失败处理清晰，不让用户猜文档是否可用。

## 9. 后端能力设计

### 9.1 服务分层

| 服务 | 职责 |
|---|---|
| `RunService` | 创建、更新、完成和恢复 AI Run |
| `RunEventService` | 生成 Product Event 和 Trace Event |
| `ContextPackService` | 组织项目、客户、联系人、知识、记忆上下文 |
| `SkillRunService` | 执行 Skill、记录输入输出和版本 |
| `ArtifactService` | 保存和关联交付物 |
| `MemoryCandidateService` | 生成、确认、拒绝和写入候选记忆 |
| `CitationService` | 管理来源引用 |
| `ApprovalService` | 管理高风险动作确认 |

### 9.2 建议数据对象

| 对象 | 说明 |
|---|---|
| `ai_runs` | Run 主表 |
| `ai_run_steps` | 面向用户的步骤 |
| `ai_run_events` | 前端消费的 Product Event |
| `ai_trace_events` | 内部调试和审计事件 |
| `context_packs` | 上下文快照 |
| `context_pack_items` | 上下文条目 |
| `skill_runs` | Skill 执行记录 |
| `artifacts` | AI 生成或修改的交付物 |
| `artifact_sources` | 交付物来源 |
| `source_citations` | 引用来源 |
| `memory_candidates` | 候选记忆 |
| `approvals` | 人类确认动作 |

### 9.3 Product Event 协议

前端不直接消费底层 tool log，而是消费产品语义事件。

| 事件 | 说明 |
|---|---|
| `run.created` | Run 创建 |
| `run.started` | Run 开始 |
| `step.started` | 用户可理解步骤开始 |
| `step.completed` | 步骤完成 |
| `assistant.delta` | 流式文本增量 |
| `assistant.completed` | AI 回复完成 |
| `artifact.created` | 生成交付物 |
| `memory_candidate.created` | 生成候选记忆 |
| `approval.requested` | 请求用户确认 |
| `run.completed` | Run 完成 |
| `run.failed` | Run 失败 |

设计要求：

- `assistant.delta` 与 `step` 事件分离，避免正文被进度污染。
- 普通问答可以只推 `assistant.delta` 和 `run.completed`。
- 长任务才推 `step`、`artifact`、`approval` 等事件。

## 10. 权限、安全与可控性

### 10.1 权限原则

- 权限过滤必须早于检索、上下文拼装和模型调用。
- AI 不能因为跨项目知识检索泄露客户资料。
- Artifact 保存必须验证用户对目标项目/客户的写权限。
- 记忆写入必须验证 scope 权限。

### 10.2 高风险动作

以下动作必须走 Approval：

- 删除或覆盖项目资产。
- 写入正式项目/客户/联系人记忆。
- 修改客户档案和联系人关键字段。
- 对外发送材料或生成可下载正式文档。
- 跨客户复用敏感资料。

### 10.3 失败恢复

| 失败类型 | 处理方式 |
|---|---|
| LLM 流中断 | 保留已生成内容，允许重试 |
| 工具读取失败 | 标记失败来源，继续降级回答 |
| 保存失败 | 提示用户重试，不丢失正文 |
| 知识检索失败 | 明确说明未使用知识库 |
| 记忆写入失败 | 保留候选记忆，允许稍后确认 |

## 11. 质量与验收标准

### 11.1 功能验收

| 功能 | 验收标准 |
|---|---|
| 普通问答 | 立即反馈、流式输出、Markdown 正常、不展示复杂任务进度 |
| 长任务 | 有 Run、Step、状态、结果和失败处理 |
| Skill | 有输入检查、交付物、保存位置、QA 清单 |
| 知识库引用 | 有来源、权限过滤、无结果时不伪造 |
| 记忆候选 | 可确认、可拒绝、有来源 |
| 交付物 | 可保存、可回溯 Run、可查看来源 |

### 11.2 体验验收

- 用户不用理解模型、工具和系统提示词，也能完成咨询任务。
- 普通聊天不能被内部日志打扰。
- 复杂任务不能让用户猜系统是否还在工作。
- 所有写入动作都要明确“写到哪里了”。
- 失败时要说明发生了什么、已保留什么、还能做什么。

### 11.3 质量指标

| 指标 | 建议目标 |
|---|---|
| 普通问答首个 UI 反馈 | < 300ms |
| 普通问答首 token | < 3s，视模型和网络可调整 |
| 长任务状态可见性 | 100% 有运行状态 |
| 核心 Skill 可保存交付物比例 | 100% |
| 核心 Skill golden case 覆盖 | 每个核心 Skill 至少 3 个 |
| 记忆候选来源完整率 | 100% |
| 知识引用权限过滤 | 100% |

## 12. 分阶段升级路线

### Phase 1：Run 底座收口

目标：先解决 AI 工作状态不统一、进度展示混乱、回复闪现或消失的问题。

范围：

- 定义并实现 AI Run Contract。
- 普通问答接入轻量 Run。
- 项目对话长任务接入完整 Run。
- 前端用 Product Event 驱动 Activity Timeline。
- 工具日志和用户正文分离。

完成标准：

- 项目对话普通问答体验稳定。
- 长任务有清晰运行状态。
- 回复正文、Markdown 和表格不被工具事件破坏。

### Phase 2：核心咨询 Skill 交付物化

目标：让最重要的咨询能力成为可交付产品单元。

优先 Skill：

1. 会前准备。
2. 风险分析。
3. 方案建议。
4. 项目复盘。
5. 客户机会分析。
6. PMO / 变革管理 / FDD / 技术会计中选择 2-3 个高价值方向。

完成标准：

- 每个核心 Skill 有输入、流程、输出、QA、保存位置。
- 每个核心 Skill 产出 Artifact。
- 每个核心 Skill 有 Skill Run 记录和 golden case。

### Phase 3：知识库与记忆闭环

目标：把团队案例和客户资料变成可复用上下文资产。

范围：

- 知识库支持项目对话和 Skill 检索。
- 回答和交付物支持来源引用。
- 生成候选记忆。
- 用户确认后写入项目、客户、联系人或用户记忆。

完成标准：

- 会前准备和风险分析能使用知识库来源。
- 记忆候选有来源和确认流程。
- 知识库不是孤立页面，而是服务项目、客户和 Skill。

### Phase 4：产品形态升级

目标：让 Aria 的第一体验从“功能集合”变成“咨询任务工作台”。

范围：

- 工作台展示今日咨询任务和待确认事项。
- 项目页突出下一步 AI 工作。
- 客户页突出机会、关系风险和历史经验复用。
- Skill 页升级为交付物能力库。

完成标准：

- 用户从工作台或项目页能完成一条端到端咨询工作流。
- 生成结果可保存、可引用、可沉淀。
- 产品形态清晰表达 Agentic Workspace。

## 13. 研发拆解建议

### 13.1 P0 任务

| 任务 | 说明 |
|---|---|
| 定义 Run Contract | 明确 Run、Step、Event、Artifact、Memory Candidate |
| 项目对话接入轻量 Run | 普通问答立即反馈，隐藏复杂进度 |
| 长任务接入 timeline | Skill、文件读取、交付物生成展示进度 |
| Markdown 渲染稳定 | 表格、列表、标题不被 event 打断 |
| Artifact 保存收口 | 回复、Skill 输出、文档统一挂 Run |

### 13.2 P1 任务

| 任务 | 说明 |
|---|---|
| 核心 Skill 交付物化 | 先做 5-8 个 |
| Context Pack | 记录本轮上下文来源 |
| Source Citation | 支持知识和记忆引用 |
| Memory Candidate | 支持候选记忆确认 |
| 工作台任务入口 | 展示今日建议和待确认事项 |

### 13.3 P2 任务

| 任务 | 说明 |
|---|---|
| Partner Review | 高价值交付物复核 |
| Artifact 版本管理 | 生成物版本、对比、回滚 |
| 高级知识组织 | 行业、客户、案例、方法论标签 |
| Run 分析报表 | Skill 使用、成功率、失败率、节省时间 |

## 14. 风险与取舍

| 风险 | 说明 | 取舍 |
|---|---|---|
| 一次性重构过大 | Run、Skill、知识、记忆都相关 | 先收口 Run，再逐层接入 |
| 过度产品化底层 Agent | 用户不关心工具和模型 | 底层可追踪，前台少展示 |
| 知识污染记忆 | 检索到的信息不一定是长期事实 | 先候选、再确认、可回滚 |
| Skill 数量太多 | 平均升级会拖慢质量 | 先做少数核心 Skill |
| 前端状态复杂 | 流式、步骤、工具、保存并行 | 用 Product Event 统一驱动 |

## 15. 升级后的产品判断标准

当以下体验成立时，可以认为 Aria 初步完成 Agentic Workspace 升级：

1. 用户不需要知道底层 Agent 怎么运行，也能从项目或客户页完成咨询任务。
2. AI 不只是回答，而是能生成可保存、可复用、可审查的交付物。
3. 每次复杂 AI 工作都有 Run 记录、上下文来源、产出和状态。
4. 知识库和记忆能真正参与项目和客户工作，而不是孤立功能。
5. 核心 Skill 有稳定输入、输出和质量标准。
6. 普通问答安静、长任务透明、高风险动作可确认。

## 16. 一句话总结

这次升级的核心不是“再加几个页面”，而是把 Aria 现有的项目、客户、Skill、知识库、对话、交付物和记忆统一到一个咨询工作循环里：

```text
用户目标
  -> 上下文组织
  -> Run 执行
  -> Skill / Tool 调用
  -> 交付物生成
  -> 记忆沉淀
  -> 下一步行动
```

这个循环跑通后，AriaAI 才真正从“带 AI 的项目管理工具”升级为“专业咨询顾问的 Agentic Workspace”。
