# 项目空间重构计划

更新日期：2026-05-07

## 1. 背景

本轮重构的目标不是继续优化一个独立的“笔记”功能，而是把项目内的笔记、文档、上传材料、AI 生成物和交付文件统一收敛为一个“项目空间”。

项目空间是项目级上下文的主容器：

- 用户可以录入信息、上传资料、维护 Markdown。
- AI 可以读取空间目录、读取 Markdown、更新 Markdown，并在后续阶段管理文件归档。
- Markdown 是默认协作界面，原始文件和交付物作为空间资产保留。
- 所有项目相关文件都应在统一目录结构下被管理，而不是分散在“笔记”“文档”“生成物”等多个入口中。

## 2. 产品定义

项目详情页中的“笔记”和“文档”统一升级为“空间”。

空间内包含三类对象：

| 类型 | 说明 |
|---|---|
| Markdown 文档 | 用户和 AI 共同维护的主工作面，例如项目概览、会议纪要、需求分析、方案草稿、行动清单 |
| 源文件 | 用户上传的 PDF、DOCX、PPTX、XLSX、图片等原始材料 |
| 交付物 | AI 或用户生成的 PPTX、DOCX、XLSX、PDF、图片、Markdown 报告等成果文件 |

空间体验原则：

- 用户看到的是一个统一空间，而不是多个割裂模块。
- Markdown 优先，AI 默认读写 Markdown。
- 上传文件保留原始文件，同时自动生成同名 Markdown 派生文档。
- AI 生成物应能保存回项目空间，并进入统一目录树。
- 高风险操作，例如删除、整篇覆盖，应保留确认或版本历史。

## 3. 推荐目录结构

每个项目默认空间建议采用如下结构：

```text
project-space/{project_id}/
  00_项目总览/
    项目概览.md
    项目背景.md
  01_输入材料/
    原始文件/
      客户需求文档.docx
      客户需求文档.md
    访谈记录.md
  02_需求与方案/
    需求澄清.md
    方案思路.md
  03_会议与推进/
    会议纪要.md
    行动清单.md
  04_交付物/
    售前方案.pptx
    报价说明.docx
    交付物说明.md
  99_归档/
```

第一阶段不要求物理存储立即完全匹配该结构，但 UI、API 和 AI 工具应逐步向该模型收敛。

## 4. 第一阶段已完成

本阶段先完成前端入口统一，不做大规模数据库迁移。

- 项目导航新增“空间”入口。

## 5. 第二阶段：上传文件自动生成 Markdown

目标：任何上传到项目空间的可解析文档，都自动生成同名 Markdown 派生文档。

建议后端策略：

- 保留原始文件 `ProjectFile`。
- 使用现有 `extract_text_from_file` 提取文本。
- 自动创建一个 `.md` 类型的 `ProjectFile`。
- 建立原文件和 Markdown 派生文件之间的关联。

建议新增字段：

| 字段 | 说明 |
|---|---|
| `origin` | `uploaded` / `ai_generated` / `markdown_derivative` / `manual` |
| `source_file_id` | 派生文件来源，例如 `.md` 来源于某个 `.docx` |
| `content_status` | `pending` / `processing` / `ready` / `failed` |
| `space_path` | 后续用于统一目录路径，第一阶段可由 folder + name 推导 |

上传示例：

```text
客户需求说明.docx
客户需求说明.md
```

AI 默认读取和更新 `客户需求说明.md`，原始 `docx` 作为附件保留。

验收标准：

- 上传 DOCX/PDF/PPTX/XLSX 后自动出现同名 Markdown。
- Markdown 内容来自文件提取文本，并带有来源说明。
- 生成失败时原文件仍可用，并显示失败状态。
- 项目记忆重建能感知新生成的 Markdown。

## 6. 第三阶段：AI 空间工具

现有工具：

- `read_project_markdown_document`
- `update_project_markdown_document`

建议升级为空间级工具：

| 工具 | 能力 |
|---|---|
| `list_project_space` | 返回空间目录树、文件类型、摘要、来源关系 |
| `read_space_item` | 读取 Markdown 内容或文件摘要 |
| `write_space_markdown` | 创建或覆盖 Markdown |
| `patch_space_markdown` | 对 Markdown 做局部更新 |
| `move_space_item` | 移动文件或 Markdown 到目录 |
| `rename_space_item` | 重命名空间对象 |
| `create_space_folder` | 创建空间目录 |
| `save_artifact_to_space` | 将 AI 生成物保存进项目空间 |

安全边界：

- 删除文件必须用户确认。
- 覆盖整篇 Markdown 前应有确认或版本记录。
- AI 的写操作需要记录操作日志。
- 高价值 Markdown 建议保留最近 N 次版本快照。

## 7. 第四阶段：交付物归档

目标：AI 生成的 PPTX、DOCX、XLSX、PDF、Markdown 等成果不再只作为聊天 artifact 存在，而是自动进入项目空间。

建议行为：

- 默认保存到 `04_交付物/`。
- 同时创建一个 Markdown 说明文件，记录：
  - 交付物名称
  - 生成时间
  - 生成来源
  - 对应聊天或 Skill
  - 适用场景
  - 后续待办

验收标准：

- 聊天生成物可以一键保存到空间。
- 保存后在空间文件视图可见。
- 项目记忆和文档洞察能识别这些交付物。

## 8. 第五阶段：旧笔记迁移

现有旧字段：

- `Project.notes`
- `Project.md_notes`

迁移建议：

```text
00_项目总览/历史沉淀.md
00_项目总览/项目笔记.md
```

迁移策略：

- 先读旧字段并生成空间 Markdown 文件。
- 旧字段进入只读兼容期。
- 前端不再直接展示旧字段作为主编辑面。
- 最终在一次正式迁移后废弃旧字段写入。

验收标准：

- 旧项目的笔记内容不会丢失。
- 用户打开空间后能看到历史笔记。
- 新内容只写入空间 Markdown。

## 9. 技术风险

| 风险 | 应对 |
|---|---|
| Notes / Documents / Artifacts 三套历史能力耦合较深 | 分阶段收敛，先统一入口，再统一数据模型 |
| 上传文件转 Markdown 可能耗时较长 | 使用后台任务和状态字段 |
| 大文件解析失败影响体验 | 原文件先落库，派生 Markdown 可失败重试 |
| AI 写入 Markdown 可能覆盖用户内容 | 默认 patch / append，整篇 replace 需要确认或版本 |
| 旧链接和旧数据兼容 | 保留 `/notes`、`/documents` 兼容路由和旧字段迁移期 |

## 10. 当前结论

第一阶段已经完成“空间”入口统一和左侧统一目录树。下一步应优先做“上传文件自动生成 Markdown”和“AI 目录维护工具”。这一步完成后，项目空间会从 UI 概念变成真正的数据和 AI 工作面，为后续 AI 统一管理文档、交付物归档、旧笔记迁移打基础。
