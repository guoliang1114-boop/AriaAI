# 对话系统设计规范

> 创建日期：2026-05-20
> 版本：v1.2（新增 ActionPolicy 双轴权限模型）
> 关联：[09-项目对话问题根因分析.md](./09-项目对话问题根因分析.md)
>
> **定位**：这份文档是对话系统的**单一信源（Single Source of Truth）**。任何对话流的改动，先改这份 spec，再改代码。
>
> **与已有架构的兼容承诺**：
> 1. **不推倒 P0-P4 Phase 架构**（[services/chat/phases/](../AriaAI/backend/app/services/chat/phases/)）。Mode 显式化是**叠加**在 P0-P4 之上，不是替代。
> 2. **不重复造 Router**。已有的 [`task_orchestrator.route_project_task_request`](../AriaAI/backend/app/services/task_orchestrator.py) 是 LLM Router + Rule-First 的完整实现，本规范要做的是把它**抽象成通用 IntentRouter**，让 chat-mode 路由和 task-type 路由共用一个服务，不是各起炉灶。
> 3. **不绕过 Capability Protocol**。`ConsultingCapability` 和 task_orchestrator 的 Capability/Step 体系处理结构化交付物（PPT/Word/Excel/PDF/Markdown），Mode 显式化只覆盖**未升级为 Task 的 chat 主路径**。
> 4. **流式架构下保留轻量修复**。SSE 流式生成期间无法做"schema 拒绝并重试"，因此 P2 阶段的轻量参数兜底必须保留（只删关键词推断，不删默认值生成）。
> 5. **Policy 与 Router 双层**。**Policy（硬规则）和 IntentRouter（软分类）并存**，不是互相替代：身份问答、危险操作、明确写入意图这些用 Policy 给确定性决策；模糊的 mode 归类才交给 LLM Router。

## 核心架构 TL;DR

```
User Message
   ↓
Policy Guards          ← 身份拦截 / destructive 词识别 / 明确写入意图
   ↓
IntentRouter           ← Rule-First short-circuit + LLM Router + fallback
   ↓
(ChatMode, ActionPolicy, task_route?)
   ↓
Prompt / Context / Tool Scope    ← Mode 决定剧本，Policy 决定权限
   ↓
Direct Answer  或  Task Orchestration（升级到 task_orchestrator）
   ↓
UI Progress Contract
   ↓
ChatTrace + Golden Set 防回归
```

**关键区分**：
- **ChatMode**：对话的"剧本"。决定 prompt 模板、context 范围、historic window、可用模型。**6 种枚举**。
- **ActionPolicy**：对话的"权限"。决定本次消息能调哪类工具、是否需要确认。**6 种枚举**。
- **Mode × Policy** 共同决定本次请求的完整契约。同一个 Mode 下，不同 Policy 给出完全不同的工具权限。

## 0. 设计原则

| 原则 | 落到代码上是什么 |
|---|---|
| **Mode 显式** | 每次对话开始定 1 个 `ChatMode`，整条链路只读不改 |
| **Policy 显式** | 每次对话开始定 1 个 `ActionPolicy`，决定工具权限和确认级别 |
| **Policy + LLM 双层** | Policy 用硬规则给确定性决策（身份/危险/明确写入），IntentRouter 用 LLM 给概率分类。不互相替代 |
| **Prompts as Data** | 所有 prompt 模板存 `prompts/` 文件，不再写在 `.py` 字符串里 |
| **Tool 用 description 表达意图** | 工具调用规则写在 tool description，不写在 system prompt 里堆 MUST/CRITICAL |
| **可观测** | 每次请求生成 `ChatTrace`，可查询、可重放；Policy 和 Repair 决策都进 Trace |
| **可回归** | 改 prompt / 路由前先跑 Golden Set，回归则 block 合并 |

## 1. 核心架构：Intent → Mode → Action

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│   Intent     │───▶│    Mode      │───▶│   Action     │
│              │    │              │    │              │
│ LLM Router   │    │ 不可变枚举   │    │ 装配 prompt  │
│ + fallback   │    │ 决定一切下游 │    │ 选 model     │
│              │    │              │    │ 选 tools     │
└──────────────┘    └──────────────┘    └──────────────┘
   单次决策            状态机              纯函数
```

**关键不变量**：
- Intent 决策有且仅有一次，结果是 `ChatMode`
- Mode 决定 prompt / model / tools / history window，下游不再做"局部判定"
- 任何"根据 X 改写 Y"的逻辑，要么挪到 Intent 决策层，要么挪到 Mode 配置表

## 2. ChatMode 枚举

6 种模式，覆盖所有 chat 主路径 + 与 Capability Protocol 的交界。

```python
class ChatMode(str, Enum):
    STANDALONE_QA = "standalone_qa"
    PROJECT_DEEP_DIVE = "project_deep_dive"
    CROSS_PROJECT_PORTFOLIO = "cross_project_portfolio"
    WORKSPACE_INVENTORY = "workspace_inventory"
    SKILL_EXECUTION = "skill_execution"
    TASK_ORCHESTRATION = "task_orchestration"   # 已升级为 task_orchestrator 处理
```

**`TASK_ORCHESTRATION` 的特殊性**：这个 Mode 不直接装配 prompt，而是**把控制权交给 [task_orchestrator](../AriaAI/backend/app/services/task_orchestrator.py)**：当 `route_project_task_request` 返回 `response_mode ∈ {artifact, orchestrated, edit}` 且置信度足够时，进入这个 Mode；P0 阶段会 early-return，由 task 自己流式输出 step 进度。Mode 显式化层只负责"把消息路由到这个 Mode"，不接管 task 内部流程。

### 2.1 Mode 完整规格表

| 维度 | STANDALONE_QA | PROJECT_DEEP_DIVE | CROSS_PROJECT_PORTFOLIO | WORKSPACE_INVENTORY | SKILL_EXECUTION | TASK_ORCHESTRATION |
|---|---|---|---|---|---|---|
| **何时触发** | 无 project_id，无 skill 显式调用，无 portfolio/inventory 信号 | 有 project_id，单项目问答 | 用户要看"某客户的所有项目"汇总 | 用户要看"工作台全部项目"清单 | 用户在 UI 显式 arm Skill，或消息里 `@skill` | `route_project_task_request` 返回 `response_mode ∈ {artifact, orchestrated, edit}` 且 task_type 命中 |
| **Prompt 模板** | `prompts/modes/standalone_qa.md` | `prompts/modes/project_deep_dive.md` | `prompts/modes/cross_project_portfolio.md` | `prompts/modes/workspace_inventory.md` | `prompts/modes/skill_execution.md` | 不由 chat 装配，由 task step 自管 |
| **Default model** | `moonshot-v1-8k`（短消息）/ `kimi-k2.6`（长） | 用户默认 model | `deepseek-v4-flash`（如有）/ 用户默认 | `deepseek-v4-flash`（如有）/ 用户默认 | Skill 指定 model 或用户默认 | task step 各自指定 |
| **max_tokens** | 1536 / 2048 | 8192 | 4096 | 6144 | Skill 指定 / 8192 | 各 step 自定 |
| **历史窗口** | 24 条 | 24 条 | **保留最近 6 条**（不再清零） | **保留最近 6 条**（不再清零） | 24 条 | N/A |
| **Project Context** | 不注入 | 完整注入 | Portfolio 聚合块 | Inventory 聚合块 | 当前 project（若有） | step `collect_project_context` 自行收集 |
| **工具池**（受 ActionPolicy 二次约束） | ∅ | `read_*` + `update_*` + `write_*`（**实际权限由 Policy 决定**，默认 read-only） | `read_project_markdown_document` | ∅ | Skill 定义的 tool 集合 | step 自带 |
| **特殊行为** | 短消息走 fast path | 默认 read-only，写工具需 Policy 升级 | 强制要求"完整 inventory 表 + 风险摘要"格式 | 同左 + 全工作台范围 | tool 调用按 Skill spec 严格执行 | P0 early-return；流式输出 step 进度 |
| **对应 phase** | P1+P3 | P1+P2+P3+P4 | P1+P3 | P1+P3 | P1+P2+P3+P4 | P0 |

**关键变化**：原"可用 tools"列改为"工具池"。Mode 定义的是**理论上这个模式能用哪些工具**，实际本次消息能不能调 = **工具池 ∩ ActionPolicy 允许**（见 §2.5）。这避免了"PROJECT_DEEP_DIVE 默认开放写工具 → 用户问风险结果生成 MD"的漏洞。

## 2.5 ActionPolicy

ActionPolicy 决定本次消息的**工具调用权限和确认级别**。和 ChatMode 是双轴关系：

```
ChatMode      = 这是什么对话场景？（剧本）
ActionPolicy  = 本次消息允许做什么？（权限）
```

### 2.5.1 枚举定义

```python
class ActionPolicy(str, Enum):
    DIRECT_ANSWER = "direct_answer"            # 仅直接回答，不调任何工具
    READ_ONLY_TOOL = "read_only_tool"          # 允许调读类工具（list/read 文件、查询数据）
    WRITE_ARTIFACT = "write_artifact"          # 允许创建新交付物（新文件，append）
    MODIFY_EXISTING_FILE = "modify_existing_file"  # 允许修改/覆盖已有文件，**需要二次确认**
    DURABLE_TASK = "durable_task"              # 升级到 task_orchestrator 处理
    DESTRUCTIVE_ACTION = "destructive_action"  # 删除/破坏性操作，**必须用户确认**
```

### 2.5.2 Policy 决策来源

Policy 由 **Policy Guards（硬规则）** 优先决定，**IntentRouter（LLM）** 作为 fallback：

| 触发信号 | 输出 Policy | 来源 |
|---|---|---|
| 消息匹配身份问法 keyword list | 拦截，不进 Policy 流（前置层） | Identity Guard |
| 消息含明确 destructive 词（"删除"/"清空"/"丢弃"/"delete"/"drop"） | `DESTRUCTIVE_ACTION` | Policy Guard 硬规则 |
| 消息含明确写入词 + 目标文件已存在 | `MODIFY_EXISTING_FILE` | Policy Guard 硬规则 |
| 消息含明确写入词 + 没有现存目标 | `WRITE_ARTIFACT` | Policy Guard 硬规则 |
| 消息触发 `route_project_task_request` 命中 task_type 且高置信 | `DURABLE_TASK` | task_orchestrator |
| 默认 / 模糊场景 | LLM Router 决定，最低降到 `READ_ONLY_TOOL`（项目内）或 `DIRECT_ANSWER`（无项目） | IntentRouter |

**核心原则：默认从严**。歧义场景宁可降到 `DIRECT_ANSWER` / `READ_ONLY_TOOL`，不主动升级到 write。这是审阅"用户问风险结果生成 MD"漏洞的核心修法。

### 2.5.3 Policy → 工具权限映射

| Policy | 可调工具类型 | 确认级别 |
|---|---|---|
| `DIRECT_ANSWER` | ∅（任何 tool_use 被丢弃 + Trace 记录） | N/A |
| `READ_ONLY_TOOL` | 工具池里所有 read-only tool（`read_*`、`list_*`） | 无 |
| `WRITE_ARTIFACT` | 工具池里 read-only + create/append 操作 | 无（用户已明确意图） |
| `MODIFY_EXISTING_FILE` | 工具池里所有 + replace 操作 | **HITAS Action Preview 确认** |
| `DURABLE_TASK` | 控制权移交 task_orchestrator，由 task step 决定 | 任务级确认（task_orchestrator 已有） |
| `DESTRUCTIVE_ACTION` | delete 类工具 | **HITAS Action Preview 确认** |

每个 tool 在注册表里声明自己需要的最低 Policy（见 §4.2），调用前由 `policy_guard.check(tool_name, current_policy)` 校验。

### 2.5.4 Mode × Policy 笛卡尔积（仅列有意义组合）

| Mode | DIRECT | READ | WRITE | MODIFY | DURABLE | DESTROY |
|---|---|---|---|---|---|---|
| STANDALONE_QA | ✅ 默认 | ❌ | ❌ | ❌ | ❌ | ❌ |
| PROJECT_DEEP_DIVE | ✅ | ✅ **默认** | ✅ 用户明确 | ✅ 需确认 | → 转 TASK_ORCH | ✅ 需确认 |
| CROSS_PROJECT_PORTFOLIO | ✅ 默认 | ✅（只读） | ❌ | ❌ | ❌ | ❌ |
| WORKSPACE_INVENTORY | ✅ 默认 | ❌ | ❌ | ❌ | ❌ | ❌ |
| SKILL_EXECUTION | ✅ | ✅ | ✅ Skill 定义 | ✅ Skill 定义 | → 转 TASK_ORCH | ✅ 需确认 |
| TASK_ORCHESTRATION | N/A | N/A | N/A | N/A | ✅ 默认 | N/A |

**注意 PROJECT_DEEP_DIVE 的默认值是 READ_ONLY_TOOL，不是 WRITE**。要写必须用户明确说出来。这就解决了"问风险结果生成文件"的漏洞。

### 2.5.5 二次确认四分级（来自审阅反馈）

| 情况 | 行为 |
|---|---|
| **读工具** | 不弹确认，直接执行 |
| **创建新交付物**（用户明确要求）| 不弹确认，但回复里清楚说明"已保存为 X" |
| **修改/覆盖/删除现有文件** | **HITAS Action Preview 确认**：服务端持久化冻结工具名和参数，用户确认后确定性执行 |
| **模型意图与用户原话不一致**（例如：用户问"如何", 模型想 write） | Trace 记录 + 降级为 `DIRECT_ANSWER`，不执行 |

第四种情况靠 Policy Guard 的"declared_intent vs router_decision"对比检测，差异过大就降级。

HITAS 设计细节见 [16-Human-in-the-Loop Tool Approval 设计.md](./16-Human-in-the-Loop%20Tool%20Approval%20设计.md)。核心约束：确认动作必须写入 `PendingToolAction`，confirm/reject 端点必须认证并校验项目成员，确认后直接执行已保存的 `tool_name + tool_input_json`，不得重新请求 LLM 生成工具调用。

## 3. Intent → Mode + Policy 决策

### 3.1 统一 Router 边界，不再双轨

**当前判断：task_orchestrator 仍负责可恢复任务的创建、执行和兼容 API；IntentRouter 是 chat 主链路唯一入口**。它吸收 task 路由的确定性部分，并输出统一的 `IntentDecision(chat_mode, action_policy, task_route)`。这比让 P0 再单独调用 task router 更稳定：
- API 入口先异步预路由，再装配 prompt / context / model / tools。
- P0 durable task 只消费 prepare 阶段已经得到的 `task_route`；如果是历史同步调用，才会兜底补跑一次。
- task_orchestrator 继续执行 task step、Capability Protocol、artifact persistence，不再决定 chat-mode。

这个 Router 回答三个问题：

```
IntentRouter → IntentDecision(chat_mode, action_policy, task_route?, confidence, trace)
```

### 3.2 通用 IntentRouter 设计

```python
# backend/app/services/intent_router.py
@dataclass(frozen=True)
class IntentDecision:
    chat_mode: ChatMode
    action_policy: ActionPolicy
    task_route: TaskRoute | None      # 如果 mode == TASK_ORCHESTRATION，这里非空
    confidence: float
    reason: str
    method: Literal["policy_guard", "rule_short_circuit", "llm_router", "rule_fallback"]
```

当前落地约束：

- `prepare_chat_runtime_async` 是 API 主入口：它先调用 `classify_chat_intent_async`，再根据决策装配 prompt/context/model/tool scope。
- `prepare_chat_runtime` 是同步 Rule-First 兼容入口，只用于老测试、脚本或不允许 async 的内部调用。
- `classify_chat_intent_async` 是完整统一 Router，包含 Rule-First、确定性 task route、结构化 LLM Router、Policy clamp。
- P0 durable task 优先复用 `ChatRuntime.intent_task_route`，不能在正常 API 流程里重复路由。
- task_orchestrator 暴露 `rule_based_project_task_route` 作为确定性 task route，IntentRouter 不依赖 `_rule_based_*` 私有函数；task_orchestrator 仍负责执行任务和兼容旧 `route_project_task_request` API。
- LLM Router 只能澄清低置信 mode；不能把 `DIRECT_ANSWER` / `READ_ONLY_TOOL` 静默升级成 `WRITE_ARTIFACT`、`MODIFY_EXISTING_FILE`、`DURABLE_TASK` 或 `DESTRUCTIVE_ACTION`。
- 每次 IntentDecision 必须附带 `trace`：包含最终 mode/policy、规则基线、LLM payload、override/clamp 方法。`ChatTrace.metadata.intent_trace` 是排查线上路由问题的第一现场。

```python
INTENT_ROUTER_PROMPT = """You classify a user message for AriaAI chat.
Return JSON with two decisions:
  1. chat_mode: standalone_qa | project_deep_dive | cross_project_portfolio
                | workspace_inventory | skill_execution | task_orchestration
  2. task_route: if chat_mode == task_orchestration, include the task_type
                 (generate_client_ppt | generate_project_excel | ...) and plan_steps
  3. confidence: 0-1
  4. reason: short string

Decision rules:
- If user asks to CREATE/SAVE/EXPORT a deliverable (PPT/Word/Excel/PDF/Markdown), choose task_orchestration
- If user is in a project and asks about its content, choose project_deep_dive
- If user asks across multiple projects of one client, choose cross_project_portfolio
- ...
"""

async def classify_intent(
    req: SendMessageRequest,
    *,
    llm_complete: Callable | None = None,
    model: str = "",
) -> IntentDecision:
    """五层管道（来自审阅反馈）：
       Policy Guards → Rule-First short-circuit → LLM Router → Schema → fallback
    """
    # 1. Policy Guards — 硬规则给确定性决策
    if req.force_skill:
        return IntentDecision(
            chat_mode=ChatMode.SKILL_EXECUTION,
            action_policy=_skill_default_policy(req.skill_id),
            task_route=None,
            confidence=1.0,
            reason="forced_by_user",
            method="policy_guard",
        )
    policy_guard_decision = _policy_guards(req)   # 身份/destructive/明确写入识别
    if policy_guard_decision is not None:
        return policy_guard_decision
    
    # 2. Rule-First short circuit — 高置信度规则路径直接返回
    rule_decision = _rule_based_intent(req)
    if rule_decision.confidence >= 0.9:
        return rule_decision
    
    # 3. LLM Router
    if llm_complete is None:
        return rule_decision  # no LLM available → use rule fallback
    try:
        llm_decision = await _llm_router(req, llm_complete, model)
    except Exception:
        return rule_decision
    
    # 4. Schema 校验 + 分歧检测
    if not _schema_valid(llm_decision):
        return rule_decision
    if _should_rule_override_llm(rule_decision, llm_decision):
        _log_disagreement(req.content, rule_decision, llm_decision)
        return rule_decision
    
    # 5. 默认从严：模糊场景降到 READ_ONLY_TOOL 或 DIRECT_ANSWER
    return _conservative_policy_clamp(llm_decision)
```

**五层管道的优势**：
- **Policy Guards** 让身份问答、删除确认、明确写入意图获得确定性决策，不被 LLM 概率性误判
- **Rule-First short-circuit** 让高置信度场景省 LLM 调用
- **LLM Router** 处理模糊场景
- **Schema 校验 + 分歧检测** 防止 LLM 输出污染
- **Conservative clamp** 兜底从严，宁可降到 read-only 也不主动升级到 write

**实现步骤**：
1. 把 `task_orchestrator.py` 里的 LLM Router 内核（`route_project_task_request` 函数体、`_rule_based_router_decision`、`_should_rule_route_override_llm`、`_log_router_disagreement`）整体迁移到新的 `services/intent_router.py`。
2. 新增 `services/policy_guards.py`，覆盖身份拦截、destructive 词识别、明确写入意图识别（这些都是确定性硬规则）。
3. `task_orchestrator` 继续暴露同名函数，但内部调用 `intent_router.classify_intent`，从 `IntentDecision` 取出 `task_route` 返回（向后兼容）。
4. `prepare_chat_runtime` 改为调 `intent_router.classify_intent`，从中拿 `chat_mode` + `action_policy`。
5. P0 阶段仍然只关心 `task_route`，行为不变。
6. P1/P2 阶段新增 `policy_guard.check(tool_name, action_policy)` 校验，工具池 ∩ Policy 才允许执行。

### 3.3 Fallback 策略

- LLM Router 超时/失败/低置信度（<0.55）→ 用 `_rule_based_intent` 的结果
- 高置信度规则路径（≥0.9）直接 short-circuit，省 LLM 调用
- 所有分歧都记录到 `ChatTrace`，方便事后调优 prompt

降级日志必须能在 `ChatTrace` 里看到：

```json
"intent_classification": {
  "decided_mode": "PROJECT_DEEP_DIVE",
  "method": "keyword_fallback",
  "confidence": 0.4,
  "reason": "llm_router_timeout"
}
```

### 3.4 性能要求

- Router 调用 ≤ 500ms（P95）
- Router 用便宜模型（Kimi-k2-8k 或 Deepseek-flash），与 task_orchestrator 共用同一个 `llm_complete`
- 单次 Router 输出 ≤ 200 token
- Router 输出强 JSON schema，解析失败立即 fallback
- Rule-First short-circuit 命中率目标：**≥30%**（省 LLM 调用成本）

## 4. Tool 注册表

### 4.1 设计原则

> **如果模型在错误调用工具，问题在 tool description，不是在 system prompt 里加 MUST。**
> —— Anthropic Function Calling Best Practices

所有"什么时候用 / 什么时候不用"的规则**只在 tool description 里写一次**。system prompt 不再夹带工具教学。

### 4.2 工具规范化模板

```yaml
# backend/app/prompts/tools/update_project_markdown_document.yaml
name: update_project_markdown_document
purpose: |
  Create or rewrite a Markdown file inside the current project space.
when_to_use: |
  User explicitly asks to save, write, create, modify, replace, or rewrite a project document.
  Example triggers: "保存为新文档", "把这个改成 X 后保存", "新建一份 README"
when_not_to_use: |
  Advisory/analysis-only requests like "识别风险", "分析现状", "总结一下".
  Read-only questions about project files.
  Any case where the user has not explicitly asked to persist content.
required_params:
  - mode: one of [create, replace, append]
  - file_name: string (if mode=create) or file_id/file_name (if mode=replace/append)
  - content: full Markdown content (for replace, send the complete new file, not a diff)
ui_effect: |
  After this returns, the user sees the saved file in the project file panel.
modes_available: [PROJECT_DEEP_DIVE]
required_policy:
  # 校验本次请求的 ActionPolicy 是否允许调用此工具
  create: WRITE_ARTIFACT          # mode=create 要求至少 WRITE_ARTIFACT
  append: WRITE_ARTIFACT
  replace: MODIFY_EXISTING_FILE   # mode=replace 要求 MODIFY_EXISTING_FILE（含确认）
confirmation_rule:
  create: none                    # 不弹确认
  append: none
  replace: client_dialog          # 客户端弹窗确认（显示 diff）
```

**调用前校验**（伪代码）：

```python
def execute_tool(tool_name: str, tool_input: dict, action_policy: ActionPolicy):
    spec = load_tool_definition(tool_name)
    required = spec["required_policy"].get(tool_input.get("mode"), spec["required_policy"]["default"])
    if not policy_allows(action_policy, required):
        # 不执行，记录到 Trace
        trace.record_tool_blocked(tool_name, reason=f"need={required} got={action_policy}")
        return ToolBlockedResult(...)
    if spec["confirmation_rule"][tool_input.get("mode")] == "client_dialog":
        return ToolPendingConfirmationResult(...)
    return registry.execute(tool_name, tool_input)
```

代码里通过 loader 自动转成 Anthropic tool schema：

```python
def load_tool_definition(name: str) -> dict:
    spec = yaml.safe_load(open(f"prompts/tools/{name}.yaml"))
    return {
        "name": spec["name"],
        "description": (
            f"{spec['purpose']}\n\n"
            f"WHEN TO USE: {spec['when_to_use']}\n\n"
            f"WHEN NOT TO USE: {spec['when_not_to_use']}\n\n"
            f"After execution: {spec['ui_effect']}"
        ),
        "input_schema": spec["input_schema"],
    }
```

### 4.3 当前工具清单（需要规范化）

| Tool | 状态 | 优先级 |
|---|---|---|
| `update_project_markdown_document` | 现有规则在 PROJECT_MARKDOWN_TOOL_PROMPT 里散落 | P0 迁移 |
| `read_project_markdown_document` | 同上 | P0 迁移 |
| `write_project_office_document` | 同上 | P0 迁移 |
| `generate_ppt` / `generate_ppt_from_skill` | Skill 内使用，有 `_route_ppt_tool_for_skill` 兜底 | P1 迁移 |
| `generate_docx` / `generate_xlsx` / `generate_pdf` | Skill 内使用 | P1 迁移 |
| `save_json` / `save_text` | 通用持久化工具 | P2 迁移 |

### 4.4 工具兜底层职责（重构，不是删除）

> 审阅反馈：流式 + 多 provider 环境下完全删除 repair 会引入新故障。目标是**重构 repair 让它中性 + 可观测**，而不是"消灭 repair"。

**保留并增强**：
- 工具参数 **schema 校验**（在 registry.execute 入口）
- **轻量参数兜底**：合理默认值生成。例如 `file_name` 由 `title` 推导、`mode` 在有 `file_id` 时默认 `replace`。这是 SSE 流式生成的现实约束 —— 模型流到一半才发现参数缺失，无法"中断重试"
- **工具执行错误捕获** + 友好提示
- **所有 repair 都进 ChatTrace**：哪个 tool、哪个字段、补了什么默认值，方便事后分析模型给参数的能力

**改造（不是删除）**：
- `_should_accept_tool_use` 关键词二次过滤 → **改为 `policy_guard.check`**（基于 ActionPolicy 而非关键词）
- `_user_requested_project_markdown_write` 整个函数 → **迁移到 `policy_guards._detect_write_intent`**，作为 Policy Guard 的一部分；原本散落在 chat_tools 的关键词列表统一进 Policy 层
- `extract_tool_use_json_blocks` 文本兜底解析 → 优先使用 Anthropic 原生 tool_use API；当 provider 不支持时**降级保留**，并在 Trace 标记 `tool_use_via_text=true`
- 修复函数里的**关键词推断逻辑**（如 `_default_xlsx_sheets_for_request` 根据"访谈"关键词推断默认表头）→ **删除关键词推断**，改为**中性默认值**（空表头 + 空数据）；如果需要场景化的智能默认值，应该让模型自己出参数

**关键区分**：

| 兜底行为 | 这次怎么改 | 备注 |
|---|---|---|
| 默认值生成（filename from title） | ✅ 保留并增强（进 Trace） | 流式架构现实约束 |
| 关键词推断（"访谈" → 访谈表头） | ❌ 删除推断，改为中性默认值 | 跟"Tool 用 description 表达"冲突 |
| 关键词二次过滤（user 没说写文件就丢工具） | ⚠️ **迁移到 Policy Guard**，不是简单删除 | 关键词逻辑收敛到统一层，不是消失 |
| Schema 拒绝 + 模型重试 | 不引入 | 流式无法纯粹实现 |
| 文本提取 tool_use | ⚠️ 降级保留 | 仅当 provider 不支持原生 tool_use API |

**审阅反馈精神**：散落在各处的关键词补丁要被消灭，但消灭它们不是因为"关键词不好"，而是因为"散落"。统一到 Policy Guard 层之后，关键词作为硬规则继续存在，但**有且只有一份**，且决策都有 Trace。

### 5.1 现状（7 层叠加）


### 5.2 目标态（4 层）

```

[2] mode_directives           (mode 专属行为约束，10-20 行)
[3] context_block             (mode 决定的结构化上下文)
[4] rag_block                 (按需，独立分区)
```

**消失的层：**
- `identity_rules` → **挪到 server-side 拦截器**：用 keyword list（不是单一 regex）匹配身份问法的常见变体，命中直接返回固定模板，不进 LLM。覆盖至少：
  ```python
  IDENTITY_KEYWORDS = [
      "你是谁", "你叫什么", "你是什么", "你是哪个", "你是什么模型",
      "介绍一下你自己", "介绍下你自己", "自我介绍",
      "你能做什么", "你的功能", "你有什么能力",
      "who are you", "what are you", "what model", "introduce yourself",
  ]
  ```
  非命中才走 LLM。这避免了单一 regex 的覆盖盲区。
- `skill prompt` → **合并到 mode_directives**：SKILL_EXECUTION 模式的 mode template 包含 skill 内容
- `skill briefing patch` → **删除**：信息已经在 context_block 里
- `PROJECT_MARKDOWN_TOOL_PROMPT` → **整体删除**：内容拆到各 tool 的 description

### 5.3 装配函数

```python
def build_system_prompt(mode: ChatMode, context: ChatContext) -> str:

    return template.render(
        context_block=render_context(mode, context),
        rag_block=context.rag_context if context.rag_context else None,
    )
```

**装配只有一处实现**（统一在 `chat/prompt_assembler.py`），不再有 `claude.py` 和 `openai_compat.py` 双份。

## 7. 可观测性：ChatTrace

### 7.1 数据结构

```python
class ChatTrace(BaseModel):
    trace_id: str                      # 例：chat-2026-05-20-abc123
    conversation_id: int
    request_received_at: datetime
    
    intent_classification: IntentDecision
    mode: ChatMode
    
    prompt_layers: list[PromptLayer]   # 每层名字 + token 数 + 版本
    history_window_size: int
    history_was_truncated: bool
    
    tool_decisions: list[ToolDecision]
    artifacts_produced: list[ArtifactRef]
    
    stage_timings_ms: dict[str, int]   # 已有 prepare_metrics 的扩展
    model_used: str
    total_input_tokens: int
    total_output_tokens: int
    
    fallback_events: list[str]          # router_timeout / tool_repair_applied / etc.

class ToolDecision(BaseModel):
    tool_name: str
    was_called: bool
    decided_at_stage: Literal["p1", "p3"]
    skipped_reason: str | None          # if not called, why
    repaired_params: dict | None        # if params were auto-corrected
    artifact_id: str | None
```

### 7.2 持久化

- Trace 存到 PostgreSQL 表 `chat_traces`，保留 30 天
- 关键字段建索引（mode、conversation_id、created_at）
- 提供端点 `GET /chat/{conversation_id}/trace?message_id=...`

### 7.3 前端集成

- 开发模式下，每条 AI 消息底部加一个 "🔍 Trace" 按钮
- 点击展开 Trace 详情（mode、prompt 层、tool 决策、timing）
- 生产环境对管理员可见

### 7.4 触发告警

每周自动统计：
- `fallback_events` 比例（>5% 说明 router 不靠谱）
- `tool_decisions.skipped_reason="user_did_not_request"` 比例（>10% 说明 tool description 还不够清晰）
- `history_was_truncated=True` 比例（看用户长对话占比）

**产出**：长 prompt 噪声消除，模型 attention 回到用户消息。

### 总周期

5.5-6.5 周（M2: 1w + M1: 1w + M3a: 1.5w + M3b: 2-3w + M4: 1w）。比原 4 周方案稍长，但每个里程碑都可独立产出可见价值，且不会有"集中合并日地狱"。M3a 比原 1 周多 0.5 周是因为新增了 ActionPolicy + Policy Guards 的实现。

---

## 10. 在这份规范之后

### 10.1 维护约定

- **任何对话流的改动**（prompt、router、tool、context）**先改 spec，再改代码**
- spec 改动需 PR review，至少一人确认
- spec 改动伴随 Golden Set 新增/调整
- 不再在代码里写"未来某天可能要..."的 TODO，要做就改 spec

### 10.2 不在本规范覆盖的

- 模型 provider 切换策略（除 mode 维度外）
- RAG 检索质量
- 知识库索引
- 干系人/客户记忆生成

这些有各自的 spec（02、03、04），交集只在"作为 ChatContext 的输入"。

### 10.3 验证

回到 [02-技术债与行动清单.md 第 4 节](./02-技术债与行动清单.md#4-待办事项--产品验证下周开始) 的产品验证方案：M1+M2 落地后，让种子顾问连续用 1 周，重点观察：

- 是否仍然遇到"AI 没理解我"
- 是否仍然遇到"AI 做了我没让它做的事"
- 是否仍然遇到"AI 突然失忆"

三个症状的发生频率应该显著下降。

---

## 11. 一句话总结

> Chat 系统不应该靠散落关键词决定剧本，也不应该完全信任 LLM Router。最佳实践是：先由统一 IntentRouter 做结构化决策（Policy Guards → Rule-First → LLM Router → Schema → Trace → fallback 五层管道），输出 `ChatMode + ActionPolicy + task_route`；然后按这个决策装配 prompt、上下文、工具权限和 UI 展示契约，并用 ChatTrace 与 Golden Set 防止回归。

## 附录：版本演进

### v1.1 → v1.2 改动来源

本版本相对 v1.1 的核心增加是 **ActionPolicy 双轴权限模型**，来自外部审阅反馈：

1. **新增 ActionPolicy 枚举**（6 种）+ Mode × Policy 双轴矩阵，精确解决"用户问风险结果生成 MD 文件"的核心漏洞
2. **五层管道**：Policy Guards → Rule-First → LLM Router → Schema → Trace → fallback。Policy 用硬规则给确定性决策，LLM 处理模糊场景，两者并存
3. **PROJECT_DEEP_DIVE 默认 read-only**：原 v1.1 在 Mode 表里给 PROJECT_DEEP_DIVE 直接列了 update/write 工具，存在权限漏洞；v1.2 改为 Mode 给"工具池"、Policy 给"实际权限"
4. **二次确认四分级**：读=不确认 / 创建=不确认 / 修改-覆盖-删除=客户端弹窗 / 意图不一致=降级 DIRECT_ANSWER
5. **关键词不是"全删"而是"统一到 Policy 层"**：散落补丁消灭，但身份/危险/明确意图这些硬规则反而需要确定性，迁移到 `services/policy_guards.py`
6. **`_repair_*` 不是"删除"而是"重构 + 进 Trace"**：流式 + 多 provider 现实下完全删除会引入新故障；目标是去除关键词推断、保留中性默认值、所有修复进 Trace 可观测
7. **M3a 扩到 1.5 周**：纳入 ActionPolicy + Policy Guards 实现
