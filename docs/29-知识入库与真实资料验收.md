# 知识入库与真实资料验收

日期：2026-09-22。前置运行版本 `52488f9`，前置文档版本 `bb057b4`。本轮 `33df8e3` 已成功发布，原生链路与实际文件副本验收通过；[#69](https://github.com/guoliang1114-boop/AriaAI/issues/69) 所列入库、检索、权限和引用稳定性工作已验收，Issue 已关闭。生产语义启用与历史索引重建仍是独立操作。

## 本轮修复

知识入库此前复用文件预览解析器：PDF 仅前 15 页、Excel 仅前 200 行；Word 只读段落，PPT 只读顶层文本框。大于 200,000 字符的内容还可能被截断后标记为已索引。这些限制会造成检索缺证据。

- Word 按正文顺序提取段落和表格，包含嵌套表格，合并单元格去重。
- PPT 提取文本框、递归组合图形中的文字、表格和演讲备注，保留幻灯片位置；空页计入页数，但纯空白页不会成为有效证据。
- 入库使用 `require_complete=True`：PDF 读取全部页并保留页码，Excel 读取全部行。普通预览继续保留原有页数/行数限制。
- 200,000 字符的入库上限保持不变；超过上限明确失败，提示拆分资料。缺失文件、损坏文件或不可用解析器不会作为错误占位文字入库；错误信息不含正文或源文件路径。
- 原生来源权限、内容哈希复核、最终授权、耐久任务和失败状态继续生效；没有新增数据库迁移、外部 embedding 服务或生成模型调用。

## 用户使用路径

1. 在知识库页上传 PDF、DOCX、PPTX、XLSX、Markdown 或 TXT。当前页面使用工作区的手动上传来源，首次上传会尝试创建；操作仍须有相应写权限。高级项目、客户、个人来源通过原生 `POST /knowledge/sources` 创建，指定对应 scope，不把工作区上传自动解释为项目私有资料。
2. 查看文档状态和任务进度。入库完成后为 `indexed`；失败时查看任务原因，损坏文件需重新提供有效资料，超限文档需拆分。可重试错误使用原生任务重试，重建使用文档的原生 `reindex` 入口。
3. 搜索后可以查看提取内容、下载经过内容哈希验证的原文，或将选中的文档带入项目对话。发送前确认实际选中文档；历史文档 ID 和新版文档 ID 有独立命名空间。
4. 对话及 Skill 工作流通过同一知识上下文与权限链使用资料。回答引用使用 `[K1]` 等本轮证据键，展示引用时绑定文档、Source、chunk 和内容哈希；只有实际引用的来源显示为引用，不把搜索命中本身当成答案事实。

## 真实资料副本验收

通过原生鉴权 API 只读获取当前线上唯一已索引文档的原件：Source 1 / Document 1，PPTX，139 页，10,886,786 字节。文件 SHA-256 为 `3a8c3eb22ec89451e92285bb14593013d3fc625d1f960776bbc1b54aef7be33e`。原件和私有问题清单均不提交仓库。

当前解析器在该文件上漏读了 67 个表格；修复后的提取文本为 45,348 字符，旧解析器为 37,107 字符。此比较来自同一原件的两版解析，不等同于线上历史索引的生成过程；线上历史索引有 14 个 chunk，其时间戳未改写。

`scripts/knowledge_document_eval.py` 将原件副本放入自动清理的临时存储和内存 SQLite，经原生文档注册、写权限、索引最终授权、检索、知识上下文和引用绑定函数验收。只调用本地 embedding 模型，不调用生成模型、不创建生产任务。副本属于临时个人来源，另一个隔离用户对全部显式文档查询均返回空结果；这没有改变线上工作区来源的原有共享权限。

固定 9 个问题包含 7 项表格/正文事实查找和 2 项无关主题排除，要求：预期片段确实存在于原文、同一检索 chunk 含所需片段、提示中保留证据、引用正确绑定文档与 Source、无权限用户无法访问。负例必须没有结果。文档被临时重命名为无业务含义的别名，避免靠原文件标题代替内容命中。

| 模式 | 问题结果 | chunk 数 | 入库耗时 | 预热检索 P50 / P95 |
| --- | --- | --- | --- | --- |
| hash / 词法基线 | 9/9 | 17 | 389 ms | 20 / 24 ms |
| FastEmbed / 混合语义 | 9/9 | 142 | 7,746 ms | 66 / 71 ms |

语义模型为 `BAAI/bge-small-zh-v1.5`，使用已有本地缓存；检索分位数采用 nearest-rank，样本数 9。数值是开发机上的隔离副本结果，不是生产、大库、首次模型下载或生成回答延迟。

初评两种模式各为 8/9：一项预期错误地把表格中跨单元格的句子当作连续文本。核对原件后，保留全部查询，将该预期改为原始两行（包括相邻单元格及结论），并补充“预期存在于原文”的校验；没有调整检索算法、阈值或放宽返回结果要求。初版私有清单 SHA-256 为 `99231d3b9bcfc0342ac5fa36340f4d547bae60afc0fd5929f9d16066be22822a`，修订后为 `7482346bb4a4270cb5a2cfd628c0a062f4387c2b680fa9d8c91bc63ac39ceca6`。

脱敏证据：[词法结果](evidence/2026-09-22-knowledge-real-hash.json)、[语义结果](evidence/2026-09-22-knowledge-real-semantic.json)。只记录哈希、计数、真假结果和耗时，不包含文件名、路径、问题、预期答案或原文。

### 复现

私有 JSON 清单格式如下，`document_index` 从 0 开始；无关问题使用 `null` 和空 `phrases`。

```json
{
  "documents": [{"path": "/private/local/copy.pptx"}],
  "cases": [
    {"query": "资料中的具体问题", "document_index": 0, "phrases": ["原文中的预期片段"]},
    {"query": "无关主题", "document_index": null, "phrases": []}
  ]
}
```

从 `backend/` 运行 `.venv/bin/python scripts/knowledge_document_eval.py /private/manifest.json`；追加 `--semantic` 使用配置的本地语义模型。失败返回非零退出码。清单应保留在私有位置，报告可以归档；调用完成或失败后均恢复进程原有 Provider 和上传目录配置。

## 生产启用与限制

本轮完成的是实现及实际文件副本验收，没有改动线上 Provider 配置或业务索引。发布时线上仍为 hash 配置；2026-09-23 曾切换为 `fastembed`，09-24 语义重建失败后回退为 `hash`，并以原生流程重建为 17 个完整抽取分块，线上按本节 9 题复核 9/9（见 [24 回退记录](24-知识语义检索与质量验收.md)）。生产语义检索仍未启用。

生产启用仍按 [24 启用与回滚](24-知识语义检索与质量验收.md) 执行：预热、本地语义配置、服务重启、由有权限的操作者通过原生来源文档 `reindex` 逐文档重建，检查任务成功、覆盖率、引用和业务问题。正常代码部署不会自行安排此业务重建。此次目标原件已可明确定位为 Source 1 / Document 1 和上述 SHA-256；操作前须重新核对原件和权限。

支持的是可提取的文本；不包含扫描件 OCR、图片/图表视觉理解、Word 页眉页脚和文本框。Excel 读取已有缓存值，不计算公式。表格保留行/单元格关系，不保证转换为自然语言句子；大文件超过字符上限须拆分。没有验证任意格式或任意问题的完整召回率，也没有将确定性引用绑定验收解释为生成模型回答正确率。
