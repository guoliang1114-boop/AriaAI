# 记忆系统优化方案

> 更新日期：2026-05-28  
> 关联文档：[01-产品战略方向](./01-产品战略方向.md)、[04-RAG演进方案](./04-RAG演进方案.md)、[05-对话系统设计与规范](./05-对话系统设计与规范.md)、[11-Model-Harness产品方案设计](./11-Model-Harness产品方案设计.md)

## 1. 文档定位

本文用于梳理 AriaAI 当前记忆系统的优化方向，重点回答三个问题：

1. 当前项目记忆和客户记忆的问题在哪里。
2. 是否需要引入用户层记忆。
3. 下一阶段如何把记忆从“AI 总结”升级为“可追溯、可治理、可召回的组织知识资产”。

本文不要求立即开发代码，而是作为后续 Memory Harness 设计和产品排期依据。

## 2. 当前记忆系统现状

AriaAI 当前已有两类核心业务记忆：

| 层级 | 当前能力 | 主要内容 |
|---|---|---|
| 项目记忆 | `Project.context_memory_json` | 项目目标、阶段、风险、开放问题、下一步、重要文档、财务、交付信号、干系人观察 |
| 客户记忆 | `ClientRecord.client_memory_json` | 客户画像、决策模式、关键联系人、经验教训、项目历史、敏感话题 |

已有治理能力：

- `memory_version`
- `memory_stale`
- `memory_updated_at`
- `memory_rebuild_status`
- memory snapshots
- rollback
- summary cache
- batch rebuild
- memory operations dashboard
- 项目记忆提升到客户记忆

已有产品能力：

- 项目详情页展示项目记忆。
- 客户详情页展示客户记忆。
- 项目对话可注入项目记忆。
- 客户 scope 下可注入客户记忆。
- 部分项目记忆字段支持 `ai` 与 `pinned` 分槽。

这说明当前系统已经具备“长期记忆”的基础，但还没有完全进入“可信组织记忆”的阶段。

### 2.5 记忆系统与 Harness 架构的接口关系

本方案与 [11-Model-Harness产品方案设计](./11-Model-Harness产品方案设计.md) 直接衔接。记忆系统在 Harness 中的职责分布如下：

| Harness | 记忆相关职责 | 本方案对应章节 |
|---------|------------|--------------|
| **Context Harness** | 决定每次 AI Run 注入哪些记忆、注入多少 token | 第 9 节 召回策略 |
| **Persistence Harness** | 保存 memory candidate、长期记忆、evidence | 第 6、7 节 |
| **Event Harness** | 向前端发送记忆变更事件（candidate 生成、记忆更新） | 第 10.3 节 |
| **Policy Harness** | 控制记忆读写权限、敏感信息过滤 | 第 11 节 |
| **Run Manager** | 记录本轮 run 是否产生 memory candidate | 第 6 节 |

关键接口契约：

- **Context Harness → Memory Retrieval**：输入为 `run_id` + `user_message` + `scope`，输出为按优先级排序的记忆片段列表。
- **Persistence Harness → Memory Candidate**：在 `persisting` 阶段，将 candidate 写入队列，而非直接覆盖长期记忆。
- **Run Manager 记忆标记**：AI Run 记录本轮是否产生 `memory_candidate`，用于后续审计和追踪。

## 3. 核心诊断

### 3.1 记忆偏总结，证据不足

当前记忆主要由 LLM 根据项目数据重建为 JSON。它适合作为摘要，但不适合作为可追溯事实库。

问题：

- 单条记忆没有明确 `source_type`。
- 单条记忆没有明确 `source_id`。
- 用户很难知道某个结论来自哪次聊天、哪个文件、哪个任务或哪个付款记录。
- 记忆被重建后，旧结论为什么变化不够透明。

目标状态：

> 每条关键记忆都应该能回答：这句话从哪来、何时产生、谁确认过、是否仍有效。

**量化现状**（待基线测量）：

| 指标 | 当前基线 | 目标 | 测量方式 |
|------|---------|------|---------|
| 记忆全量重建频率 | 每个项目变更触发 1 次 | slot-level 后降低 60% | 重建次数 / 变更次数 |
| 单次重建平均 token 成本 | [待测量] | 降低 40% | 重建 prompt token 数 |
| 记忆来源可追溯率 | 0% | > 90%（关键记忆 100%）| 有 evidence 的记忆 / 关键记忆总数 |

### 3.2 stale 粒度偏粗

当前很多项目变更都会把整个项目记忆标记为 stale，然后触发重建。

问题：

- 成本较高。
- 高频变化会反复触发重建。
- 稳定的长期事实可能被模型重写。
- 用户难以理解“为什么记忆又过期了”。

目标状态：

> 只有受影响的记忆槽位 stale，而不是整个记忆对象总是 stale。

例如：

| 变更类型 | 应影响的记忆槽 |
|---|---|
| 新增付款 | `financial_status` |
| 新增/完成待办 | `next_actions`, `recent_progress` |
| 新增项目文件 | `important_documents`, `delivery_signals` |
| 更新客户干系人 | `stakeholder_notes`, 客户 `key_contacts` |
| AI 生成会议纪要 | `recent_progress`, `open_questions`, `next_actions` |

### 3.3 缺少 Memory Candidate 层

现在更像是：

```text
业务数据变化
  ↓
重建 memory JSON
  ↓
直接成为长期记忆
```

建议改成：

```text
业务数据 / 对话 / 文件 / Skill 输出
  ↓
生成 Memory Candidate
  ↓
去重、分类、打分、关联证据
  ↓
用户确认或系统低风险自动采纳
  ↓
进入长期记忆
```

Memory Candidate 的价值：

- 避免自动记忆污染。
- 让用户知道 AI 想记住什么。
- 让高价值经验可以被提升为客户记忆或组织知识。
- 为未来记忆审核、删除和回溯提供基础。

### 3.4 召回方式偏静态

当前项目记忆格式化后注入 prompt，字段和数量相对固定。

问题：

- 用户问风险时，不一定需要全部项目记忆。
- 用户问客户沟通时，应优先召回客户记忆和干系人。
- 用户问交付物时，应优先召回目标、文档、进展和交付标准。
- 固定注入容易占用上下文预算。

目标状态：

> 记忆召回应根据用户问题、当前页面、Skill、知识范围和任务类型动态选择。

### 3.5 项目记忆提升到客户记忆的规则还不够明确

已有提升能力，但需要更清晰的产品标准。

适合提升到客户记忆：

- 客户长期决策模式。
- 客户沟通偏好。
- 关键人立场和影响力。
- 可复用的合作经验。
- 敏感话题和避雷点。
- 跨项目有效的信任信号。

不适合提升到客户记忆：

- 单个项目的临时待办。
- 一次性交付状态。
- 已过期的报价、付款或排期。
- 未确认的猜测。
- 不具备跨项目复用价值的噪音。

## 4. 引入用户层记忆

### 4.1 为什么需要用户层记忆

当前项目记忆回答“这个项目是什么”。  
客户记忆回答“这个客户是谁”。  
用户记忆回答“AI 应该如何服务这个用户”。

用户层记忆可以沉淀：

- 用户喜欢中文还是英文。
- 用户喜欢简洁还是详细。
- 用户是否偏好先给结论。
- 用户是否要求只查询不修改。
- 用户是否习惯先做 review 再开发。
- 用户对 UI、文档、提交、部署的偏好。
- 用户在咨询场景中偏好的表达风格。

这类信息不属于项目，也不属于客户，但会影响所有交互体验。

### 4.2 与行业用户记忆方案的关系

业界常见的 AI 用户长期记忆方案（如 OpenClaw、Mem0 等）通常把长期记忆用于跨会话保存用户偏好、重要事实和上下文。常见形式包括：

- 用户偏好。
- 用户事实。
- 工作方式。
- 长期上下文。
- 可搜索的 Markdown 记忆文件。

AriaAI 可以借鉴这种思想，但不建议简单照搬为一个大文本文件。原因是 AriaAI 有业务对象、权限和团队协作场景，更适合结构化、可编辑、可审计的用户记忆。

### 4.3 用户记忆建议结构

建议新增 User Memory，第一版结构如下：

```json
{
  "response_preferences": {
    "language": "zh",
    "verbosity": "normal",
    "tone": "direct_collaborative",
    "format_preferences": ["conclusion_first", "short_sections", "action_plan"]
  },
  "work_style": {
    "prefers_root_cause_first": true,
    "prefers_no_code_changes_without_confirm": true,
    "prefers_review_before_implementation": true,
    "prefers_docs_before_large_refactor": true
  },
  "product_preferences": {
    "hide_internal_tool_logs": true,
    "show_progress_for_long_tasks_only": true,
    "prefer_lightweight_preview": true
  },
  "domain_preferences": {
    "consulting_output_style": "client_ready_but_practical",
    "planning_style": "phased",
    "risk_language": "specific_and_actionable"
  },
  "durable_facts": {
    "name": "",
    "role": "",
    "team_context": ""
  }
}
```

第一版不需要过度复杂，核心是让 AI 在所有项目和客户之上，知道当前用户的基本工作偏好。

### 4.4 用户记忆边界

必须避免三类记忆混淆：

| 信息 | 应进入 |
|---|---|
| “用户喜欢中文、先给结论、不要擅自改代码” | 用户记忆 |
| “客户 A 决策慢，需要董事长确认” | 客户记忆 |
| “项目 B 当前处于 lead 阶段，风险是付款未确认” | 项目记忆 |
| “某类咨询提案应包含 why now、方案、路线图、价值” | Skill/组织方法论 |

用户记忆不应该保存客户敏感事实，客户记忆不应该保存用户个人偏好。

### 4.5 用户记忆对 Skill 的影响

用户记忆不应改变 Skill 的专业逻辑，但可以调整输出方式：

| 用户记忆 | 影响的 Skill | 调整方式 |
|---------|------------|---------|
| "偏好先给结论" | `consulting-proposal-advisor` | 强制结论-led 标题，前置执行摘要 |
| "不要未经确认改代码" | `office-document-editor` | 只读模式，修改生成 diff 待确认 |
| "偏好中文" | 全部 Skill | 输出语言切换为中文 |
| "简洁风格" | `digital-strategy` | 减少冗余背景，压缩到核心观点 |
| "详细风格" | `audit-risk-assessment` | 补充更多判断依据和条款引用 |

关键原则：**用户记忆只影响输出形式，不改变专业判断。**

## 5. 推荐的记忆分层

建议 AriaAI 形成四层记忆：

```text
User Memory
  用户偏好、工作方式、输出风格、个人长期事实

Client Memory
  客户长期画像、决策模式、干系人、敏感话题、跨项目经验

Project Memory
  项目目标、阶段、风险、进展、文件、任务、财务、交付信号

Skill / Organization Memory
  方法论、模板、行业知识、可复用交付标准
```

优先级建议：

1. 系统安全和权限规则最高。
2. 用户记忆影响表达风格和工作方式。
3. 客户记忆影响客户关系判断。
4. 项目记忆影响当前事实和项目推进。
5. Skill 记忆影响专业方法和输出结构。

冲突处理原则：

- 项目事实优先于客户长期概括。
- 客户长期偏好优先于通用 Skill 模板。
- 用户表达偏好只影响输出方式，不改变业务事实。
- 安全和权限规则永远高于所有记忆。

## 6. Memory Candidate 设计

### 6.1 Candidate 类型

建议第一版支持：

| 类型 | 说明 | 目标层 |
|---|---|---|
| `user_preference` | 用户表达风格、工作方式偏好 | 用户记忆 |
| `project_fact` | 项目稳定事实 | 项目记忆 |
| `project_risk` | 风险、阻塞、开放问题 | 项目记忆 |
| `project_next_action` | 下一步行动 | 项目记忆 |
| `client_preference` | 客户偏好、敏感点 | 客户记忆 |
| `client_relationship_signal` | 关系、信任、决策信号 | 客户记忆 |
| `consulting_lesson` | 可复用经验 | 客户记忆或组织记忆 |

### 6.2 Candidate 字段

```json
{
  "id": 1,
  "scope": "user | project | client | organization",
  "type": "user_preference",
  "content": "用户偏好先查原因，不要直接优化代码。",
  "source_type": "chat_message",
  "source_id": 123,
  "project_id": 32,
  "client_id": null,
  "confidence": 0.86,
  "status": "pending | accepted | rejected | archived",
  "created_by": "ai | user | system",
  "created_at": "2026-05-28T00:00:00",
  "accepted_at": null
}
```

### 6.3 采纳规则

当前 v1 实现采用比早期建议更保守的规则：

- 对话中的“提交记忆候选”只创建 `pending` 记录，不直接触发全量重建或覆盖正式记忆。
- 用户、项目、客户三类候选都必须显式 accept/reject；项目与客户还要重新校验当前读写权限。
- Candidate 记录 `source_type/source_id/source_run_id/source_refs/content_sha256`，Assistant Message 同步保存无正文引用和 Run Output 状态。
- accept 后才增加正式记忆版本并生成 snapshot；accepted 内容进入受保护锚点，后续 AI 重建会合并而不是覆盖。
- reject 只保存裁决人与裁决时间，不改变正式记忆。
- 组织方法论仍不自动沉淀。

## 7. 证据与溯源

建议每条关键记忆都关联 evidence。

Evidence 字段：

```json
{
  "source_type": "chat | file | task | payment | stakeholder | manual | skill",
  "source_id": "123",
  "source_label": "项目对话 #247",
  "quote": "用户要求只负责找原因，不要负责优化。",
  "created_at": "2026-05-28T00:00:00"
}
```

展示原则：

- 普通聊天不展示完整证据。
- 记忆管理页展示来源。
- 重要客户记忆和项目风险应可追溯。
- 删除或修改记忆时保留操作记录。

## 8. 增量更新策略

### 8.1 当前策略

当前以 stale + rebuild 为主：

```text
数据变化
  ↓
memory_stale = true
  ↓
重建完整 memory
```

### 8.2 建议策略

改为混合策略：

```text
低频初始化 / 修复
  → full rebuild

日常数据变化
  → slot-level candidate / slot-level update

用户明确保存
  → memory candidate

高价值客户经验
  → promote candidate
```

Slot-level stale 示例：

| 记忆槽 | 触发源 |
|---|---|
| `financial_status` | payment 创建、更新、删除 |
| `important_documents` | 文件上传、生成、删除 |
| `next_actions` | todo 创建、完成、延期 |
| `key_risks` | 风险分析、会议纪要、用户明确风险描述 |
| `stakeholder_notes` | 干系人更新、客户沟通记录 |
| `decision_patterns` | 多项目复盘、客户会议结论 |

### Slot 依赖关系与 Rebuild 边界

部分 slot 之间存在依赖，变更一个可能需要联动标记：

| 触发源 | 主 stale slot | 联动 stale slot | 原因 |
|--------|-------------|----------------|------|
| 新增付款 | `financial_status` | `key_risks`（若付款阻塞风险解除） | 财务变化可能影响风险状态 |
| 完成关键待办 | `next_actions` | `recent_progress`, `delivery_signals` | 待办完成即进度更新 |
| 客户沟通记录 | `stakeholder_notes` | `client_preference`（若观察到新偏好） | 沟通中可能发现偏好变化 |

**Slot-level update vs Full Rebuild 的边界**：

| 场景 | 策略 | 判断条件 |
|------|------|---------|
| 单 slot 数据变化 | slot-level update | 变更明确归属于一个 slot，且无跨 slot 影响 |
| 多 slot 同时变化 | slot-level update（批量） | 变更可归类到 ≤ 3 个关联 slot |
| 项目阶段跃迁 | full rebuild | 阶段变化（如 lead → delivery）影响全局上下文 |
| 记忆质量异常 | full rebuild | 检测到记忆内部矛盾或过期率 > 50% |
| 首次初始化 | full rebuild | 项目无现有记忆 |

## 9. 召回策略

### 9.1 召回输入

Memory Retrieval 应考虑：

- user message
- active project
- active client
- selected skill
- page context
- knowledge scope
- conversation mode
- action policy

### 9.2 召回输出

```json
{
  "user_memory": ["用户偏好中文、先给结论、不要未经确认改代码。"],
  "client_memory": ["客户决策链较长，需要提前对齐关键人。"],
  "project_memory": ["当前项目处于 lead 阶段，核心风险是范围和预算未确认。"],
  "evidence_refs": []
}
```

### 9.2.1 上下文预算分配

动态召回必须有预算约束，否则记忆总量可能耗尽上下文窗口。

假设总上下文预算为 8K tokens（预留 4K 给对话历史和模型生成）：

| 记忆层 | 预算上限 | 优先级 | 截断策略 |
|--------|---------|--------|---------|
| 安全和权限规则 | 固定 200 tokens | P0（不可截断）| 无 |
| 用户记忆 | 800 tokens | P1 | 保留最近 3 条核心偏好 |
| 客户记忆 | 1,000 tokens | P2 | 保留关键决策模式 + 敏感话题 |
| 项目记忆 | 2,000 tokens | P3 | 按场景召回子集（非全量）|
| Skill / 组织记忆 | 500 tokens | P4 | 仅召回当前 Skill 相关方法论 |
| Evidence | 300 tokens | P5 | 仅保留关键记忆的来源摘要 |
| 动态调整缓冲区 | 200 tokens | - | 由 Routing Harness 根据场景再分配 |

**动态调整规则**：
- 风险分析场景：项目记忆预算提升至 2,500，客户记忆降至 500。
- 客户沟通场景：客户记忆预算提升至 1,500，项目记忆降至 1,000。
- 交付物生成场景：Skill 记忆预算提升至 1,000，用户记忆降至 500。

### 9.3 场景化召回

| 场景 | 优先召回 |
|---|---|
| 普通项目问答 | 项目 brief、阶段、目标、关键风险 |
| 风险分析 | key risks、open questions、delivery signals |
| 客户沟通 | 客户记忆、干系人、敏感话题、沟通偏好 |
| 会前准备 | 客户记忆、项目当前状态、待办、干系人、风险 |
| 交付物生成 | 项目目标、重要文件、交付信号、Skill 方法论 |
| 代码/产品讨论 | 用户偏好、当前任务上下文、相关 docs |

### 9.4 已实施：项目记忆按问题召回与引用（2026-08-25）

当前项目对话已在现有 `Project.context_memory_json` 之上先落地一层零迁移的动态召回，不再对每个问题无条件注入全部项目记忆。

- 根据本轮问题识别 `risk`、`delivery`、`financial`、`stakeholder`、`documents`、`overview` 等召回切面，并仅选择相关记忆槽位。
- 只有用户明确要求“全量/全面/完整”时才使用 `full` 召回；普通项目问题使用 `focused` 或 `overview`。
- 每轮最多注入 12 条项目记忆证据，单条最多 480 字符；发生截断时在 Context Receipt 中显式告警。
- 对可编辑槽位优先召回用户固定/accepted 锚点，再补充 AI 综合项，避免用户确认的事实被单槽位预算截掉。
- 注入 Provider 的每条记忆使用稳定的 `[M1]`、`[M2]` 引用键；最终答案只会暴露实际回指且通过校验的记忆来源。
- `Project Memory Evidence Manifest v1` 只持久化项目 ID、记忆版本/新鲜度、召回模式、切面、槽位、索引和内容 SHA-256，不复制记忆正文。
- 回答持久化、ChatTrace、Run Evaluation 和前端引用共用同一份 Manifest 校验结果；伪造、跨轮或被篡改的 `[M*]` 不会进入对用户可见的来源。
- 记忆为 `STALE` 时仍保留新鲜度保护：模型必须优先采用更新的项目事实，并在依赖陈旧结论时说明限制。

后续进展（2026-08-28）：查询时精选已与持久化槽位账本打通。项目 12 个槽位和客户 8 个槽位拥有独立版本、内容 SHA-256、来源引用与新鲜度；财务、进展、待办、里程碑、文件和干系人变更只标记受影响槽位。Provider 读取前会校验槽位摘要，Context Receipt 只报告当轮选中槽位的陈旧数和来源数。每槽位内容已进一步拆成事实账本；局部重建按实际陈旧集合读取来源、生成严格 patch 并定点更新槽位/事实，带写前基线校验和自动全量回退。综合 JSON 暂保留为兼容视图。

## 11. 安全与治理

### 11.1 自动记忆污染

风险：

- 用户临时表达被误认为长期偏好。
- 客户敏感信息被错误写入用户记忆。
- 外部文档内容污染用户偏好。

应对：

- 第一版以显式记忆为主。
- 自动提取只生成 candidate。
- 外部内容不能直接写入用户记忆。
- 用户记忆必须可查看、可删除、可禁用。

### 11.1.1 记忆失败回退机制

| 场景 | 检测方式 | 回退动作 |
|------|---------|---------|
| 用户记忆与项目事实冲突 | 模型输出中出现"根据您的偏好..."但与项目数据矛盾 | 触发冲突提示，优先项目事实，标记用户记忆为"需复核" |
| 用户记忆导致输出质量下降 | 用户连续 2 次修正 AI 输出，且修正方向与用户记忆相反 | 自动降低该记忆的权重，生成 candidate 提示用户删除 |
| 关键记忆遗漏 | 用户问"上次不是说..."但记忆未召回 | 触发 memory gap 检测，标记为候选记忆，提示用户确认 |
| 用户禁用记忆后体验下降 | 用户关闭记忆注入后，AI 输出明显不连贯 | 允许用户快速重新启用，保留记忆 30 天 |

### 11.2 权限与边界

原则：

- 用户记忆属于用户。
- 客户记忆属于客户空间。
- 项目记忆属于项目空间。
- 组织记忆需要更高权限。

不同用户在同一客户/项目中：

- 可以共享客户/项目记忆。
- 不共享个人用户偏好。
- 用户偏好只影响该用户自己的 AI 体验。

### 11.3 敏感信息

用户记忆不应默认保存：

- 密码、密钥、token。
- 身份证件、银行卡等敏感个人信息。
- 客户机密细节。
- 未经确认的人事评价。

### 11.3.1 敏感信息自动检测机制

| 信息类型 | 检测规则 | 处理方式 |
|---------|---------|---------|
| 密码/密钥/token | 正则匹配：长度 > 16 的随机字符串、含 `sk-`/`Bearer`/`AK` 前缀 | 拒绝保存，提示用户"敏感信息不会进入记忆" |
| 身份证号 | 正则匹配：15/18 位数字，含校验位验证 | 拒绝保存，打标 `sensitive_blocked` |
| 银行卡号 | Luhn 算法校验 | 拒绝保存 |
| 客户机密细节 | 关键词 + 上下文判断（如"保密"、"内部"、"勿外传"）| 生成 candidate，标记为 `high_sensitivity`，必须用户确认 |
| 人事评价 | 涉及人名 + 负面评价词汇 | 生成 candidate，标记为 `subjective`，必须用户确认 |

检测层：
- **第一层**：正则/规则引擎，实时拦截明显敏感信息。
- **第二层**：模型轻量判断（调用低成本模型），识别上下文敏感信息。
- **第三层**：用户手动标记，反馈回检测规则库。

## 12. 分阶段落地建议

### Phase 1：用户记忆 v1

目标：快速提升个人化体验。

范围：

- 新增用户层记忆结构。
- 设置页可查看、编辑、删除。
- 对话中支持“记住这个偏好”。
- prompt 注入简短 User Memory。
- 默认只保存显式记忆。

**显式记忆定义**：

| 类型 | 示例 | Phase 1 处理方式 |
|------|------|----------------|
| **显式记忆** | 用户说"记住我偏好中文"、"以后先给结论" | 直接生成 candidate → accepted |
| **半显式记忆** | 用户连续 3 次在同一类场景表达相同偏好 | Phase 1 不处理，Phase 2 生成 candidate → 用户确认 |
| **隐式记忆** | AI 从对话中推断出的偏好 | Phase 1 不处理，Phase 2 引入 candidate 机制后处理 |

Phase 1 只处理显式记忆。半显式和隐式记忆在 Phase 2 引入 candidate 机制后处理。

验收标准：

- 用户偏好能跨项目生效。
- 用户可以看到和删除偏好。
- 不会自动把客户/项目事实写进用户记忆。

### Phase 2：Memory Candidate

目标：降低记忆污染，提升用户控制感。

范围：

- 新增候选记忆概念。
- 对话、文件、Skill 输出可以生成候选。
- 用户可 accept/reject。
- 项目和客户记忆页展示候选。

验收标准：

- AI 不再直接把所有观察写入长期记忆。
- 用户能决定哪些内容沉淀。
- 客户记忆提升更透明。

当前进展（2026-08-23）：基础闭环已落地。新增 `memorycandidate` 表与 `/memory-candidates` 创建、列表、详情、接受和拒绝 API；项目聊天“沉淀”改为创建来源关联候选，项目记忆页提供审核；`RunOutputRecord v1`、Product Run Event 和持久化 Activity Timeline 只保存候选引用与摘要哈希，不复制候选正文。客户候选已按相关项目成员权限隔离，accepted 项目/客户候选会在后续 AI 重建中保留。

裁决授权加固（2026-08-30）：accept/reject 不再仅依赖 Router 入口的一次权限检查。最终写事务会重新锁定并刷新候选所有者、目标 Project/Client、当前 `ProjectMember` 及候选本身，同时重验账号激活状态、写角色和客户—项目关系。若撤权先完成，裁决返回 403 且正式记忆不变；若裁决先持有成员行锁，撤权必须等待该事务结束。客户裁决按 `ClientIdentityNamespace → User → Project(s) → Client(s) → ProjectMember → MemoryCandidate` 锁序执行，账号停用、降级和删除也先锁 `User`，避免 PostgreSQL 反向锁死。项目/客户接受还将 candidate、聚合记忆、slot/fact/snapshot 与来源消息置于同一次 commit，任一步失败时整体回滚。同日随后的迁移 `035_v1_35` 已把该授权从规范化名称关系升级为稳定 `Project.client_id`；名称 advisory lock 仅保留为创建、改名和关系改绑的 writer namespace，不再承担运行时归属判定。

稳定客户身份进展（2026-08-30）：上述长期模型已由加法迁移 `035_v1_35` 落地。`Project.client_id` 是客户记忆、Stakeholder、RAG、Context Builder 和候选授权的唯一关系身份，`Project.client` 降为展示快照；迁移仅在新增列时对规范化后唯一的历史名称执行一次回填，重名、空白、未匹配以及未来新建的同名客户都不会被运行时名称推断认领。客户 ACL 同时纳入创建者与稳定项目成员：viewer 只读，owner/editor 可写；重建、摘要、晋升和 Briefing 在 Provider 返回后再次锁内复权，撤权或改绑后的旧结果不得保存。Briefing 最终保存会冻结所有确定性来源行并重验 source version；文件摘要还绑定磁盘 SHA-256，失败回执在内部 rollback 后重新授权。客户删除或解除关联也不会把 client-only 文档扩大为全局知识。

并发与后台任务收口（2026-08-30）：客户普通元数据仍可由任一关联项目的 owner/editor 维护，但改名和删除会影响全部关联项目，因此除管理员/客户创建者外，必须对所有关联项目均有写权。项目/客户记忆队列在发布 scheduler job 前先持久化可声明状态，worker 用状态与 generation token/项目 `updated_at` 做 CAS；cancel、ABA 重排队、成功后迟到失败均不能写旧记忆、snapshot、warm job 或 failure receipt。Knowledge 持久任务和 Durable TaskRun 均绑定真实发起人，只有代码级显式内部调用才能选择 trusted-system；Provider/embedding/文件生成返回后必须再次通过 active User、精确 Project/Client membership、job/step lease 和来源快照，才能原子写入 chunk、checkpoint、ProjectFile、Artifact 或回执。Knowledge 派生 JSON 使用不可变版本 key 与原子 replace，rollback journal 清理由失败事务产生的新文件，原件 path/SHA 在抽取前后和最终锁内重验。HITAS 项目写入同样只在最终 action/actor/project/file 锁内发布 Office/Markdown 结果；撤权、回收、拒绝和 supersede 会删除临时结果，提交失败会补偿恢复磁盘状态。

补充进展（2026-08-24）：项目与客户结构化记忆的新鲜度已进入模型侧保护和用户侧 Context Receipt。`memory_stale=true` 时，上下文明确要求把旧综合结论视为暂定信息，并优先采用更新的里程碑、待办、进展、文件与本轮输入；前端同时展示记忆版本和“陈旧/最新/缺失”状态。Receipt 只持久化状态、版本和证据计数，不复制记忆正文，因此无需新增数据库迁移。

动态召回进展（2026-08-28）：Phase 4 的 `query-aware retrieval` 已覆盖项目、客户和用户三层。项目层按风险/交付/财务/干系人/文档选择槽位并使用 `[M*]` 引用；客户层仅在关系、决策、干系人、历史经验和跨项目问题中注入；用户层按本轮语言、语气、格式和详略要求移除冲突旧偏好。三层选择结果进入无正文 Context Receipt 与 60 场景确定性门禁。独立 slot 存储、定向 stale、事实级 provenance、局部生成/保存、写前冲突检测和安全全量回退均已落地。每条事实拥有稳定内容身份、版本生命周期、独立完整性与 `matched/scoped/legacy/unresolved` 诚实来源状态；剩余工作是接入能直接产生结构化 source ID 的提取器，并在兼容期验证后把综合 JSON 降级为只读视图。

## 14. 数据模型演进方案

### 14.1 当前模型

- `Project.context_memory_json: JSONB`
- `ClientRecord.client_memory_json: JSONB`

### 14.2 目标模型

建议**新增表**（而非修改现有表），降低迁移风险和回滚成本：

| 表名 | 说明 | 与现有表关系 | 引入阶段 |
|------|------|------------|---------|
| `user_memories` | 用户层记忆 | 新增，关联 `users.id` | Phase 1 |
| `memory_candidates` | 候选记忆队列 | 新增，关联 `projects`/`clients`/`users` | Phase 2 |
| `memory_evidences` | 记忆证据 | 新增，关联 `memory_candidates` 或长期记忆 | Phase 3 |
| `project_memory_slots` | 项目记忆槽位（拆槽）| 渐进式迁移，逐步替代 `context_memory_json` | Phase 4 |
| `client_memory_slots` | 客户记忆槽位 | 渐进式迁移，逐步替代 `client_memory_json` | Phase 4 |
| `project_memory_facts` | 项目槽位内的稳定事实身份、生命周期与来源关系 | 关联项目和槽位 | Phase 3/4 |
| `client_memory_facts` | 客户槽位内的稳定事实身份、生命周期与来源关系 | 关联客户和槽位 | Phase 3/4 |

### 14.3 迁移策略

**Phase 1：用户记忆（零侵入）**
- 新增 `user_memories` 表。
- 不影响现有 `Project` / `ClientRecord` 的任何逻辑。
- 回滚：删除 `user_memories` 表即可。

**Phase 2：候选记忆（旁路系统）**
- 新增 `memory_candidates` 表。
- 现有 `context_memory_json` 继续工作，候选记忆作为旁路写入。
- 候选记忆不影响现有记忆注入逻辑，仅在前端展示候选列表。
- 回滚：停止写入 candidate，前端隐藏候选列表。

**Phase 3：证据与溯源（扩展字段）**
- 已落地实际表名 `projectmemoryfact` / `clientmemoryfact`，由 `034_v1_34` 从槽位账本幂等回填。
- 每条事实保存内容摘要、首次/最近出现版本、active/retired 生命周期、新鲜度和来源关系；来源不足时明确保留 `scoped`、`legacy` 或 `unresolved`，不虚构直接证据。
- 后续结构化提取器可直接写入更精确的 source ID，但不得绕过 Aria 的项目/客户权限和记忆候选裁决。
- 回滚：事实账本处于双写增强层，不影响综合 JSON 和槽位兼容读取。

**Phase 4：增量更新（渐进拆槽）**
- 已新增实际表名 `projectmemoryslot` / `clientmemoryslot`，由 `033_v1_33` 从现有 JSON 幂等回填。
- 已进入双写与校验阶段：综合 JSON 重建同步 slot，读取时以 SHA-256 校验后的 slot 覆盖兼容视图。
- 已实现变更类型到受影响槽位的定向 stale；兼容聚合仍保留总体 stale 供旧客户端使用。
- 已由 `034_v1_34` 增加事实级 evidence ledger，并完成 slot-level 局部重建；待结构化 source ID 和兼容读取完成验证后，再进入废弃阶段：停止写入 `context_memory_json`，保留只读兼容 1 个版本后删除。
- 回滚：双写期间可随时切回读取 `context_memory_json`。

### 14.4 关键设计原则

- **不删除现有字段**，只新增表和字段。
- **双写兼容期**：每个阶段都有新旧并行的过渡期。
- **可独立回滚**：每个阶段的改动可独立回滚，不影响其他阶段。
- **数据零丢失**：迁移过程中，旧数据始终保留直至验证完成。

### 14.5 开放问题的解决生命周期（已实施）

`open_questions` 仍是当前待确认状态的唯一记忆槽位，`ProjectMemoryFact` 仍提供内容身份和 active/retired 生命周期。`ProjectQuestionResolution` 保存当前生命周期状态，`ProjectQuestionResolutionEvent` 只追加每次解决/重开的原始审计；它们补充而不替代项目记忆，绑定问题 SHA-256、原事实身份、Assistant Message/Conversation、说明、操作者以及聚合/槽位版本。解决事务会同步退休问题事实；重开把问题恢复为 pinned 锚点。任何后续项目记忆变化只产生 `needs_review` 投影，不允许模型自动宣告旧结论继续有效。表和约束由 `038_v1_38` 管理。

Phase 3S 增加 `ProjectQuestionProfile`，仅保存同一问题 SHA-256 下的人工责任元数据：负责人、优先级、截止日期、当前 revision 和操作者；`ProjectQuestionProfileEvent` 为每次实际变化保留前后值。它不保存开放/解决状态，也不会让责任记录变成记忆事实。项目工作台只显示仍存在于当前开放问题或解决账本中的身份，避免已经退出两个事实源的元数据反向制造“幽灵问题”。负责人必须是当前有效项目成员；profile 写入在项目最终写锁内重新授权并按 expected revision 失败关闭。`039_v1_39` 负责唯一身份、priority/revision CHECK、SET NULL/CASCADE 外键及索引。

Phase 3T 不创建新的“问题证据表”，而是在读取时构造当前问题证据池。项目记忆通过 query-aware 槽位选择生成无正文 manifest，项目知识通过当前项目 ACL 做向量召回；候选回答只读取其持久化 metadata 中已经通过校验的 knowledge/project-memory cited identities。知识证据以稳定 evidence ID 对齐，项目记忆以 `slot + content_sha256` 跨记忆版本对齐；历史引用未命中当前证据池时明确降级，不能因为“过去读过”就冒充当前证明。`open_questions` 来源只能证明不确定性存在，明确按 context-only、零支持权重处理，不能用问题本身循环证明答案。向前端返回的项目记忆来源不含事实值或 SHA-256，知识来源不含 chunk 正文；只保留标题、槽位、版本、检索分数、provenance 等有界元数据，并分别显示召回来源数与可用于支持的来源数。准备度是人工选答辅助，不是记忆事实、置信概率或正确性裁决；记忆陈旧时继续显示警告并保持关单禁用。本阶段无数据库迁移。

Phase 3U 同样不建立补证计划表，也不把规则建议写回项目记忆。每次显式生成都会重新读取 Phase 3T 的当前证据基准，将 `memory_stale`、证据状态、支持来源数、候选强度和 warning 代码折叠为 hash-only basis fingerprint；计划响应不携带项目记忆事实正文、内容摘要、来源标题或检索 chunk。陈旧记忆会形成阻断缺口和“先刷新再分析”的内部核验草稿，但规划器本身不会触发重建；只有上下文来源时会要求补原始证据，而不会把 `open_questions` 当作答案证据。用户在前端编辑的动作和负责人不持久化、不进入记忆候选，也不改变问题事实或解决状态。本阶段无数据库迁移。

Phase 3V 只在用户点击“准备创建”后持久化补证动作冻结预览，并且仍不把预览、拒绝项或人工沟通草稿写入项目记忆。第二次明确确认且当前证据 basis 未变化时，项目待办目标通过现有数据源进入后续记忆刷新，因此确认事务会将受影响的项目记忆、槽位和事实标记为 stale；人工沟通请求目前是独立协作账本，不冒充已发送事实，也不触发记忆刷新。证据漂移、预览过期、快照破坏或权限/负责人失效只改变 promotion 审计状态，不创建业务目标。`040_v1_40` 的三张表补充 HITAS 与协作审计，不替代 `open_questions`、问题解决账本、记忆事实或候选记忆。

## 15. 总结

AriaAI 的记忆系统下一步应从“两层业务记忆”升级为“四层记忆体系”：

```text
User Memory
  ↓
Client Memory
  ↓
Project Memory
  ↓
Skill / Organization Memory
```

其中，用户记忆是最值得近期补上的一层。它投入不大，但能显著提升 AI 的连续性和个人化体验。

长期来看，真正的壁垒不只是“能记住”，而是：

- 记得对。
- 记得有来源。
- 记得可删除。
- 记得能按场景召回。
- 记得能沉淀为团队资产。

这也是 AriaAI 从“项目 AI 助手”走向“客户关系智能系统”和“组织记忆系统”的关键一步。
