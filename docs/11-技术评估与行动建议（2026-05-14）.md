# AriaAI 技术评估与行动建议

> 评估日期：2026-05-14
> 评估基础：项目文档（`00-09`）、代码结构、构建状态、测试覆盖、安全审计清单
> 版本基准：`V0.0.2`，commit `407ee5c`

---

## 一、总体判断：产品方向对，技术债在积累

### 1.1 产品层面：方向非常清晰，但功能已超过验证深度

**已经做对的**

- **战略定位准确**。「客户关系智能系统」比「AI 协作工作台」更有护城河，北极星场景（会前 30 秒）定义得很尖锐。
- **核心资产模型已成型**。项目记忆 → 客户记忆 → 结构化干系人 → 跨项目沉淀，这个分层架构是扎实的。
- **关键闭环已跑通**。Skill 从项目/客户空间启动 → Chat 执行 → 保存为文档 → 触发记忆刷新，这个回流链路已经有产品价值。
- **会前简报 V1 已落地**。这是离北极星场景最近的功能，技术上不调用 LLM（纯聚合），产品表达很克制。

**但最大的判断是：功能已经过度建设了。**

当前阶段，产品在没有真实用户闭环验证的情况下，已经完成了：
- 10 个 Alembic 迁移版本
- 记忆快照、diff、回滚
- 任务治理服务端统计
- 多视角摘要缓存
- 结构化干系人全链路
- 项目空间重构第一阶段

这些都很对，但风险在于：**团队在用工程技术假设用户需求，而不是让用户行为告诉产品该建什么。**

### 1.2 技术层面：架构在进化，但安全和运维是短板

**好的方面**

- 后端大路由拆分已经在发生（`projects_briefing.py`、`projects_memory.py`、`projects_files.py` 已拆分出来）。
- Alembic 迁移治理很规范（10 个版本，命名统一，有治理脚本）。
- `services/` 层拆分得比较细（40+ 个 service 文件），业务逻辑没有全堆在 router 里。
- 前端构建 329ms，很健康。

**差的方面**

| 维度 | 现状 | 风险 |
|------|------|------|
| 安全 | 3 个 P0 漏洞敞开 | 数据泄露一次，前面所有建设归零 |
| 备份 | 零数据库备份策略 | 误操作或迁移失败无法恢复 |
| 运维 | 无 HTTPS、无监控、无日志聚合 | 生产环境裸奔 |
| 前端稳定性 | 零 ErrorBoundary | 任何组件抛错就是全局白屏 |
| 测试 | 后端 55%，前端 pages/hooks 未统计 | 核心模块（file_generators、知识库）0% |
| RAG | 全量 chunk 加载到内存做余弦相似度 | 知识库增长后会 OOM |

## 二、中肯建议：三条线，先救命再打仗

按 **生存 > 验证 > 建设** 的逻辑重新排序，不是按功能规划的 Sprint 顺序。

### 线 1：安全与生存（本周必须做）

这几件事不做，数据泄露或丢失一次，前面所有功能建设都归零。

| 优先级 | 事项 | 涉及文件 | 为什么紧急 |
|--------|------|----------|-----------|
| P0 | 修复无用户时认证绕过 | `main.py:225-230` | 任何人可在空库环境访问全部 API |
| P0 | CORS 从 `*` 改为明确域名 | `config.py:129`、`.env` | 当前配置是 XSS/CSRF 的温床 |
| P0 | 删除 `Login.tsx` 的 Token 控制台日志 | `Login.tsx:34` | Token 暴露在浏览器控制台 |
| P0 | 建立数据库定时备份 | 新增 `backup.sh` | 当前零备份，迁移失败无法恢复 |
| P1 | Nginx API 代理加 `client_max_body_size` | `nginx_ariaai.conf` | 上传大文件会 413 |
| P1 | PM2 加 `max_memory_restart` | `ecosystem.config.js` | 内存泄漏时自动重启 |

### 线 2：产品验证（下周开始，比任何功能都重要）

文档里写得很清楚：「找 5 个真实顾问在真实工作中使用北极星场景」。但这件事在代码和迭代计划里一直没有被**工程化地推进**。

建议不是「找人聊聊」，而是：

1. **选一个种子顾问**，给他开一个账号，让他在下周的真实客户会议前使用会前简报。
2. **埋 3 个极简观测点**：
   - 他打开会前简报后，有没有点「带着简报开启对话」？（转化漏斗）
   - 他在聊天里有没有触发干系人捕获？（行为触发是否自然）
   - 他有没有把 Skill 结果保存为文档？（回流闭环是否顺手）
3. **每周跟他聊 15 分钟**，只问三个问题：
   - 这周哪个时刻 AriaAI 帮了你？
   - 哪个时刻你觉得它碍事？
   - 如果只能留一个功能，你留哪个？

这比规划里的任何 Sprint 都更能决定下一版本该做什么。

### 线 3：架构收敛（本月做，但要克制）

**应该做的**

| 事项 | 理由 |
|------|------|
| 项目空间第二阶段：上传文件自动转 Markdown | 这是当前产品主线的核心基础设施，做完后「空间」才真正从 UI 概念变成数据和 AI 工作面 |
| 继续拆分 `projects.py`（还剩 3380 行）和 `clients.py`（1887 行） | 大文件是开发效率的瓶颈，但不需要一口气拆完，每次改哪个模块就把那部分拆出去 |
| 前端加 ErrorBoundary | 30 分钟的事，防止白屏 |
| 引入 TanStack Query | 替代现在各页面重复的 `useEffect + useState + fetch`，有缓存、去重、自动刷新 |

**不应该做的（至少这个月不做）**

| 事项 | 为什么暂缓 |
|------|-----------|
| RAG 引入 pgvector / rerank | 当前知识库规模小，Python 内存计算还能撑，且这不是北极星场景的瓶颈 |
| DeepSeek / 更多 Provider | 当前 Claude + Kimi 已覆盖主力场景，多 Provider 是运维负担 |
| 前端无障碍全面改造 | 内部工具，用户是顾问团队，可以排在商业化之后 |
| 记忆版本化的任意版本互比 | 已有快照 + diff + 回滚，够用了，不要继续堆 |
| CSS 全面 Tailwind 化 | `index.css` 1029 行确实大，但不影响用户 |

## 五、一句话总结

> **AriaAI 已经从「能不能做出来」进入「值不值得继续投入」的阶段。技术架构在正确轨道上，但接下来 30 天最重要的事不是写代码，而是让一个真实顾问在真实会议前打开会前简报，然后告诉我们他看到了什么。**
>
> 代码可以慢慢还，方向错了再快也是偏离。
