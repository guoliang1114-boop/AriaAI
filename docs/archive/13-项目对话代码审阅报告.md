## 三、审阅发现的问题

### 3.1 Critical（已修复 ✅）

#### Bug 1：@文件提及不注入文件内容

- **位置**：`context_builder.py` `build_project_context()` / `build_chat_context()`
- **根因**：`mention_context.file_ids` 被读取但从未用于文件内容注入。文件内容注入只发生在 `file_ids` 参数（来自 `req.file_ids`），而 `@文件` 提及的 ID 只进入 `mention_context.file_ids`
- **影响**：用户 `@文件` 后，AI 看不到文件内容，提及只是文本装饰
- **修复**：在 `build_chat_context()` 入口处合并 `mention_context.file_ids` 到 `file_ids` 参数

```python
# 修复后
_mention = mention_context or {}
_mentioned_file_ids = _mention.get("file_ids") or []
if _mentioned_file_ids:
    merged_file_ids = list(dict.fromkeys((file_ids or []) + _mentioned_file_ids))
    file_ids = merged_file_ids
```

#### Bug 2：P3 re-follow-up 截断未追踪

- **位置**：`chat_streaming.py` ~1505 行
- **根因**：re-follow-up 流中检测到截断时只发了 status 事件，未设置 `p3_double_truncated = True`
- **影响**：re-follow-up 被截断时，消息 metadata 不会标记 `truncated`，前端不显示"继续生成"按钮
- **修复**：在 re-follow-up 截断检测处添加 `p3_double_truncated = True`

#### Bug 3：P3 follow-up pending_markdown_saves 缺少 original_content

- **位置**：`chat_streaming.py` ~1370 行
- **根因**：P3 follow-up 中创建 `pending_markdown_saves` 时遗漏了 `original_content` 字段
- **影响**：P3 阶段写入的 Markdown 文件，前端 Diff 预览无法显示原内容
- **修复**：补全 `original_content` 字段

### 3.2 High（已修复 ✅）

#### Bug 4：@提及触发器过于宽泛

- **位置**：`projectChatMentions.ts` `getActiveMentionQuery()`
- **根因**：未检查 `@` 前的字符，导致 `email@domain.com` 也能触发提及面板
- **修复**：增加前置字符检查：`lastAt > 0 && !/\s/.test(beforeCursor[lastAt - 1])`

#### Bug 5：mention regex 过于宽泛

- **位置**：`projectChatMentions.ts` `MENTION_PATTERN`
- **根因**：`@[filesmh]` 字符类匹配 `@i:`、`@l:`、`@e:`、`@h:` 等无效格式
- **修复**：改为 `@[fsm]:` 精确匹配三种类型码

### 3.3 Medium（待修复）

#### Issue 6：sendMessageAsync 无超时/取消机制

- **位置**：`useProjectChatComposer.ts` `sendMessageAsync()`
- **根因**：fetch 调用没有 `AbortController` 或 timeout
- **影响**：后台请求挂起时用户无法取消
- **建议**：添加 `AbortController` 和 30s 超时

#### Issue 7：自动干系人检测无取消机制

- **位置**：`ProjectChatTab.tsx` ~317 行
- **根因**：useEffect 中的 async IIFE 无取消逻辑
- **影响**：组件卸载后可能 setState
- **建议**：添加 `useEffect` cleanup 或 `AbortController`

#### Issue 8：chat_plan.py 双 LLM 调用成本翻倍

- **位置**：`chat_plan.py` ~97-134 行
- **根因**：先 `complete()` 无 tools 获取计划描述，再 `complete()` 有 tools 预测工具
- **影响**：计划模式 token 成本翻倍
- **建议**：文档化此行为，或优化为单次调用（用 reasoning + function calling 模拟）

#### Issue 9：chat_streaming.py 单文件 1,740 行

- **位置**：`chat_streaming.py`
- **根因**：P1/P2/P3/P4 全在一个文件中，职责混杂
- **影响**：难以测试、难以review、改动风险高
- **建议**：拆分为 `chat_p1_planning.py`、`chat_p2_tools.py`、`chat_p3_followup.py`、`chat_p4_persist.py`

#### Issue 10：后台任务内存注册表

- **位置**：`chat_async.py` `_background_chat_tasks`
- **根因**：任务状态存储在进程内存，服务重启丢失
- **影响**：部署/重启后无法追踪运行中的后台任务
- **建议**：引入 Redis 或至少持久化到 TaskRun 表

### 3.4 Low（代码异味）

#### Issue 11：工具调用代码重复

- **位置**：`chat_streaming.py` 中 P2 主工具和 P3 follow-up 工具的执行逻辑几乎相同
- **建议**：提取 `execute_tool_with_artifact()` 通用函数

#### Issue 12：硬编码中文提示

- **位置**：`chat_streaming.py` 中大量 `\uXXXX` 转义中文
- **影响**：可读性差，国际化困难
- **建议**：使用常量或 i18n 字典

#### Issue 13：print() 调试语句残留

- **位置**：`chat_streaming.py` 中约 20 处 `print(f"[P1/P2/P3] ...", flush=True)`
- **建议**：替换为结构化 logging
