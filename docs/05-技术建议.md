# AriaAI 技术建议

> 日期：2026-03-26  
> 目的：从技术视角明确项目的关键风险、优先事项和实施方向  
> 原则：先稳住核心链路，再提升质量，再做平台化扩展

---

## 1. 总体判断

AriaAI 的技术难点不在单点功能，而在于以下几类能力的组合：

- 项目级上下文管理
- LLM 调用与工具执行
- RAG 检索与知识引用
- 文件生成与交付链路
- 异步任务与状态同步
- 前后端多模块协作

因此，技术规划不应按“功能模块越多越好”推进，而应优先解决：

> **系统如何长期稳定地产出可靠结果**

---

## 2. 当前最值得优先解决的问题

## 2.1 把“项目上下文组装”独立出来

### 问题

现在聊天链路中已经承担了很多职责：

- 用户输入
- 技能 prompt
- 项目背景
- 文件注入
- RAG 上下文
- 历史消息

如果这些逻辑持续堆在 `chat.py`，后续会越来越难维护。

### 建议

抽一个独立的 `context builder` 层，统一负责构造模型输入。

### 建议职责

- 加载项目基础信息
- 加载项目摘要
- 加载会话历史摘要
- 加载显式选中文档
- 加载显式选中文件
- 加载技能提示词
- 合并为统一上下文对象

### 预期收益

- 减少 `chat.py` 膨胀
- 便于后续替换上下文策略
- 更容易做 token 控制与质量调优

---

## 2.2 给 RAG 增加质量控制层

### 问题

“能检索”不等于“检索有价值”。  
咨询和交付场景对准确性要求高，如果召回质量不稳，用户会快速失去信任。

### 建议

不要只做简单 top-k 检索，至少补齐以下能力：

- chunk 策略可配置
- 检索结果分数阈值
- 文档来源展示
- 查询范围控制
- 项目文档与通用知识分层
- 为未来 rerank 留接口

### 短期实现建议

- 给 `retrieve()` 返回结构化结果，而不是只返回拼接字符串
- 增加 `score` 字段
- 增加 `document_id` / `document_name` / `chunk_index`
- 前端展示来源

### 预期收益

- 回答更可信
- 后续更容易优化检索质量
- 方便做“引用到项目输出物”能力

---

## 2.3 把交付物生成独立成子系统

### 问题

PPT、Word、PDF 现在虽然能生成，但从长期看，它们不是一个小工具，而是系统价值核心之一。

### 建议

把“交付物生成”从一般 tools 视角升级为独立子系统。

### 最少应具备的结构

- 输入模型
- 任务状态
- 输出模型
- 文件元数据
- 模板绑定
- 版本管理预留

### 建议拆分方向

- `generation request`
- `generation task`
- `generation result`
- `artifact metadata`

### 预期收益

- 更容易扩展文档类型
- 更容易做失败重试
- 更容易支持“生成后继续修改”

---

## 2.4 统一前后端数据契约

### 问题

项目已经有不少 API 和模型，继续扩展后最容易出的问题就是：

- 字段变更不同步
- 状态值不一致
- 前端 silently broken

### 建议

尽快建立统一的数据契约规范。

### 建议措施

- 后端 schema 命名稳定化
- 前端 API model 集中维护
- 状态字段统一枚举
- 接口新增/修改 checklist
- 对关键接口建立最小回归验证

### 重点接口

- `/chat/send`
- `/projects/*`
- `/knowledge/*`
- `/skills/*`
- `/artifacts/*`
- `/auth/*`

### 预期收益

- 降低联调成本
- 降低改动引发的连锁错误
- 提高多人协作稳定性

---

## 2.5 建立统一的异步任务状态机

### 问题

现在系统里已经存在多类异步流程：

- SSE 聊天
- 文档索引
- 工具执行
- 文件生成
- 定时任务

如果每一类都用自己的状态表达，前后端会越来越乱。

### 建议

建立统一的任务状态机语义。

### 推荐状态

- `pending`
- `running`
- `success`
- `failed`
- `cancelled`

### 配套建议

- 统一错误结构
- 统一日志格式
- 统一前端展示逻辑
- 统一重试机制

### 预期收益

- 状态更清晰
- 更容易扩展后台任务
- 前端更容易做统一体验

---

## 3. 短期建议（未来 2-4 周）

## 3.1 架构层

- 抽离 `context builder`
- 抽离结构化 RAG 返回模型
- 统一生成任务状态定义
- 明确 `AriaAI / ConsultantAI` 命名过渡策略

## 3.2 数据层

- 明确 PostgreSQL 是主数据库
- 说明 SQLite 仅保留兼容或本地测试用途
- 给关键模型增加更清晰的状态字段约束

## 3.3 工程层

- 统一文档编码策略
- 统一日志输出格式
- 制定新增接口/模型的改动清单
- 明确哪些文档是权威文档

## 3.4 用户价值层

- 上传文档后自动摘要
- 引用来源展示
- 执行摘要 / 周报 / 建议书初稿作为重点交付物

---

## 4. 中期建议（未来 1-2 个月）

## 4.1 项目上下文系统

- 会话摘要持久化
- 项目记忆卡
- 项目内重要结论沉淀
- 上下文优先级与 token budget 控制

## 4.2 知识系统

- 项目知识与通用知识分层
- rerank 机制
- 高价值知识片段沉淀
- 文档版本与失效策略

## 4.3 交付系统

- 文件版本管理
- 模板绑定项目
- 生成物迭代编辑链路
- 更强的 PPT / Word 结构控制

## 4.4 观测与运维

- 聊天链路日志
- RAG 命中日志
- 文件生成日志
- 失败分类与统计

---

## 5. 长期建议（未来 2-4 个月）

## 5.1 平台化能力

- 共享知识库
- 团队模板
- 团队权限
- 可配置化技能体系

## 5.2 AI 质量系统

- Prompt 版本管理
- 技能评估标准
- RAG 命中质量评估
- 输出质量回收机制

## 5.3 更成熟的任务编排

- 多步骤任务编排器
- 任务恢复机制
- 更完整的后台执行队列
- 定时任务与项目生命周期联动

---

## 6. 建议的技术优先级排序

如果只能按顺序做，我建议这样排：

1. 上下文构建层
2. RAG 质量控制
3. 交付物生成子系统
4. API / 模型契约统一
5. 异步任务状态机
6. 日志与可观测性
7. 模板系统增强
8. 技能系统平台化

---

## 7. 具体实施建议

## 7.1 代码结构建议

### 后端建议新增职责划分

- `app/services/context_builder.py`
- `app/services/retrieval_service.py`
- `app/services/generation_service.py`
- `app/services/task_state.py`

### 理想职责

- `context_builder`
  - 负责模型输入拼装
- `retrieval_service`
  - 负责知识检索与返回结构
- `generation_service`
  - 负责文件生成流程编排
- `task_state`
  - 负责统一状态定义

---

## 7.2 数据模型建议

建议后续考虑增加或强化的对象：

- `ProjectContextSnapshot`
- `ConversationSummary`
- `GenerationTask`
- `RetrievalHit`
- `ArtifactVersion`

这些不一定要马上全部落库，但从设计上应提前留位置。

---

## 7.3 测试建议

当前最值得补的不是全量测试，而是关键链路测试。

### 优先测试的链路

- 登录
- 创建项目
- 上传知识文档
- 检索知识
- 发起聊天
- 工具执行
- 生成并下载文件

### 优先类型

- API 集成测试
- RAG 结果结构测试
- 文件生成 smoke test
- 关键状态流转测试

---

## 8. 最值得尽早统一的工程规范

- 产品命名规范
- 文件编码规范
- 数据库规范
- 状态字段命名规范
- API 变更规范
- 文档维护规范

如果这些现在不统一，后面每次开发都会重复损耗精力。

---

## 9. 一句话建议

> **先把“项目上下文 + 知识引用 + 交付物生成”这条链做稳，再做更大的平台。**

这条链稳定了，系统才有真正的技术骨架。  
否则功能越多，复杂度越高，但体验未必变好。

---

## 10. 推荐下一步

如果要立刻进入执行，我建议下一步做三件事：

1. 设计 `context builder` 结构
2. 重构 RAG 返回模型
3. 定义交付物生成任务模型

这三件事会直接决定项目后面是否好扩展、好维护、好提质。
