# AriaAI 技术建议

> 更新日期：2026-04-15
> 说明：基于当前主线代码的现实状态给出技术取舍建议。本轮新增安全加固方向，并对前端状态管理提出具体建议。

---

## 1. 总体判断

近几轮技术工作最明显的进展有四点：

- 聊天链路已经完成一次成功的结构拆分，且流式输出的跨对话内容隔离问题已修复
- Web 与后端的部分契约开始收敛（`src/config/api.ts` 统一化推进中）
- 项目空间的业务价值明显增强
- CI/CD 流程已初步固化数据库迁移步骤

因此，当前最重要的技术目标不再是"证明能做出来"，而是**把主链路稳定下来 + 堵住安全漏洞 + 降低维护成本**。

---

## 2. 当前最值得继续推进的方向

### 2.1 安全加固（新增，立即推进）

本轮审查发现若干安全风险，建议在下一个迭代周期内专项处理：

- **API Key 加密存储**：用户的 LLM API Key 目前明文存数据库，应使用对称加密（Fernet/AES）存储
- **JWT secret 校验**：启动时检测是否使用了 `.env.example` 中的默认值
- **文件路径遍历**：文件下载/访问路由需加 `pathlib` 边界检查
- **认证端点速率限制**：`/auth/login` 接入 `slowapi` 频率限制
- **Markdown XSS**：AI 输出渲染层引入 `DOMPurify`

这五个点的修复成本都不高，但暴露风险很高，建议作为一个独立小 Sprint 先完成。

---

### 2.2 复制聊天拆分的成功经验

`chat.py` 的拆分已经证明方向正确。接下来最值得复用这套策略的对象是：

- `aria-web/src/pages/projects/ProjectDetail.tsx`
- `AriaAI/backend/app/routers/projects.py`

前者已开始第一轮拆分（`ProjectDetailLayout.tsx`、`useProjectDetailData.ts`），需要继续推进。后者 1500+ 行，尚未启动拆分，是当前最重的结构债务。

---

### 2.3 统一 API 与配置来源

现状已经比之前好很多，但仍存在局部绕开统一配置的代码。建议：

- 所有 Web 请求都统一走 `src/config/api.ts`
- SSE、导出和普通请求不要再各自维护独立入口

---

### 2.4 前端状态管理升级

当前前端存在两个值得改进的状态管理问题：

**认证状态脆弱性：**
- JWT 过期后 UI 不主动感知，多并发 401 触发多次 logout（race condition）
- 建议：请求拦截器中用 flag 防止重复 logout；解析 JWT `exp` 实现 token 静默刷新

**缺少全局 Error Boundary：**
- React 中任意未捕获异常会导致整页白屏
- 建议：在路由层或关键页面层级添加 `<ErrorBoundary>` 组件

中长期可以评估引入 React Query 替代手写 fetch + 状态管理，自动处理缓存失效、重试和 loading 状态。

---

### 2.5 优先补测试，而不是继续裸重构

聊天已有最小回归测试，这是非常好的起点。下一步应把测试覆盖推进到：

- 项目详情聚合
- notes / todos
- 知识库状态流转
- 设置来源链路

---

### 2.6 单独做一轮编码与文案治理

这不是"美化问题"，而是可维护性问题。乱码会同时伤害：

- 用户体验
- 文档可信度
- 代码可读性

---

## 3. 当前仍需解决的技术问题

### 3.1 新的复杂度中心已经转移到项目域

聊天拆分完成后，最重的复杂度已经迁移到项目域前后端。`projects.py` 的 1500+ 行和还未完成拆分的 `ProjectDetail.tsx` 是当前最大的维护风险点。

---

### 3.2 数据库查询性能

项目域存在 N+1 查询问题（列表 + 关联对象逐一查询），以及部分外键字段缺失数据库索引。数据量小时不明显，应在数据增长前修复。

建议：使用 `selectinload()` 优化关联查询，在 Alembic 迁移中为 `project_id`、`user_id`、`client_id` 等高频过滤字段补索引。

---

### 3.3 RAG 仍偏 baseline

结构化引用已经有了，但检索策略、过滤和扩展性仍偏基础。具体问题：

- 无 rerank，召回质量依赖 embedding 相似度
- 前端不展示引用来源，用户无法验证 AI 回答依据
- 本地 FAISS 在数据量增长后扩展性受限

---

### 3.4 自动化保护不足

当前重构节奏已经快于测试体系增长速度。每次大型重构都存在回归风险而没有自动化保护。

---

## 4. 建议实施节奏

### Sprint 0（安全加固）

- API Key 加密存储
- JWT secret 启动校验
- 文件路径遍历防护
- 认证端点速率限制
- Markdown XSS 防护（DOMPurify）

### Sprint A

- 拆分 `ProjectDetail.tsx`（继续推进已开始的工作）
- 收口项目聊天统一 API 配置
- 修复认证 race condition + 增加 Error Boundary

### Sprint B

- 拆分 `projects.py`
- 补项目主链路测试
- 修复 N+1 查询 + 补 FK 索引

### Sprint C

- 清理乱码与用户可见文案
- 同步文档与 i18n

### Sprint D

- 推进 RAG 升级（rerank 评估 + 引用来源展示）
- 继续增强生成物与沉淀能力

---

## 5. 成功标准

如果下面几件事成立，可以认为技术收敛进入更稳阶段：

- 安全审查清单中的高风险项全部修复
- 项目前后端不再由两个超大文件承载主逻辑
- Web 请求入口真正统一
- 项目链路有可依赖的回归测试
- 主要用户可见文案不再有乱码
- RAG 升级开始从"能检索"走向"能解释、能扩展"
