# AriaAI 技术建议

> 更新日期：2026-04-14
> 说明：基于当前主线代码的现实状态给出技术取舍建议。

---

## 1. 总体判断

近几轮技术工作最明显的进展有三点：

- 聊天链路已经完成一次成功的结构拆分
- Web 与后端的部分契约开始收敛
- 项目空间的业务价值明显增强

因此，当前最重要的技术目标不再是“证明能做出来”，而是“把主链路稳定下来并降低维护成本”。

---

## 2. 当前最值得继续推进的方向

### 2.1 复制聊天拆分的成功经验

`chat.py` 的拆分已经证明方向正确。接下来最值得复用这套策略的对象是：

- `aria-web/src/pages/projects/ProjectDetail.tsx`
- `AriaAI/backend/app/routers/projects.py`

### 2.2 统一 API 与配置来源

现状已经比之前好很多，但仍存在局部绕开统一配置的代码。建议：

- 所有 Web 请求都统一走 `src/config/api.ts`
- SSE、导出和普通请求不要再各自维护独立入口

### 2.3 优先补测试，而不是继续裸重构

聊天已有最小回归测试，这是非常好的起点。下一步应把测试覆盖推进到：

- 项目详情聚合
- notes / todos
- 知识库状态流转
- 设置来源链路

### 2.4 单独做一轮编码与文案治理

这不是“美化问题”，而是可维护性问题。乱码会同时伤害：

- 用户体验
- 文档可信度
- 代码可读性

---

## 3. 当前仍需解决的技术问题

### 3.1 新的复杂度中心已经转移到项目域

聊天拆分完成后，最重的复杂度已经迁移到项目域前后端。

### 3.2 RAG 仍偏 baseline

结构化引用已经有了，但检索策略、过滤和扩展性仍偏基础。

### 3.3 自动化保护不足

当前重构节奏已经快于测试体系增长速度。

---

## 4. 建议实施节奏

### Sprint A

- 拆分 `ProjectDetail.tsx`
- 收口项目聊天统一 API 配置

### Sprint B

- 拆分 `projects.py`
- 补项目主链路测试

### Sprint C

- 清理乱码与用户可见文案
- 同步文档与 i18n

### Sprint D

- 推进 RAG 升级
- 继续增强生成物与沉淀能力

---

## 5. 成功标准

如果下面几件事成立，可以认为技术收敛进入更稳阶段：

- 项目前后端不再由两个超大文件承载主逻辑
- Web 请求入口真正统一
- 项目链路有可依赖的回归测试
- 主要用户可见文案不再有乱码
- RAG 升级开始从“能检索”走向“能解释、能扩展”
