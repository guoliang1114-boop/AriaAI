## 3. 已完成与未完成

### 3.1 已完成

- 项目初始化与基础工程结构
- 路由和登录守卫
- 页面级信息架构
- API 客户端封装
- 聊天页面第一版
- 项目页面第一版
- 技能、知识库、设置页面第一版

### 3.2 正在暴露的问题

- 页面虽然多，但状态管理还偏分散
- 体验和 macOS 端还没有完全对齐
- 长会话、长列表、异常态处理仍需补强
- 当前文档长期落后于代码，容易误判网页端仍未开工

### 3.3 已确认的近期代码问题

- 聊天历史分页存在口径不一致
  - `Chat.tsx` 首屏请求 `limit=3`
  - 但 `hasMore` 首屏判断却使用 `messagesData.length === 30`
- 共享 API 契约还不够稳定
  - macOS 和 Web 都在调用同一后端，但分页、首屏加载、状态刷新策略还没有统一

## 4. 下一阶段目标

网页端下一阶段不建议再追求“多做几个页面”，而应该收敛到三个目标：

### 4.1 目标一：把核心链路跑顺

优先跑顺：

1. 登录
2. 打开项目
3. 发起聊天
4. 查看历史消息
5. 进入知识库 / 技能 / 设置

如果这些链路不稳定，继续加页面价值不大。

### 4.2 目标二：和 macOS 端共享同一套工作台语义

网页端不应该变成一个平行产品。

必须优先保持一致的对象：

- 项目
- 会话
- 消息
- 技能
- 知识文档
- 设置

必须优先保持一致的行为：

- 鉴权
- 分页
- 首屏加载
- 失败提示
- 刷新策略

### 4.3 目标三：形成可持续迭代的前端结构

网页端现在已经过了“随手堆页面”阶段，下一步需要开始收敛：

- 页面内状态与共享状态边界
- API 类型和页面模型的组织方式
- 错误处理规范
- 加载态和空状态规范

## 5. 建议的开发优先级

### P0

- 修复聊天分页口径不一致
- 统一 Web 和 macOS 的核心 API 契约
- 补齐关键页面的加载态、空状态、失败态
- 先把聊天 / 项目 / 登录三条链路联调稳定

### P1

- 收敛页面级状态管理
- 做更稳定的项目详情加载策略
- 补长列表体验
- 收敛设置页和知识库页的交互质量

### P2

- 主题与视觉细节完善
- 更完整的响应式适配
- 进一步抽离复用组件

---

## 6. 与后端的协作要求

网页端开发进入当前阶段后，最重要的不是“接口够不够多”，而是“接口语义够不够稳”。

优先需要后端稳定下来的部分：

- `/auth/*`
- `/chat/conversations`
- `/chat/conversations/{id}/messages`
- `/chat/send`
- `/projects`
- `/projects/{id}/detail`
- `/settings/*`

建议规则：

- 新增分页参数时同步更新两端
- 新增字段时先更新 `types/api.ts`
- 不要让 Web 端和 macOS 端分别推着后端长出两套返回结构

---

## 7. 一句话结论

网页端现在最需要的不是“继续证明它能做出来”，而是：

> **把第一版已经做出来的页面收敛成一个真正可联调、可持续迭代、和 macOS 端一致的 AriaAI 工作台入口。**
