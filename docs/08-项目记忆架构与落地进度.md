# 项目记忆架构与落地进度

更新日期：2026-04-18

适用范围：

- 项目概览页 `AI 项目总结`
- 项目聊天上下文
- 项目级 Skill / 生成物
- 跨项目复用的客户级长期记忆

---

## 1. 背景

AriaAI 已经具备项目详情、聊天、文档、里程碑、待办、财务、知识库和生成物等基础能力，但如果每次都把全量上下文直接喂给模型，会持续遇到几类问题：

- 首字慢
- 成本高
- 容易被 `max_tokens` 截断
- 同一项目在不同页面重复调 AI
- 多个项目之间的客户经验无法沉淀

所以这里需要的不是继续堆 prompt，而是把“原始上下文 -> 结构化记忆 -> 视图摘要”做成分层系统。

---

## 2. 设计目标

1. AI 能基于完整项目事实工作，而不是只看当前页面的一小段数据。
2. 页面侧摘要尽量秒开，避免每次打开都重新调模型。
3. 项目聊天、概览、设置、执行页共享同一份项目记忆，而不是各算各的。
4. 支持多视角摘要，而不是只有一条笼统总结。
5. 在项目层之上沉淀客户层长期记忆，形成跨项目复用。
6. 逐步把记忆构建、摘要预热、失败重试等能力后台化。

---

## 3. 分层设计

### 3.1 第一层：原始上下文层

这是项目和客户的真实业务数据来源，包括：

- 项目基础信息、描述、阶段、成员
- 里程碑、待办、财务流水
- 项目文件与文件摘要
- 项目笔记、聊天沉淀
- 知识库文档
- 客户档案与客户关联项目

特点：

- 信息最全
- 更新最频繁
- 不直接面向最终页面展示

当前代码中的对应能力：

- `build_project_context_data()`
- `build_project_memory_data()`
- `build_client_memory_data()`

### 3.2 第二层：结构化项目记忆层

这是项目级长期记忆，当前挂在 `Project.context_memory_json` 上。

核心字段：

- `project_brief`
- `current_stage`
- `current_objective`
- `recent_progress`
- `key_risks`
- `open_questions`
- `next_actions`
- `important_documents`
- `financial_status`
- `delivery_signals`
- `stakeholder_notes`
- `memory_version`
- `last_updated_at`
- `stale`
- `rebuild_log`
- `_coverage`

其中部分槽位已支持 `ai + pinned` 双层结构，便于后续保留人工固定内容。

当前代码中的对应能力：

- `parse_project_memory()`
- `save_project_memory()`
- `get_project_memory_payload()`
- `mark_project_memory_stale()`

### 3.3 第三层：项目视图摘要层

这是基于第二层记忆按页面或角色生成的摘要层，用于直接面向用户展示。

当前已支持视角：

- `overview`
- `risk`
- `stakeholder`
- `delivery`
- `client-facing`
- `financial`
- `documents`

设计原则：

- 只从结构化记忆出发，不直接重吃原始全量上下文
- 按 `project_id + memory_version + summary_type + language` 缓存
- 常用摘要优先预热
- 支持流式输出与强制刷新

当前代码中的对应能力：

- `build_project_memory_view_prompt()`
- `build_project_summary_from_memory_prompt()`
- `ProjectMemorySummary` 表
- `/projects/{id}/memory/summarize`
- `/projects/memory/warm-summaries-batch`

### 3.4 第四层：客户记忆层

这是客户级跨项目长期记忆，当前挂在 `ClientRecord.client_memory_json` 上。

核心字段：

- `client_profile`
- `decision_patterns`
- `key_contacts`
- `lessons_learned`
- `project_history`
- `sensitive_topics`
- `memory_version`
- `last_updated_at`
- `stale`
- `rebuild_log`
- `source_project_ids`

定位：

- 记录单项目之外的客户级经验
- 为客户范围聊天提供上文
- 为新项目提供更强起点
- 逐步沉淀咨询方法论中的“客户画像 + 历史经验”

当前代码中的对应能力：

- `build_client_memory_data()`
- `parse_client_memory()`
- `save_client_memory()`
- `get_client_memory_payload()`
- `mark_client_memory_stale_by_name()`

## 4. 当前落地状态

### 4.1 总体结论

项目级三层记忆已经完成可用 V1，客户级第四层记忆已经进入系统化管理阶段。

当前系统已经具备：

- 原始数据 -> 结构化项目记忆 -> 多视角摘要 的完整主链路
- 项目记忆缓存、`stale` 标记、异步重建状态、重建日志、来源覆盖
- 项目详情、概览、聊天、设置、系统设置中的项目记忆入口
- 客户记忆的后端模型、API、项目回流、聊天注入、客户详情入口
- 系统设置中的 `Client Memory Manager`
- 客户记忆批量重建能力

### 4.2 项目级已完成

- `Project.context_memory_json`
- `memory_stale / memory_version / memory_updated_at`
- `memory_rebuild_status / memory_rebuild_failed_at`
- `rebuild_log`
- `_coverage`
- `key_risks / open_questions / stakeholder_notes` 的 `ai + pinned` 双层结构
- 项目记忆 API、批量重建、任务队列、摘要预热
- 概览 / 聊天 / Memory / Settings / Milestones / Todos / Notes / Financials / Documents 全部接入
- `Project Memory Manager`

### 4.3 客户级已完成

- `ClientRecord.client_memory_json`
- `client_memory_stale / client_memory_version / client_memory_updated_at`
- 客户记忆重建、批量重建、手动提升项目记忆
- 聊天 `knowledge_scope = client` 时优先注入客户记忆
- 客户详情页入口
- `Client Memory Manager`

## 6. 异步与缓存策略

### 6.1 项目记忆

当前已实现：

- 数据变化后标记 `memory_stale`
- APScheduler debounce 重建
- `idle / queued / rebuilding / failed` 状态
- 常用摘要自动预热
- 预热基础限流、防重、预算、退避重试
- 设置页查看任务队列、取消任务、立即执行

### 6.2 客户记忆

当前仍以同步和手动触发为主：

- 单客户重建
- 批量重建
- 项目记忆手动提升到客户记忆

客户记忆尚未形成完整的后台异步队列闭环。

## 8. 未完成项

### 8.1 部分完成

1. 客户记忆仍以手动重建为主  
虽然客户记忆已经支持系统级管理和批量重建，但目前仍以手动和半自动流程为主，还没有完全做到“自动后台重建 + 自动吸收归档项目经验”的闭环。

2. 客户记忆前端仍偏管理视图  
当前已有 `Client Memory Manager` 和客户详情页入口，但还没有独立 `Memory` 工作页、历史版本查看和面向顾问的多视角摘要工作台。

### 8.2 尚未完成

1. 槽位级增量更新  
当前仍是整包重建，尚未做到“只更新风险 / 财务 / 文档”。

2. 独立记忆主表与历史版本  
项目记忆、客户记忆仍保存在主业务表字段中，没有独立版本表与回滚能力。

3. 更完整的后台任务系统  
还未完全产品化为统一优先级队列、全局预算治理、完善的失败重试与告警、跨项目/跨客户统一监控台。

4. 客户级更强的产品入口  
包括客户详情独立 `Memory` 页面、客户记忆多视角摘要缓存、项目归档后自动提升客户经验、客户级异步状态与队列可视化。
