## 1. 概要

V0.0.4 围绕"**把当下能看见的体验问题与能感受到的连续性问题，一次性收口**"展开，由三条互相支撑的主干 + 一组遗留硬化构成：

| 主干 | 一句话 | 来源 |
|---|---|---|
| **A. Run Harness v1** | 项目对话所有"看得见的过程"统一到一条事件驱动的活动时间线（思考→Skill→工具/任务→交付物） | doc/11 Phase 1 |
| **B. 用户记忆 v1** | AI 跨项目认得"我"——风格/语言/汇报偏好显式可控 | doc/12 Phase 1 |
| **C. 遗留与硬化** | code-review 留下的中小问题、隐患和死代码 | doc/10 |

三条主干互相支撑：Harness 落地后，**所有 run（含记忆写入候选）走同一套事件协议**，Phase 2 的 Memory Candidate 才能自然挂上；用户记忆通过 Run Harness 的 `confirmation_required` 事件来确认"是否记住这条偏好"。

> **不在 V0.0.4**：Memory Candidate/证据/动态召回（Memory Phase 2-4）；AI Run 持久化数据模型（Harness Phase 2）；Tool/Context/Persistence Harness 标准化（Harness Phase 3）；独立聊天页与项目对话统一。见 §6。

## 2. 主干 A：Run Harness v1（最高优先级）

> 来源：[doc/11 §11 Phase 1](./11-Model-Harness产品方案设计.md#phase-1轻量-harness-收口--run-activity-timeline)。
> 用户可感知收益最大，且为后续 Phase 2/3 与记忆 Candidate 打地基。

### 2.1 A1 — Product Run Event v1 + 时间线骨架 + Skill 身份

**后端**
- 定义 Product Run Event v1（doc/11 §8）：`run_started` / `status` / `text_delta` / `step_started` / `step_completed` / `tool_progress` / `task_update` / `confirmation_required` / `artifact_ready` / `message_persisted` / `run_done` / `run_failed`。
- 新增 Event Harness 薄层：把现有内部事件（`tool_executing/result`、`agent_step`、`task_run`、`status`、LLM chunks）映射为 Product Run Event（doc/11 §8 末尾映射表）。
- 流式开头若 `runtime.skill_name` 存在，发 `run_started.skill = {name, id?}`。
- **过渡策略**：旧 stream event 与新 Product Run Event **双发**；feature flag 控制前端消费哪套；可灰度，可回滚（doc/11 §11）。

**前端**
- 接 `streamingSteps` 死代码：消费 `step_started` / `step_completed` / `tool_progress`。
- 新增 `buildActivityTimeline()` 规范化函数 + `ProjectChatActivityTimeline` 组件（doc/11 §9.5）。
- `ChatStreamingMessage`（流式）与 `ProjectChatMessageBubble`（持久化）**共用同一组件**，保证直播/刷新一致。
- 顶部 SkillBanner（仅有 skill 时渲染）。
- 默认折叠策略：进行中展开、完成折叠为单行摘要、可点开复盘（doc/11 §13.2 决策 7）。

**验收**：普通问答无内部进度；Skill 调用顶部显示 Skill 横幅 + 真实工具步骤；流式/刷新一致；事件双发期间异常率 < 1%。

### 2.2 A2 — 后台任务进度内联

**前端**
- 把 `task_update` 灌进同一时间线（kind="durable_task"），按 TaskRun 的 4 步（收集上下文→生成大纲→生成保存→整理交付）实时渲染。
- 「任务」面板保留为详情/历史入口，移除"必须跳到面板看进度"的痛点。

**验收**：复杂任务在对话里直接看到 4 步 + 最终文件；不再需要跳任务面板。

### 2.3 A3 — PPT 生成方式可见/可选

**衔接** 本会话已落地的 `rule:pptx_from_prior_outline` 路由（引用既有大纲→对话模型生成 PPT；冷启动→确定性流水线）。

**前端**
- 在 PPT 触发处加轻量提示或开关："**按我的大纲**" / "**自动生成项目 PPT**"，让生成路径可控、可预期。
- 与时间线衔接：两种路径在时间线中视觉风格一致（task mode），仅来源不同。

**验收**：用户可显式选择生成方式；当前的智能路由作为默认。

## 3. 主干 B：用户记忆 v1

> 来源：[doc/12 §12 Phase 1 + §13 优先级 1-2](./12-记忆系统优化方案.md#phase-1用户记忆-v1)。

### 3.1 范围

- **新增 User Memory 数据结构**（按用户 id 隔离）。字段建议参考 doc/12 §4.3：`communication_style`（写作风格/语气）、`language_preferences`（中/英、术语）、`reporting_preferences`（汇报风格、PPT 默认结构）、`product_role_context`（角色身份）、`explicit_preferences`（显式声明）。
- **"个人信息"设置页**新增"用户偏好"卡：可查看 / 编辑 / 删除每条偏好；显式来源标记（手动 / "记住这个偏好"采纳）。
- **对话内"记住这个偏好"动作**：基于 Harness 的 `confirmation_required` 事件——AI 检测到偏好性发言（如"以后给我用英文回复"）时，弹一张确认卡，用户点"记住"才写入；不自动写。
- **Prompt 注入**：runtime 准备阶段把简短 User Memory（一两段）拼进 system frame。
- **保护边界**（doc/12 §4.4）：用户记忆**只装个人偏好/工作风格/语言**，**不装客户事实和项目业务结论**——后者属客户/项目层。
- **隔离**：与 docs/10 §6 提到的"font_size 全局无用户维度"对齐——用户级设置走同一张表/同一接口（统一 per-user 存储）。

### 3.2 验收

- 用户偏好跨项目生效（在项目 A 设的语言偏好，在项目 B 也生效）。
- 用户可看到、可删每条偏好；删除即时生效。
- 不会自动把客户/项目事实写进用户记忆（防污染，doc/12 §11.1）。
- 偏好确认走 HITAS 路径，确认前不写入。
- 单测覆盖：注入 / 删除 / 防污染 / 跨项目可见。

## 5. 我建议补入 V0.0.4 的项

> 基于这轮会话的代码观察，是 docs/10-12 没明确列、但与三条主干强相关的小增量。

### 5.1 端到端 Skill 执行集成测试（缺口补齐）

- 当前 skill 测试只覆盖**选择**（test_skill_router）、**CRUD/seeding**（test_skills_router）、**`_build_completed_skill_progress` 单测**。**真正端到端的"Skill 选中 → 路由 → 生成 PPT → 交付 → run done"没集成测试**。
- V0.0.4 补 1-2 个 e2e 测试（mock LLM，跑 stream_chat_events 走完一个 PPT skill 轮），断言事件序列与最终 artifact。这次会话已经修了 `rule:pptx_from_prior_outline` + 真流式，趁热把回归网兜上。

### 5.2 Event 协议的 contract 测试

- 主干 A1 的 Product Run Event v1 一旦定型，**用 golden case 锁住事件序列与字段约束**（受 doc/11 §8 字段约束驱动）。
- 价值：后续 Harness Phase 2/3 重构时不会破坏前端兼容。

### 5.3 Run 简单观察性基线

- A1 完成后，按 `display_mode` 统计每天的 run 数、按 `final_status` 统计成功率、按阶段统计平均耗时（**先打日志即可，不上 dashboard**）。
- 这是 Harness Phase 2 "AI Run 数据模型" 的零成本前哨——拿到数据再决定 Phase 2 范围。

### 5.4 docs/10 维护

- V0.0.4 收口后，**清理 docs/10**：把已落地条目移到"已修复"分节，剩余继续作为 backlog。避免遗留事项越积越多失去信号意义。

## 8. 风险与对策

| 风险 | 应对 |
|---|---|
| 主干 A 事件双发期间前端组件分裂 | 严格只让一处消费事件（新组件 + flag），旧路径冻结，禁止穿插 |
| 主干 B 用户偏好被模型过度推断 | 默认只走显式"记住这个偏好"，AI 不直接写；进入用户记忆要 HITAS 确认（doc/12 §11.1） |
| Phase 1 范围蔓延（"顺便也做 Phase 2"） | §6 已显式列出推迟项；评审时若有新增"顺便"项一律重新排期 |
| 时间线在多设备/不同窗口不一致 | A1 验收明确要求"流式/刷新一致"；单测覆盖 `buildActivityTimeline` 输出 |
| Skill 横幅误触发 | `run_started.skill` 只在 `runtime.skill_name` 非空时发；不要从 metadata 反推 |
| 事件双发增加 SSE 带宽 | 仅内部灰度期；M4 完成立即下线旧事件 |
| C2（markdown 去重）误删用户正文 | 保守策略（精确字符串匹配 + 起止边界） + 单测 + 灰度 |
| `font_size` 接入新 per-user 表时旧 localStorage 值丢失 | 加一次性迁移：首次读到新表为空且 localStorage 有值 → 写回 |
