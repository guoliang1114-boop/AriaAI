# 向 Codex 学习：AriaAI 产品提升建议

> 更新日期：2026-05-24  
> 关联文档：[01-产品战略方向](./01-产品战略方向.md)、[05-对话系统设计与规范](./05-对话系统设计与规范.md)

## 1. 背景

Codex 是面向编程任务的 agent，AriaAI 是面向咨询团队的客户关系智能系统。两者领域不同，但 Codex 的产品机制对 AriaAI 有参考价值：

- 任务有明确 workflow 和完成标准。
- 上下文会在长期使用中沉淀为记忆。
- 高风险动作有权限、沙箱和确认。
- 复杂任务可拆解、验证和回放。
- 长对话需要压缩和状态管理。

AriaAI 不应复制 Codex 的编程体验，而应吸收这些机制，服务“会议前 30 秒知道该说什么、该避什么、该推进什么”的北极星场景。

## 2. 可借鉴机制

| Codex 机制 | 含义 | AriaAI 对应 |
|---|---|---|
| Workflow recipe | 每类任务有步骤、标准和验证方式 | Skill、顾问能力目录、task orchestrator |
| Persistent memory | 从历史互动中沉淀偏好、惯例和风险 | 项目记忆、客户记忆、干系人历史 |
| Risk boundary | 按风险决定是否允许执行 | ActionPolicy、ToolAccessPolicy、HITAS |
| Tool trace | 工具调用可观察、可解释 | ChatTrace、工具卡、Action Preview |
| Compaction | 长对话压缩但保留关键事实 | 历史窗口、后续智能压缩 |
| Verification | 完成后验证，不只生成 | Skill verification、交付物校验 |

## 3. 建议一：跨项目经验自动捕获

### 现状

项目记忆和客户记忆已经存在，但客户记忆仍偏手动。项目记忆可以提升到客户记忆，聊天和 Skill 结果也可保存为项目资产，但系统还没有足够主动地从日常行为中抽取客户洞察。

### 建议

在 P4 持久化、项目归档、Skill 保存、干系人更新等时机捕获信号。

可捕获信号：

| 信号 | 示例 | 沉淀目标 |
|---|---|---|
| 客户敏感点 | 对价格、合规、组织调整敏感 | 客户记忆、干系人敏感点 |
| 决策模式 | 需要三周内部预审 | 客户记忆 |
| 沟通偏好 | 喜欢先看数字再讨论方案 | 干系人沟通偏好 |
| 踩坑经验 | 一期延期来自需求频繁变更 | 客户记忆、项目复盘 |
| 有效策略 | 先给决策人向上汇报口径 | 干系人沟通策略 |

### 落地方式

短期用规则和关键词检测，不必先上复杂 LLM 抽取：

- 在 P4 识别“敏感、担心、拍板、审批、预算、合规、延期”等信号。
- 先生成候选，不自动写入长期记忆。
- 让用户在会前简报、项目记忆页或干系人页确认。

### 价值

让 AriaAI 从“用户主动整理记忆”变成“系统主动发现可沉淀资产”。

## 4. 建议二：会前 Briefing 升级为行动剧本

### 现状

`ProjectBriefingTab` 已有 30 秒会前卡，后端有 `/projects/{id}/briefing` 和 `/briefing/refine`。当前简报能聚合 say、avoid、confirm、experience、干系人、待办、里程碑和沟通信号。

### 建议

从信息看板升级为行动剧本。

建议模块：

| 模块 | 内容 | 数据来源 |
|---|---|---|
| 开场方式 | 针对本次干系人的开场话术 | 干系人画像、最近沟通 |
| 议题顺序 | 先讲什么，后讲什么 | 项目阶段、风险、待办 |
| 必须确认 | 本次会议必须拿到的决策或信息 | open questions、里程碑 |
| 避雷区 | 不应触碰的话题和表达方式 | 敏感点、历史经验 |
| 推进动作 | 会后立即执行的动作 | todos、milestones、客户阶段 |
| 来源引用 | 每条建议来自哪里 | 记忆、聊天、文档、干系人历史 |

### 价值

顾问不只是“了解情况”，而是可以直接开会。

## 5. 建议三：HITAS 风险分层

### 现状

修改和删除类操作会进入 HITAS。新建文件通常可以直接执行。这个设计安全，但高频使用时仍可能产生确认疲劳。

### 建议

引入风险分层和用户信任级别。

| 风险等级 | 操作 | 默认处理 |
|---|---|---|
| 低 | 新建文档、生成新 PPT、读取文件 | 自动执行 |
| 中 | 修改草稿、移动文件、追加 Markdown | Action Preview 确认 |
| 高 | 覆盖重要文档、批量改文件 | Action Preview + 明确影响范围 |
| 破坏性 | 删除文件、删除文件夹 | 强确认，保留可恢复删除 |

用户设置：

- `ask-always`：所有中高风险都确认。
- `auto-approve-low`：低风险自动执行。
- `never-auto`：任何写入都确认。

### 价值

在不牺牲安全性的前提下降低确认疲劳。

## 6. 建议四：Skill 多轮迭代

### 现状

Skill 执行偏一次性：选择 Skill、生成结果、保存。咨询工作实际更像“初稿、反馈、改版、定稿”。

### 建议

Skill 增加多轮迭代模型：

1. 第一轮生成初稿。
2. 用户给反馈。
3. 系统基于已有产物增量修改。
4. 每次修改保存版本和 diff。
5. 用户锁定最终版。

需要能力：

- Skill run record。
- artifact version。
- Markdown/Office diff。
- 回滚到指定版本。
- 修改现有文件时走 HITAS。

### 价值

Skill 从“生成器”升级为“交付协作流程”。

## 7. 建议五：工具并行探索

### 现状

复杂项目分析中，读取文件、检查里程碑、查看财务、分析干系人通常串行发生。对用户来说等待时间较长。

### 建议

在只读分析场景中并行收集上下文：

- 子任务 A：读取相关项目文件。
- 子任务 B：汇总里程碑和待办。
- 子任务 C：分析财务和合同金额。
- 子任务 D：整理干系人和客户记忆。

限制：

- 只读任务可并行。
- 写入、修改、删除仍必须串行并受 HITAS 管控。
- 每个并行任务返回结构化摘要，不把原始长文本全部塞回主上下文。

### 价值

提升“全面分析这个项目”类请求的响应速度和信息覆盖。

## 8. 建议六：Skill Verification

### 现状

Skill 能生成交付物，但缺少统一的完成标准和自动验证。

### 建议

为复杂 Skill 增加 `Verification` 清单，并逐步实现自动校验。

示例：

- PPT 是否生成并注册到项目空间。
- 是否包含必需章节。
- 每页标题是否为结论句。
- 是否包含执行摘要、路线图、风险页。
- Excel 是否包含必需 sheet。
- DOCX 是否包含摘要、正文、行动项。

失败处理：

- 可自动修复的，直接进入修复循环。
- 不可自动修复的，返回明确错误和下一步。

### 价值

让 Skill 产出从“看起来完成”变成“达到交付标准”。

## 9. 建议七：对话历史智能压缩

### 现状

大多数模式使用最近 24 条历史。复杂 Skill 或长项目对话可能出现上下文退化。

### 建议

按消息类型压缩历史：

| 消息类型 | 压缩策略 |
|---|---|
| 普通文本 | 最近 3 轮保留完整，更早部分摘要 |
| 工具结果 | 保留结论、文件名、错误、关键数据 |
| HITAS 结果 | 保留 confirmed/rejected 和执行结果 |
| 生成物 | 保留 artifact ID、文件名、摘要 |
| 冗长引用 | 保留来源和关键片段 |

### 价值

降低 token 压力，让长对话仍能理解关键事实。

## 10. 优先级

| 建议 | 优先级 | 原因 |
|---|---|---|
| 跨项目经验自动捕获 | P0 | 直接增强客户关系智能护城河 |
| 会前 Briefing 行动剧本 | P0 | 直接服务北极星场景 |
| HITAS 风险分层 | P1 | 改善高频使用体验 |
| Skill 多轮迭代 | P1 | 更贴近咨询交付流程 |
| Skill Verification | P1 | 提升交付物可信度 |
| 对话历史智能压缩 | P2 | 长对话质量提升 |
| 工具并行探索 | P2 | 性能和体验优化，工程改动较大 |

## 11. 近期落地建议

未来 1-2 个月：

1. 在会前简报中增加“行动剧本”和来源引用。
2. 在 P4 和项目/Skill 保存动作后生成“客户洞察候选”。
3. 在干系人页增加候选更新确认。
4. 为 Office/PDF/提案类 Skill 写入 Verification 清单。

未来 3-4 个月：

1. 增加 Skill run record 和版本历史。
2. 增加 HITAS 风险分层设置。
3. 建立 Skill golden examples 和交付物校验。

未来 5-6 个月：

1. 推进只读工具并行探索。
2. 实现对话历史压缩。
3. 将客户洞察候选闭环到客户记忆和会前简报。
