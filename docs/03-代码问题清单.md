# AriaAI 代码问题清单与优化方案

更新日期：2026-04-15

范围：基于当前 `main` 分支代码重新核对，按真实风险与收益排序。

这份文档不只描述问题，也给出建议的优化方向，方便直接进入排期和执行。

## 1. 总体判断

当前代码并不是“不可维护”，而是已经进入典型的第二阶段：
- 主链路可用
- 项目域功能增长很快
- 结构债务开始集中暴露

当前最核心的问题不是单个 bug，而是三类系统性风险：
- 项目域前后端复杂度持续集中
- 数据库迁移与部署流程不够稳
- 自动化测试与编码治理跟不上迭代速度

## 2. P0：优先立即优化的问题

### 2.1 `ProjectDetail.tsx` 仍然是前端复杂度中心，但已开始拆分

位置：
- `aria-web/src/pages/projects/ProjectDetail.tsx`

现状：
- 主文件仍然较大
- 但这一轮已经把外层布局壳和数据加载开始拆出：
  - `ProjectDetailLayout.tsx`
  - `useProjectDetailData.ts`
- `chat / notes / todos` 的常驻挂载容器已经从主返回结构中抽离到独立布局层

风险：
- 新增一个项目功能，容易影响其他 tab
- 阅读和修改门槛高
- 前端性能、状态一致性和回归风险都集中在这里

目标状态：
- `ProjectDetail.tsx` 只保留页面框架、路由与共享状态编排
- 各 tab 的业务逻辑下沉到独立容器
- 历史遗留的旧布局代码彻底删除

优化建议：
1. 继续删除 `ProjectDetail.tsx` 里残留的旧导航 / 旧返回结构。
2. 再抽离 `files`、`financials`、`members` 的装配逻辑。
3. 把更多项目详情页里的接口请求和状态转换收口到 hooks 或服务层。

建议优先级：最高

### 2.2 `projects.py` 继续承担过多项目域职责

位置：
- `AriaAI/backend/app/routers/projects.py`

现状：
- 文件约 1528 行
- 同时处理项目 CRUD、详情聚合、文档、待办、AI 润色、我的待办等逻辑

风险：
- 一个文件承接太多入口，回归面越来越大
- service 边界不清晰，测试也难拆
- 后续项目域功能继续增长时，会变成新的 `chat.py`

目标状态：
- 路由层只做参数处理和响应格式
- 项目域业务逻辑按子域拆分

优化建议：
1. 先拆成 `project_notes`、`project_todos`、`project_files`、`project_summary` 等子路由或 service。
2. 把 `_todo_dict`、文档读写、模板初始化、AI 润色等逻辑从 router 下沉。
3. 为每个子域补最小回归测试。

建议优先级：最高

### 2.3 PostgreSQL 迁移与真实库状态容易脱节

位置：
- `AriaAI/backend/alembic/versions/*.py`
- 部署流程
- `DEPLOY.md`
- `DEPLOY_SIMPLE.md`

现状：
- 线上已经出现过“表结构存在，但 `alembic_version` 落后”的情况
- 新增字段后，代码和数据库版本不同步会直接导致接口 500

风险：
- 部署成功但功能不可用
- 排障依赖人工经验
- 同类问题会重复发生

目标状态：
- 每次部署后数据库结构与 Alembic 版本一致
- 迁移问题可预检、可恢复、可追踪

优化建议：
1. 把 `alembic upgrade head` 固化到部署步骤。
2. 在部署脚本或发布检查中增加：
   - `alembic current`
   - `alembic upgrade head`
   - 失败即阻断
3. 在部署文档里补一段“stamp 恢复流程”。
4. 后续可以增加一个简单的启动前 schema health check。

建议优先级：最高

### 2.4 项目域自动化测试覆盖仍偏薄

位置：
- `AriaAI/backend/tests/test_chat_flow.py`

现状：
- 测试仍然更偏聊天主链路
- 项目文档、待办、详情聚合、知识范围隔离覆盖不足

风险：
- 项目工作台功能越多，回归风险越高
- 线上问题更容易在部署后暴露

目标状态：
- 项目域关键链路都有最小回归保护

优化建议：
1. 先补以下接口测试：
   - 项目详情聚合
   - todos CRUD 与 `due_date`
   - notes 读取、保存、重命名、删除
   - notes AI 润色与流式输出
   - 项目级知识范围过滤
2. 后续再补前端关键交互测试或轻量 E2E。

建议优先级：最高

## 3. P1：建议本阶段完成的优化

### 3.1 中文编码污染仍有残留

位置：
- 多个前端页面
- 少量后端默认文案
- 历史 docs 文件

现状：
- 近期已经清理过一轮
- 但仍能看到部分乱码字符串或历史污染

风险：
- 影响产品专业感
- 影响模板、文案和注释维护

目标状态：
- 用户可见文案无乱码
- 常用文档和默认模板无乱码

优化建议：
1. 先清理用户可见文案。
2. 再清理默认模板和 docs。
3. 最后处理注释和历史遗留文件。

建议优先级：高

### 3.2 RAG 仍是可用但偏基础的 baseline

位置：
- `AriaAI/backend/app/services/rag.py`
- `AriaAI/backend/app/services/context_builder.py`

现状：
- 已支持项目 / 客户维度过滤
- 当前仍以本地 embedding + 相似度排序为主

风险：
- 数据规模增长后，召回质量和扩展性都会受限

目标状态：
- 检索链路支持更稳定的过滤、排序和可解释性

优化建议：
1. 明确 metadata filter 规则。
2. 评估 rerank。
3. 评估更清晰的向量索引方案。

建议优先级：中高

### 3.3 文档更新需要继续制度化

位置：
- `README.md`
- `docs/*.md`

现状：
- 文档已经追过几轮
- 但代码变化频率仍然很高

风险：
- 新成员理解和真实代码再次脱节

目标状态：
- 每轮关键结构调整都有对应文档更新

优化建议：
1. 大功能合并后同步更新 docs。
2. 部署流程有变化时同步更新部署文档。
3. 架构变化时同步更新总览和架构图。

建议优先级：中高

## 4. 已明显改善的问题

- 聊天主链路已从早期的大路由中拆出一部分职责
- 项目聊天流式输出已经修复
- 项目文档页已统一站内弹窗交互
- 待办已支持截止日期，概述和仪表盘展示已补齐
- 项目聊天默认知识范围已经改成以当前项目为主
- `ProjectDetail.tsx` 已经开始做第一轮前端结构拆分

## 5. 建议执行顺序

### 第一阶段：先稳住结构和部署

1. 拆分 `ProjectDetail.tsx`
2. 拆分 `projects.py`
3. 固化 PostgreSQL / Alembic 部署检查

### 第二阶段：补质量保障

1. 补项目域回归测试
2. 清理用户可见乱码
3. 同步部署文档与架构文档

### 第三阶段：做体验和能力升级

1. 推进下一轮 RAG 升级
2. 继续做项目域模块化
3. 逐步收敛历史遗留文件

## 6. 一个更实用的结论

如果只允许选一个方向先做，最值得先投入的不是新功能，而是：

`拆分 ProjectDetail.tsx + 拆分 projects.py + 固化 Alembic 部署检查`

这是当前最能同时降低开发风险、部署风险和回归风险的一组动作。
