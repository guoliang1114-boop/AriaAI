# AriaAI 代码问题清单与优化方案

更新日期：2026-04-15

范围：基于当前 `main` 分支代码重新核对，按真实风险与收益排序。

这份文档不只描述问题，也给出建议的优化方向，方便直接进入排期和执行。

## 1. 总体判断

当前代码并不是"不可维护"，而是已经进入典型的第二阶段：
- 主链路可用
- 项目域功能增长很快
- 结构债务开始集中暴露

当前最核心的问题不是单个 bug，而是三类系统性风险：
- 项目域前后端复杂度持续集中
- 数据库迁移与部署流程不够稳
- 自动化测试与编码治理跟不上迭代速度

此外，本次全面审查发现了若干安全风险，需独立跟进。

---

## 2. 安全风险（独立分级，优先处理）

### 2.1 JWT 密钥与 API 密钥存储风险

位置：
- `AriaAI/backend/app/core/security.py`
- `AriaAI/backend/app/models/`（LLM provider 配置表）

现状：
- JWT `SECRET_KEY` 在 `.env.example` 中有默认值，若部署时未替换，等同于明文泄露
- 用户配置的 LLM API Key（如 OpenAI、Kimi 等）在数据库中明文存储
- 若数据库泄露，所有用户的 API Key 同时泄露

建议：
1. 启动时检查 `SECRET_KEY` 是否为默认值，若是则拒绝启动
2. 对 API Key 字段使用 Fernet/AES 对称加密存储，只在调用时解密
3. 建立密钥轮换机制的基础设施（即使暂不使用）

建议优先级：**最高（安全）**

---

### 2.2 文件路径遍历风险

位置：
- `AriaAI/backend/app/routers/projects.py`（文件上传/下载路由）

现状：
- 文件路径从请求参数或数据库拼接，若未严格校验，攻击者可构造 `../../etc/passwd` 等路径
- 下载接口未校验文件是否属于当前用户项目

建议：
1. 所有文件路径操作使用 `pathlib.Path.resolve()` 并验证是否在允许目录内
2. 文件下载前校验 `file.project_id == current_user_project_id`
3. 不要将完整服务器路径暴露在响应里

建议优先级：**高（安全）**

---

### 2.3 认证端点缺少速率限制

位置：
- `AriaAI/backend/app/routers/auth.py`

现状：
- 登录、注册接口无请求频率限制
- 密码强度要求较弱（有长度检查，但无复杂度要求）
- 暴力破解无任何阻断机制

建议：
1. 引入 `slowapi` 对 `/auth/login` 设置速率限制（如 10 次/分钟/IP）
2. 密码强度规则至少要求包含大小写 + 数字
3. 连续失败次数超限后临时锁定账户

建议优先级：**高（安全）**

---

### 2.4 `MarkdownRenderer` 的 XSS 风险

位置：
- `aria-web/src/components/` 中 Markdown 渲染相关组件

现状：
- 渲染 AI 输出时使用 `dangerouslySetInnerHTML` 或等效方式
- 若 AI 输出中包含恶意 HTML/JS，可能直接在用户浏览器执行（XSS）
- 攻击路径：恶意提示词 → AI 注入 HTML → 用户浏览器执行

建议：
1. 对 AI 输出先做 HTML sanitize（推荐 `DOMPurify`）
2. 或使用 `react-markdown` + 严格白名单替代原始 HTML 渲染
3. Nginx 层配置 CSP 头增加 `script-src 'self'`

建议优先级：**高（安全）**

## 3. P0：优先立即优化的问题

### 3.1 `ProjectDetail.tsx` 仍然是前端复杂度中心，但已开始拆分

位置：
- `aria-web/src/pages/projects/ProjectDetail.tsx`

现状：
- 主文件仍然较大
- 但这一轮已经把外层布局壳和数据加载开始拆出：
  - `ProjectDetailLayout.tsx`
  - `useProjectDetailData.ts`
- `chat / notes / todos` 的常驻挂载容器已经从主返回结构中抽离到独立布局层

风险：
- 新增一个项目功能，容易影响其他 tab
- 阅读和修改门槛高
- 前端性能、状态一致性和回归风险都集中在这里

目标状态：
- `ProjectDetail.tsx` 只保留页面框架、路由与共享状态编排
- 各 tab 的业务逻辑下沉到独立容器
- 历史遗留的旧布局代码彻底删除

优化建议：
1. 继续删除 `ProjectDetail.tsx` 里残留的旧导航/旧返回结构
2. 再抽离 `files`、`financials`、`members` 的装配逻辑
3. 把更多项目详情页里的接口请求和状态转换收口到 hooks 或服务层

建议优先级：最高

---

### 3.2 `projects.py` 继续承担过多项目域职责

位置：
- `AriaAI/backend/app/routers/projects.py`

现状：
- 文件约 1528 行
- 同时处理项目 CRUD、详情聚合、文档、待办、AI 润色、我的待办等逻辑

风险：
- 一个文件承接太多入口，回归面越来越大
- service 边界不清晰，测试也难拆
- 后续项目域功能继续增长时，会变成新的 `chat.py`

目标状态：
- 路由层只做参数处理和响应格式
- 项目域业务逻辑按子域拆分

优化建议：
1. 先拆成 `project_notes`、`project_todos`、`project_files`、`project_summary` 等子路由或 service
2. 把 `_todo_dict`、文档读写、模板初始化、AI 润色等逻辑从 router 下沉
3. 为每个子域补最小回归测试

建议优先级：最高

---

### 3.3 PostgreSQL 迁移与真实库状态容易脱节

位置：
- `AriaAI/backend/alembic/versions/*.py`
- 部署流程
- `DEPLOY.md`
- `DEPLOY_SIMPLE.md`

现状：
- 线上已经出现过"表结构存在，但 `alembic_version` 落后"的情况
- 新增字段后，代码和数据库版本不同步会直接导致接口 500

风险：
- 部署成功但功能不可用
- 排障依赖人工经验
- 同类问题会重复发生

目标状态：
- 每次部署后数据库结构与 Alembic 版本一致
- 迁移问题可预检、可恢复、可追踪

优化建议：
1. 把 `alembic upgrade head` 固化到部署步骤（已部分完成）
2. 在部署脚本或发布检查中增加 `alembic current` 验证，失败即阻断
3. 在部署文档里补一段"stamp 恢复流程"
4. 后续可以增加一个简单的启动前 schema health check

建议优先级：最高

---

### 3.4 项目域自动化测试覆盖仍偏薄

位置：
- `AriaAI/backend/tests/test_chat_flow.py`

现状：
- 测试仍然更偏聊天主链路
- 项目文档、待办、详情聚合、知识范围隔离覆盖不足

风险：
- 项目工作台功能越多，回归风险越高
- 线上问题更容易在部署后暴露

目标状态：
- 项目域关键链路都有最小回归保护

优化建议：
1. 先补以下接口测试：
   - 项目详情聚合
   - todos CRUD 与 `due_date`
   - notes 读取、保存、重命名、删除
   - notes AI 润色与流式输出
   - 项目级知识范围过滤
2. 后续再补前端关键交互测试或轻量 E2E

建议优先级：最高

## 4. P1：建议本阶段完成的优化

### 4.1 N+1 查询与缺失索引

位置：
- `AriaAI/backend/app/routers/projects.py`（项目列表、详情聚合）
- `AriaAI/backend/app/models/*.py`

现状：
- 项目列表 API 对每个项目单独查询关联客户 / 待办，存在 N+1 风险
- 部分外键字段（`project_id`、`user_id`、`client_id` 在关联表中）缺少数据库索引
- 数据量小时不明显，增长后查询会出现明显劣化

优化建议：
1. 在 SQLModel/SQLAlchemy 查询中使用 `selectinload()` 或 `joinedload()` 预加载关联对象
2. 在 Alembic 迁移中为常用外键字段补 `Index`
3. 重点检查：`todos.project_id`、`knowledge_items.project_id`、`conversations.project_id`

建议优先级：高

---

### 4.2 前端认证状态管理存在脆弱点

位置：
- `aria-web/src/contexts/AuthContext.tsx`（或类似）
- `aria-web/src/api/` 中的请求拦截器

现状：
- JWT token 过期时，UI 可能还显示已登录状态，直到下次请求才触发 401
- 多个并发请求同时收到 401，可能触发多次 logout 流（race condition）
- 没有全局 Error Boundary，React 未捕获异常会导致整个页面白屏

优化建议：
1. 请求拦截器中捕获 401，通过一个全局 flag 防止 logout 被重复触发
2. 增加顶层 `<ErrorBoundary>` 组件，至少在关键页面层级上添加
3. token 快过期时（可从 JWT payload 解析 `exp`）提前静默刷新

建议优先级：高

---

### 4.3 中文编码污染仍有残留

位置：
- 多个前端页面
- 少量后端默认文案
- 历史 docs 文件

现状：
- 近期已经清理过一轮
- 但仍能看到部分乱码字符串或历史污染

风险：
- 影响产品专业感
- 影响模板、文案和注释维护

目标状态：
- 用户可见文案无乱码
- 常用文档和默认模板无乱码

优化建议：
1. 先清理用户可见文案
2. 再清理默认模板和 docs
3. 最后处理注释和历史遗留文件

建议优先级：高

---

### 4.4 RAG 仍是可用但偏基础的 baseline

位置：
- `AriaAI/backend/app/services/rag.py`
- `AriaAI/backend/app/services/context_builder.py`

现状：
- 已支持项目/客户维度过滤
- 当前仍以本地 embedding + 相似度排序为主
- 引用来源在前端无法追溯

风险：
- 数据规模增长后，召回质量和扩展性都会受限
- 用户无法验证 AI 回答依据，影响信任度

目标状态：
- 检索链路支持更稳定的过滤、排序和可解释性
- AI 回答可附带来源引用展示

优化建议：
1. 明确并统一 metadata filter 规则（project_id、client_id、file_type）
2. 评估在结果排序中引入 rerank 步骤
3. 前端展示引用来源片段（文件名 + 段落摘要）
4. 中长期评估 pgvector + PostgreSQL 替代本地 FAISS

建议优先级：中高

---

### 4.5 文档更新需要继续制度化

位置：
- `README.md`
- `docs/*.md`

现状：
- 文档已经追过几轮
- 但代码变化频率仍然很高

风险：
- 新成员理解和真实代码再次脱节

优化建议：
1. 大功能合并后同步更新 docs
2. 部署流程有变化时同步更新部署文档
3. 架构变化时同步更新总览和架构图

建议优先级：中高

## 5. P2：体验与质量优化

### 5.1 文件上传缺少进度反馈

现状：大文件上传时前端没有进度条，用户体验差。  
建议：利用 `XMLHttpRequest.upload.onprogress` 或 axios 的 `onUploadProgress` 反馈进度。

---

### 5.2 localStorage 使用分散，无统一抽象层

现状：多处组件直接读写 `localStorage`，键名无统一常量，容易因拼写差异导致数据读取失败。  
建议：封装统一的 `storage.ts` 工具层，集中管理键名和序列化逻辑。

---

### 5.3 上下文刷新时机不明确

现状：项目上下文（知识库、文件列表）在会话期间不自动刷新，用户上传文件后需手动触发才能在聊天中生效。  
建议：文件上传/删除完成后通过事件或状态更新触发上下文失效和重载。

---

### 5.4 分页支持不完整

现状：项目列表、知识库列表等在数据量增长后无分页或虚拟滚动，会出现性能问题。  
建议：关键列表接口补 `limit/offset` 或 `cursor` 分页，前端对应接入无限滚动或分页控件。

## 7. 建议执行顺序

### 第零阶段：先处理安全风险

1. API Key 加密存储
2. 文件路径遍历防护
3. 认证端点速率限制
4. Markdown XSS 防护（DOMPurify）

### 第一阶段：稳住结构和部署

1. 拆分 `ProjectDetail.tsx`（继续推进）
2. 拆分 `projects.py`
3. 固化 PostgreSQL / Alembic 部署检查

### 第二阶段：补质量保障

1. 补 N+1 查询修复与 FK 索引
2. 补项目域回归测试
3. 修复前端认证 race condition + Error Boundary
4. 清理用户可见乱码

### 第三阶段：做体验和能力升级

1. 推进下一轮 RAG 升级（引用展示 + rerank）
2. 文件上传进度、分页支持等 P2 体验项
3. 逐步收敛历史遗留文件

---

## 8. 实用结论

如果只允许选一个方向先做，最值得先投入的不是新功能，而是：

**安全加固（API Key 加密 + 路径遍历防护）+ 拆分 `ProjectDetail.tsx` + 拆分 `projects.py` + 固化 Alembic 部署检查**

安全问题一旦在生产暴露代价极高；结构问题不解决，后续每个新功能都会叠加风险。
