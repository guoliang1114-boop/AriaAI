## 🆕 最新审查新增发现

### A. 前端仍大量用“项目名称”而不是“项目 ID”做主关联，误绑风险依旧存在
**位置**:
- `AriaAI/AriaAI/AriaAIApp.swift:99`
- `AriaAI/AriaAI/Views/ProjectSpace/ProjectSpaceView.swift:71`
- `AriaAI/AriaAI/Views/ProjectSpace/ProjectSpaceView.swift:131`
- `AriaAI/AriaAI/Views/Projects/ProjectsView.swift:128`
- `AriaAI/AriaAI/Views/Sidebar/SidebarView.swift:28`
- `AriaAI/AriaAI/Views/Chat/ChatView.swift:130`

**问题**:
- 当前多个关键流程仍通过 `project.name` 去反查 API 项目
- 问题已经不是单个页面，而是 `MainWorkbenchView`、项目卡片、侧边栏、工作区、聊天入口一起依赖名称映射
- 一旦存在同名项目，工作区、删除、状态变更、聊天绑定都可能指向错误对象

**影响**:
- 这是“项目工作台”阶段最危险的结构性风险之一
- 产品已经进入多端阶段，继续允许名称充当主键，会放大 macOS / Web / 后端之间的状态错配

**建议**:
- 在前端本地 `Project` 模型中保留稳定的 API ID
- `selectedProject`、`ProjectSpaceView`、顶部 header 都改为 ID 驱动
- 名称只作为展示字段，不再作为主键替代物

### B. `loadAll()` 仍在应用加载期全量拉数据，`loadSkills()` 依旧带 seed / migrate 副作用
**位置**:
- `AriaAI/AriaAI/Services/DataStore.swift:36`
- `AriaAI/AriaAI/Services/DataStore.swift:255`
- `AriaAI/AriaAI/AriaAIApp.swift:159`

**问题**:
- 主工作区启动时仍会触发 `loadAll()`
- `loadSkills()` 里依旧会执行：
  - `/skills/seed-pro`
  - `/skills/migrate-categories`
- 这意味着普通用户打开应用时，仍会把技能初始化逻辑混进首屏加载链路

**影响**:
- 首屏加载链路变重
- 技能模块和主工作区被不必要耦合
- 一旦迁移逻辑失败，会影响整体验证与定位
- 在远端数据库场景下，这类额外往返会进一步放大延迟体感

**建议**:
- 把 seed / migrate 从客户端启动链路移出
- 改成后端启动脚本、后台管理操作或一次性迁移任务
- 客户端 `loadSkills()` 保持纯读取

### C. 调度任务执行链路仍把异步 LLM 调用当同步函数使用，这条功能线大概率没真正跑通
**位置**:
- `AriaAI/backend/app/services/task_runner.py:11`
- `AriaAI/backend/app/services/task_runner.py:40`
- `AriaAI/backend/app/services/claude.py:414`

**问题**:
- `task_runner.py` 直接 `from app.services.claude import complete`
- 但 `claude.complete` 实际是 `async def`
- 当前 `run_task()` 中直接写成 `response = complete(messages, system=system)`，没有 `await`

**影响**:
- 调度任务很可能拿到的是 coroutine 对象，而不是模型输出文本
- 结果写入 `Message.content` 时会出现错误内容或直接抛异常
- 这意味着“定时任务”这条功能链路当前很可能并不真正可用

**建议**:
- 把 `run_task()` 改成明确的异步执行模型
- 或在调度层安全地桥接事件循环，再调用 `await complete(...)`
- 顺手补一条最小可运行测试，至少覆盖“定时任务创建会话并写入 assistant 消息”这条链

### D. 知识库索引仍是进程内后台任务，失败恢复与可观测性偏弱
**位置**:
- `AriaAI/backend/app/routers/knowledge.py:25-48`
- `AriaAI/backend/app/routers/knowledge.py:51-62`

**问题**:
- 文档上传后索引依赖 `BackgroundTasks` + `_index_background`
- `_index_background` 内部用 `asyncio.run(...)` 直接跑索引
- 失败时只把 `vector_status` 标成 `failed`，没有更细的错误信息、重试机制和任务日志

**影响**:
- 小规模阶段可用，但一旦文档变大或任务变多，稳定性和排障成本会上升
- 用户只能看到“失败”，却很难知道是解析失败、embedding 失败还是数据库写入失败

**建议**:
- 给索引任务增加失败原因字段或错误日志落库
- 至少补一个手动重试入口
- 中期把索引从进程内后台任务演进成更清晰的任务执行模型

### E. Web 聊天分页参数与“是否还有更多”的判断不一致，历史消息加载会提前失真
**位置**:
- `aria-web/src/pages/chat/Chat.tsx:124-142`

**问题**:
- 初次加载和向上翻页都写死了 `limit=3`
- 但首屏判断 `hasMore` 时却用了 `messagesData.length === 30`
- 这意味着初始第一页几乎总会被判定为“没有更多消息”

**影响**:
- Web 端长对话历史加载体验会失真
- 刚做出来的分页/虚拟列表价值会被这个判断错误直接抵消
- 这类问题也说明 Web 端虽然页面覆盖面很广，但联调验证还不够扎实

**建议**:
- 统一分页常量，避免 `3 / 30` 双口径
- 把分页参数抽成共享常量
- 至少补一条“长会话向上加载更多消息”的最小回归测试

### F. 鉴权同时放在中间件和依赖里执行，远端数据库场景下会产生重复读写
**位置**:
- `AriaAI/backend/main.py:111-151`
- `AriaAI/backend/app/routers/auth.py:71-90`

**问题**:
- 全局中间件已经会校验 token、查询 `UserToken`、更新 `last_used_at`
- `get_current_user()` 又会再做一遍同样的查询和提交
- 对于需要鉴权的普通业务请求，数据库很容易在一个请求里被重复触发

**影响**:
- 对本地 SQLite 影响有限，但对远端 PostgreSQL 会明显放大延迟
- `last_used_at` 每次请求都 `commit`，会制造额外写压力
- 这和项目当前“感觉联网数据库慢”的体感是相互增强的

**建议**:
- 统一鉴权入口，避免中间件和依赖双重查询
- `last_used_at` 改成抽样更新、延迟更新或低频批量更新
- 至少把“鉴权成功的用户对象”挂到 request state，供下游复用

### 10. 没有请求重试机制
**位置**: `AriaAI/AriaAI/Services/APIClient.swift`

**问题**:
- 网络波动时请求直接失败
- 没有自动重试逻辑

**修复建议**:
```swift
func get<T: Decodable>(_ path: String, retries: Int = 3) async throws -> T {
    for attempt in 1...retries {
        do {
            return try await perform(req)
        } catch where attempt < retries {
            try await Task.sleep(nanoseconds: UInt64(pow(2.0, Double(attempt)) * 1_000_000_000))
        }
    }
    throw APIError.maxRetriesExceeded
}
```

### A. 项目明细聚合接口返回面继续膨胀

**风险**:
- 后续会出现多个入口分别维护上下文

**建议**:
