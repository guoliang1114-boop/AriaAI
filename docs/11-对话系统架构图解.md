## 每一层的设计理念详解

### Layer 1: Policy Guards —— 硬规则给确定性

```
为什么要有这层？
─────────────────
不是所有决策都适合交给 LLM 的概率。

- 身份问答（"你是谁"）→ 100% 确定，不需要 LLM 猜
- 删除文件（"清空记录"）→ 100% 危险，不能 LLM 误判
- 明确写入（"保存为文档"）→ 100% 写入意图，LLM 可能"保守"地不给权限

设计理念：
"身份/危险/明确写入 这些场景，0.1% 的误判率都是不可接受的。
硬规则给确定性，LLM 处理模糊性。"
```

**代码体现：**
- `is_identity_request()`：keyword list 匹配，命中直接返回固定模板
- `_is_destructive_request()`：三重条件（destructive 词 + 对象词 + 非否定语境）
- `detect_action_policy()`：WRITE_TERMS / MODIFY_TERMS 命中直接给权限

---

### Layer 2: Rule-First Short-Circuit —— 省钱

```
为什么要有这层？
─────────────────
LLM 调用有成本（即使是 DeepSeek，也有延迟和 token 费用）。
如果 30% 的对话可以通过规则确定，那就省了 30% 的 LLM 调用。

设计理念：
"能规则确定的，不花 LLM 的钱。
但规则只处理高置信度场景（confidence >= 0.85），
不够确定的就交给 LLM，不硬猜。"
```

**代码体现：**
- `_task_route_for_rules()`：task type 命中且 confidence >= 0.85 → 直接返回
- `is_client_project_portfolio_query()`：33 个 marker 笛卡尔积命中 → 直接返回 portfolio mode
- 低置信度（0.72 default）→ 不 short-circuit，进入 LLM Router

---

### Layer 3: LLM Router —— 语义理解兜底

```
为什么要有这层？
─────────────────
关键词列表是"枚举覆盖"，LLM 是"语义理解"。

- 关键词能覆盖："保存"/"导出"/"创建"
- 关键词覆盖不了："整一份"/"弄一个"/"给我出个数"/"打个表格"
- LLM 能理解：这些都是"创建文件"的意思

设计理念：
"关键词负责常见说法（省成本），LLM 负责长尾说法（保覆盖）。
Router 用便宜模型（DeepSeek），因为意图分类只需要 enum 输出，
不需要主模型的推理能力。"
```

**代码体现：**
- `classify_chat_intent_async()`：Rule 不够确定时，调用 `llm_complete`
- 使用 `INTENT_ROUTER_MODEL = "deepseek-chat"`（低成本）
- Prompt 传 `rule_baseline`：让 LLM 知道规则层的判断，方便分歧检测

---

### Layer 4: Schema + Clamp —— 不要相信 LLM

```
为什么要有这层？
─────────────────
LLM 会胡说。即使 DeepSeek 很便宜，它也可能：
- 输出非法 JSON
- 把 chat_mode 拼错
- 把 "read_only_tool" 升级成 "write_artifact"（幻觉自己有权限）

设计理念：
"LLM 的输出是建议，不是命令。
Schema 校验过滤非法输出，Policy Clamp 防止权限升级。
宁可保守降级（read-only），也不冒险放行（write）。"
```

**代码体现：**
- `_json_object_from_text()`：从文本里捞 JSON，失败就 fallback
- `_coerce_chat_mode()` / `_coerce_action_policy()`：非法值 fallback 到 rule 结果
- `_clamp_policy()`：**核心安全机制**，LLM 提出的 policy 不能超过 rule 层确定的权限
- `_should_rule_override_llm()`：高置信度 rule 与 LLM 分歧时，用 rule

---

### Layer 5: Mode Registry + Policy —— 配置即代码

```
为什么要有这层？
─────────────────
旧架构的痛点：5 套 base prompt 散落在 claude.py / openai_compat.py 的 if-else 里，
改一处影响 4 个路径，很容易改漏。

设计理念：
"任何改动改一张表（MODE_CONFIG），不改散落在 6 个文件里的 if-else。
Mode 决定'剧本'（prompt/model/history/context），
Policy 决定'权限'（能调什么工具）。
两者是正交的：同一个 Mode 下，不同 Policy 给出完全不同的工具集合。"
```

**代码体现：**
- `MODE_CONFIG: dict[ChatMode, ModeConfig]`：所有 mode 配置集中在一处
- `prompts/modes/*.md`：每个 mode 一个独立模板文件
- `prompts/tools/*.yaml`：每个工具的 `required_policy` 独立声明
- `filter_tools_for_policy()`：`Mode 工具池 ∩ Policy 允许 = 实际可用工具`

---

### Layer 6: P0-P4 Phases —— 流式架构兼容

```
为什么分 P0-P4？
─────────────────
流式 SSE 架构下，模型一旦开始生成，就无法"中断重试"。
所以必须分段处理：

- P0：先判断是不是 durable task（生成 PPT/Excel 的多步骤任务）
  → 是 → 直接交给 task_orchestrator，不走正常 chat 流
- P1：模型生成回复，同时检测 tool_use
- P2：执行工具，处理结果
- P3：工具结果回注，模型做 follow-up
- P4：持久化消息、保存 artifact、记录 Trace

设计理念：
"SSE 流式生成是单向的，不能回头。
所以把流程拆成阶段，每个阶段有明确的输入输出契约。"
```

**代码体现：**
- `p0_durable_task.py`：task_orchestrator 早期拦截
- `p1_planning.py`：流式检测 tool_use + truncation 处理
- `p2_tools.py`：执行 + repair + artifact 提取
- `p3_followup.py`：re-follow-up 循环（工具结果再注入）
- `p4_persist.py`：消息持久化 + Trace 记录

---

### Layer 7: ChatTrace + Golden Set —— 可观测防回归

```
为什么要有这层？
─────────────────
旧架构的问题："AI 时灵时不灵"，但开发者不知道哪一步错了。
是 mode 选错？prompt 太长？工具被过滤？模型没调工具？

设计理念：
"每次对话生成一份'审计报告'，记录：
- 选了什么 mode / policy
- 用了哪层决策（rule / llm / fallback）
- 工具为什么被 block
- 每一阶段的耗时

改 prompt / 改路由前先跑 Golden Set，
回归则 block 合并。"
```

**代码体现：**
- `ChatTrace` 模型：PostgreSQL 持久化
- `trace.py`：`build_chat_trace_payload()` + `persist_chat_trace()`
- `chat_diagnostics.py`：`GET /conversations/{id}/trace` 端点
- `tests/golden_chat_set/`：YAML 定义预期行为，pytest 自动验证

## 对比：旧架构 vs 新架构

| 维度 | 旧架构 | 新架构 |
|---|---|---|
| **意图识别** | 33 个 keyword marker 笛卡尔积 | Policy Guard + Rule-First + DeepSeek LLM Router |
| **工具权限** | prompt 堆 MUST/CRITICAL，代码层再丢弃 | Tool YAML 声明 `required_policy`，`filter_tools_for_policy` 统一过滤 |
| **prompt 组织** | 7 层叠加，散落在 5 个 py 文件 | 4 层目标，Prompt-as-Data，独立 md/yaml 文件 |
| **历史处理** | portfolio 路径直接清空历史 | 所有路径保留 history，仅按 mode 决定窗口大小 |
| **可观测性** | 只能靠读日志猜 | ChatTrace 结构化记录 + Golden Set 自动验证 |
| **成本** | 每次对话用主模型 | Router 用 DeepSeek（便宜 20 倍），生成用主模型 |

## 一句话总结每层

> **Policy Guards**：确定性决策，不给 LLM 犯错机会。  
> **Rule-First**：高置信度场景省钱，不浪费 LLM 调用。  
> **LLM Router**：语义理解兜底，覆盖关键词枚举不完的长尾说法。  
> **Schema + Clamp**：LLM 的输出是建议，不是命令——校验它、钳制它。  
> **Mode Registry**：配置即代码，改一处改全局，不再散落 if-else。  
> **P0-P4 Phases**：SSE 流式架构的现实约束，单向流必须分段处理。  
> **ChatTrace**：可观测才能调试，Golden Set 才能防回归。
