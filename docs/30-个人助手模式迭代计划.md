## 1. 背景

AriaAI 当前定位是面向咨询团队的客户关系智能系统，核心抽象是项目 / 客户 / 干系人。但同一套底座（agentic chat、tool calls、RAG、三层记忆、Skill、HITAS 审批、定时任务）完全可以支撑"个人 AI 助手"模式：记住用户本人、处理生活与工作杂事、主动提醒。

本计划的目标不是另起一个产品，而是在现有架构上做加法，让 AriaAI 同时服务好"咨询交付"和"个人助手"两种场景。

## 2. 现状盘点

### 2.1 已有能力（对照个人助手需求）

| 个人助手需要 | AriaAI 现状 |
|---|---|
| 多轮对话、流式输出 | ✅ 有（SSE 聊天，项目/工作区双 scope） |
| 工具调用 | ✅ 有（`backend/app/tools/`：Markdown/Office/PDF/文件生成） |
| 长期记忆 | ✅ 三层：用户记忆 v1、项目记忆、客户记忆 |
| 知识检索 | ✅ 有（文档上传→解析→embedding→检索） |
| 高风险操作确认 | ✅ 有（HITAS：服务端 pending action + 确认卡） |
| Skill/工作流复用 | ✅ 有（`skills/` + DB Skill + 质量门禁） |
| 定时任务 | ✅ 有（APScheduler + 任务面板） |
| 交付物生成 | ✅ 有（PPT/Word/PDF，artifact ready 事件） |

## 3. 差距分析

| 差距 | 说明 |
|---|---|
| 缺"个人"一等公民概念 | 核心抽象是项目/客户/干系人；个人助手需要 user scope 成为默认工作区，而不是挂靠在项目下 |
| 工具偏办公交付 | 现有工具围绕 PPT/Word/PDF/文件；缺生活类工具：邮件、日历、天气、提醒、网页搜索 |
| 没有移动端 | 只有 Web；手机浏览器可用，但非原生体验 |
| 用户记忆 v1 刚落地 | 偏好/风格可记，但缺少跨生活场景的长期个人画像沉淀机制 |

## 4. 迭代路线

### Phase 1：先用起来（不写代码，1 周）

1. 登录 https://aria.d2cgo.co/，用项目聊天做日常问答
2. 建一个"个人"项目，把偏好、工作方式写入用户记忆
3. 导入常用文档进知识库，验证 RAG 问答质量
4. 记录缺失能力，形成 Phase 2 需求清单（目标 ≥5 条再动代码）

### Phase 2：补个人助手能力（按需，每项以天计）

按优先级建议：

- [ ] **生活类工具**：Gmail 搜索/发信、日历读写、天气查询、定时提醒
  - 工具注册走现有 `backend/app/tools/` 规范；发信等写操作必须进 HITAS 确认流
- [ ] **个人工作区模式**：新增 user scope 默认工作区，记忆/对话/知识召回默认围着 user 转，不强制建项目
- [ ] **PWA 支持**：成本最低的"移动端"，手机可安装、离线壳；原生 app 以后再议
- [ ] **模型策略**：日常问答走便宜模型（DeepSeek/Kimi），复杂任务走 Claude；按任务类型路由

### Phase 3：跟进 V0.0.5 知识库

按 `14-V0.0.5知识库开发方案.md` 实施：Knowledge Source → Ingestion → Retrieval → Scope（user/project/client/workspace/skill），PPT/PDF/Word 优先，pgvector。个人助手的知识（个人文档、方法论）走 user scope 接入。

## 5. 待决策

1. **私有化**：当前仓库公开；个人助手涉及私人数据，建议个人相关功能走私有 fork，主仓库保持开源干净。
2. **Phase 2 范围**：先用一周再定，还是现在就锁定做哪几项？

## 6. 验收标准

- Phase 1：连续使用一周，需求清单 ≥5 条
- Phase 2：每项独立可验收——"问今天有没有会"真去查日历再回答；提醒事项到点推送
- 全程：不破坏现有咨询交付链路；所有写操作走 HITAS；`docs/` 变更先行（本仓库协作规范）
