# 向 Codex 学习：AriaAI 产品提升建议

> 创建日期：2026-05-23
> 适用范围：产品规划、Skill 体系演进、对话系统优化
> 调研对象：OpenAI Codex（CLI + App + IDE + Cloud）产品设计

---

## 1. 背景

AriaAI 的定位是**咨询团队的客户关系智能系统**，护城河在于"客户关系上下文积累得有多深、多准、多自动"。Codex 是 OpenAI 的通用编程 agent，虽然领域不同，但其在**工作流编排、记忆持久化、风险分层、并行执行**等方面的设计理念，对 AriaAI 的产品演进有直接参考价值。

本文档不是技术对比，而是从 AriaAI 的产品定位出发，分析 Codex 的哪些交互模式和产品机制可以借鉴，以更好地服务"顾问在客户会议前 30 秒打开 AriaAI，看到该说什么、该避什么、该推进什么"这个北极星场景。

---

## 2. Codex 核心设计理念

| 理念 | 说明 | AriaAI 对应 |
|------|------|------------|
| **Workflow Recipe** | 每个任务有明确的步骤、完成标准和验证方法 | Skill 体系 |
| **Memories** | 自动从历史会话提取偏好/惯例/陷阱，跨线程持久化 | 项目/客户记忆系统 |
| **Subagents** | 主 agent 保持上下文，派生并行 subagent 处理探索/分析 | P0-P4 流水线 |
| **Sandbox + Auto-review** | 多级沙箱 + 自动审查替代人工确认 | HITAS 确认系统 |
| **Compaction** | 长对话自动压缩历史，保留关键上下文 | 24 条消息窗口 |

---

## 3. 产品建议

### 3.1 跨项目经验自动捕获

> 直接增强核心护城河"越用越强"。

**现状**：项目记忆是项目级的，客户记忆需要手动"提升"。产品策略中提到"行为触发捕获"是护城河之一，但当前实现还不够自动。

**借鉴**：Codex 的 Memories 系统自动从历史会话提取偏好、惯例、陷阱，后台异步更新，不阻塞当前会话。用户不需要手动管理记忆。

**建议**：

在 P4 持久化阶段，自动检测并捕获以下类型的经验：

| 信号类型 | 触发条件 | 沉淀目标 |
|---------|---------|---------|
| 风险信号 | 用户提到"这个客户对价格敏感" | `client_memory.sensitive_topics` |
| 决策模式 | 用户多次选择"先做 MVP 再迭代" | `client_memory.decision_patterns` |
| 踩坑记录 | 工具执行失败或用户修正了 AI 输出 | `client_memory.lessons_learned` |
| 干系人洞察 | 用户提到"张总其实更在意对上交代" | `client_stakeholder.notes` |

捕获后在下一次 Briefing 中自动引用，形成"每次交互都沉淀为客户资产"的复利效应。

**产品价值**：实现"越用越强"的复利效应，让每次项目交互都沉淀为客户资产。

---

### 3.2 会前 Briefing 升级为行动剧本

> 直接服务"30 秒见客户"北极星场景。

**现状**：`ProjectMeetingBriefing` 聚合了项目记忆、客户记忆、干系人、待办、里程碑，生成 `say/avoid/confirm/experience` 卡片。但这是静态信息，缺少动态行动建议。

**借鉴**：Codex 的 workflow 会根据上下文动态生成具体步骤。例如"修 bug"recipe 不只是分析问题，而是给出"reproduce → diagnose → patch → verify"的具体行动链。

**建议**：

Briefing 从"信息看板"升级为"行动指南"：

| Briefing 模块 | 内容 | 数据来源 |
|--------------|------|---------|
| **开场** | 基于干系人笔记生成个性化寒暄建议 | `stakeholder_notes` |
| **核心议题** | 基于风险和待办生成 3 个必须讨论的点 | `key_risks` + `next_actions` |
| **避雷区** | 基于敏感话题和踩坑记录生成要避免的话题 | `sensitive_topics` + `lessons_learned` |
| **推进项** | 基于待解决问题和交付信号生成需要对方决策的事项 | `open_questions` + `delivery_signals` |
| **后续动作** | 基于当前阶段生成会议后应该立即做的事 | `current_stage` |

每个行动项都有数据来源引用（来自哪次对话、哪个项目、哪个干系人的观察）。

**产品价值**：让 Briefing 从"信息看板"升级为"行动指南"，真正实现"30 秒准备好见客户"。

---

### 3.3 HITAS 风险分层

> 减少确认疲劳，提升高频使用流畅度。

**现状**：所有 `MODIFY_EXISTING_FILE` 和 `DESTRUCTIVE_ACTION` 都需要人工确认。在高频使用场景下，确认疲劳明显。

**借鉴**：Codex 的 Auto-review 用 reviewer agent 自动评估操作风险，低风险自动批准，高风险才需人工。有 circuit breaker 防止循环拒绝。

**建议**：

对 HITAS 增加风险分层：

| 风险等级 | 操作示例 | 处理方式 |
|---------|---------|---------|
| 低风险 | 追加内容到新文档、生成新 PPT | 自动批准 + 静默执行 |
| 中风险 | 修改现有文档、覆盖文件 | 显示预览 + 一键确认 |
| 高风险 | 删除文件、删除文件夹 | 必须人工确认 + 二次确认 |

风险评估基于**操作类型 + 目标对象**：

- 新建文件 = 低风险
- 修改"草稿"状态的文档 = 中风险
- 修改"已发布"状态的文档 = 高风险
- 删除任何文件 = 高风险

支持用户设置"信任级别"：`auto-approve-low` / `ask-always` / `never-auto`。

**产品价值**：减少确认疲劳，让顾问在高频使用场景下更流畅。

---

### 3.4 Skill 多轮迭代

> 让 Skill 更贴合咨询协作流程。

**现状**：Skill 执行是一次性的——用户选择 Skill，填写模板，AI 生成文档，结束。如果用户想修改，需要重新开始。

**借鉴**：Codex 的 workflow 支持多轮迭代。例如"原型设计"recipe 支持"design → tweak → refresh → tweak"的紧密循环。

**建议**：

Skill 执行支持多轮迭代模式：

1. **第一轮**：AI 生成初稿
2. **用户反馈**："第二章太长了，精简一下" / "加上竞争分析章节"
3. **AI 增量修改**：基于初稿进行修改，而非重新生成
4. **版本历史**：每轮修改都保留 diff 记录，支持回退到任意版本
5. **锁定交付**：最终版本可以"锁定"为正式交付物

**产品价值**：让 Skill 从"一次性生成"升级为"协作迭代"，更贴合咨询工作的实际流程。

---

### 3.5 工具并行探索

> 提升综合分析场景的响应速度。

**现状**：P2 工具执行是串行的。当用户问"分析这个项目的风险和进展"时，读取项目文档、分析里程碑、检查财务数据是顺序执行的。

**借鉴**：Codex 支持并行 subagent，探索/测试/分析可并发执行，返回摘要而非原始输出。

**建议**：

在 `project_deep_dive` 模式下，当用户问综合性问题时，并行执行多个读取工具：

- 一个 subagent 读取项目文档
- 一个 subagent 分析里程碑状态
- 一个 subagent 检查财务数据
- 一个 subagent 查看干系人笔记

每个 subagent 返回结构化摘要，主 agent 合并后生成综合分析。

**注意**：不适用于写操作——生成文档、修改文件等仍需串行 + HITAS 确认。

**产品价值**：让"给我做个全面分析"从"等 30 秒"变成"等 5 秒"，提升顾问的使用体验。

---

### 3.6 Skill 验证步骤

> 让 Skill 从"生成文档"升级为"交付合格的咨询产出"。

**现状**：Skill 是 `system_prompt + user_template + tools_definition_json` 的配置记录，执行后生成文档。但缺少验证步骤——用户不知道生成的 PPT 是否真的覆盖了所有要求的章节。

**借鉴**：Codex 的每个 workflow recipe 都有明确的"完成标准"和"验证方法"。例如"修 bug"recipe 要求 Codex "re-run the repro steps after the fix"。

**建议**：

在 Skill 定义中增加 `verification_steps` 字段。例如 `digital-strategy` Skill 执行后，自动验证：

- 25 页 PPT 是否生成成功
- 是否包含 5 个必要章节（诊断→现状→目标→差距→治理）
- 是否有执行摘要页

验证失败时自动触发修复循环，而非让用户手动检查。

**产品价值**：让 Skill 从"生成文档"升级为"交付合格的咨询产出"，更贴合 `Deliverable-First` 原则。

---

### 3.7 对话历史智能压缩

> 让长对话保持高质量的上下文理解。

**现状**：固定取最近 24 条消息作为历史。长对话（如一个复杂的 Skill 执行过程）可能出现上下文退化。

**借鉴**：Codex 有 compaction 机制，当上下文过长时自动压缩历史。保留关键上下文，压缩中间输出。

**建议**：

实现对话历史智能压缩，按消息类型区分策略：

| 消息类型 | 压缩策略 |
|---------|---------|
| `tool_result` | 保留结论，压缩原始输出 |
| `text` | 保留最后 3 轮完整，更早的用摘要替代 |
| `confirmation` | 只保留最终结果（confirmed/rejected） |

在 prompt assembler 中注入压缩后的摘要，而非原始消息。

**产品价值**：让长对话（如复杂的 Skill 执行）保持高质量的上下文理解。

## 4. 优先级总结

| 方向 | 产品维度 | 优先级 | 理由 |
|------|---------|--------|------|
| 跨项目经验自动捕获 | 客户关系智能 | 🔴 高 | 直接增强核心护城河"越用越强" |
| 会前 Briefing 行动剧本 | 北极星场景 | 🔴 高 | 直接服务"30 秒见客户"场景 |
| HITAS 风险分层 | 日常使用体验 | 🟡 中 | 减少确认疲劳，提升高频使用流畅度 |
| Skill 多轮迭代 | 交付物质量 | 🟡 中 | 让 Skill 更贴合咨询协作流程 |
| 工具并行探索 | 响应速度 | 🟡 中 | 提升综合分析场景的体验 |
| Skill 验证步骤 | 交付物质量 | 🟢 低 | 当前 Skill 种类还不多，后续再加 |
| 对话历史智能压缩 | 长对话质量 | 🟢 低 | 24 条窗口对多数场景够用 |

---

## 5. 落地建议

### 短期（1-2 个月）

1. **跨项目经验自动捕获**：在 P4 持久化阶段增加轻量级信号检测（关键词匹配 + 规则），不需要 LLM 参与
2. **HITAS 风险分层**：基于操作类型 + 目标对象的规则引擎，不需要复杂的 ML 模型

### 中期（3-4 个月）

3. **会前 Briefing 行动剧本**：在现有 Briefing 基础上增加行动建议模块，需要 prompt 工程
4. **Skill 多轮迭代**：需要前端 UI 支持版本历史和增量修改，后端支持 diff 计算

### 长期（5-6 个月）

5. **工具并行探索**：需要重构 P2 工具执行为支持并行的架构
6. **Skill 验证步骤**：需要 Skill 定义模型扩展 + 验证逻辑实现
7. **对话历史智能压缩**：需要 LLM 参与的摘要生成，成本较高
