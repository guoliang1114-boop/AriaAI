# 项目对话问题根因分析

> 创建日期：2026-05-20
> 版本基准：V0.0.2，post-commit 4f427fe（含 a130f49 Capability Protocol、chat 模块拆分）
> 范围：项目内对话 `/projects/{id}/chat`（也适用于工作台对话）
> **改造规范见**：[10-对话系统设计规范.md](./10-对话系统设计规范.md)（单一信源，所有改动先改 spec 再改代码）

## 0. 现状速查（基于 a130f49 之后）

- ✅ **task-type 路由已是 LLM Router + Rule-First**：[task_orchestrator.py:452 `route_project_task_request`](../AriaAI/backend/app/services/task_orchestrator.py) 决定一条用户消息是否升级为可恢复 Task（生成 PPT/Word/Excel/PDF/Markdown 交付物）；包含 JSON schema 输出、置信度合并、分歧日志。在 [p0_durable_task.py](../AriaAI/backend/app/services/chat/phases/p0_durable_task.py) 已接入 chat 主链路。
- ✅ **Capability Protocol 已落地**：`ConsultingCapability` + `CREATE_TEXT_ARTIFACT_STEPS` 等步骤定义把"客户会议准备"等结构化交付物从纯 chat 抽离为多步骤任务。
- ✅ **chat_streaming.py 已拆分**：`services/chat/` 包含 13 个模块（runtime、workflow、phases/p0-p4、state、sse、tool_repair 等）。
- ⚠️ **chat-mode 路由仍是关键词**：`is_client_project_portfolio_query` / `is_workspace_project_inventory_query` / `_user_requested_project_markdown_write` 等判断决定"用哪套 prompt、清不清历史、用哪个模型"，仍未接入 LLM Router。
- ⚠️ **System prompt 7 层叠加 + 5 套 base prompt 分支** 仍然存在。
- ⚠️ **PROJECT_MARKDOWN_TOOL_PROMPT** 的 MUST/CRITICAL 工具教学仍在 system prompt 里。

**因此下面 4 个根因主要描述的是"未被 Capability Protocol 覆盖的 chat 主路径"，而非 task-type 路由。**

---

## 摘要

用户报告项目对话存在三类反复出现的问题：

1. **AI 理解不到用户意思** —— 同一意图换个说法就走错路径
2. **AI 乱调用工具** —— 没让生成文件却调用 `generate_*`，或说要写却不真写
3. **回复格式和期待不一样** —— 同一个项目今天回表格、明天回散文，或突然失忆

经过完整链路审阅（runtime / context_builder / chat phases / prompt 模板），定位到这不是模型问题，而是**架构层面的脆弱性**：后端用关键词匹配决定整条对话剧本，且 prompt 在"逼模型用工具"和"代码层压制工具"之间互相拉扯。

## 2. 根因 1：意图识别**双轨制**，chat-mode 这一轨仍靠关键词

### 症状映射

"AI 理解不到我的意思" —— 同一意图说法不同走完全不同代码分支。

### 双轨现状

| 路由维度 | 当前实现 | 状态 |
|---|---|---|
| **task-type 路由**（是否创建可恢复任务 / 生成 PPT-Word-Excel-PDF-MD 交付物） | LLM Router + Rule-First（[`task_orchestrator.route_project_task_request`](../AriaAI/backend/app/services/task_orchestrator.py)），P0 阶段已接入 | ✅ 已是最佳实践 |
| **chat-mode 路由**（用哪套 prompt / model / 历史窗口） | 关键词匹配（[`query_classifiers.py`](../AriaAI/backend/app/services/context_builder/query_classifiers.py) + [`runtime._is_standalone_fast_path`](../AriaAI/backend/app/services/chat/runtime.py)） | ❌ 仍是脆弱关键词 |

**修法不是再建第二个 Router，而是把 task_orchestrator 的 Router 抽象成通用 IntentRouter，chat-mode 路由复用同一个服务**（见 [10-§3](./10-对话系统设计规范.md#3-intent--mode-决策)）。

### 证据

**`is_client_project_portfolio_query` / `is_workspace_project_inventory_query`**（[query_classifiers.py:12-118](AriaAI/backend/app/services/context_builder/query_classifiers.py)）：

```python
return any(marker in text for marker in all_project_markers) \
   and any(marker in text for marker in summary_markers)
```

- `all_project_markers`：16 个中英文 marker（"全部项目"/"所有项目"/"projectportfolio"…）
- `summary_markers`：17 个 marker（"项目情况"/"汇总"/"风险"/"summary"…）
- **必须两组各命中至少一个**，才进入 portfolio 路径

**`_is_standalone_fast_path`**（[runtime.py:75-84](AriaAI/backend/app/services/chat/runtime.py)）：

字符长度 ≤280、无 project_id、无 RAG、无 portfolio 关键词 → 强制切换到 `moonshot-v1-8k`（8k context、max 1536 token）。

**`_user_requested_project_markdown_write`**（[chat_tools.py:60-125](AriaAI/backend/app/services/chat_tools.py)）：

```python
hard_write_terms = ("保存到", "保存为", "存到", "写入", "新建", "创建", "导出", ...)
document_terms = ("文档", "文件", "markdown", "报告", "材料", "清单", ...)
write_verbs = ("生成", "制作", "整理一份", "做一份", "更新", "修改", ...)
# 命中规则：hard term OR (write_verb AND document_term)
```

3 组关键词的笛卡尔积判定"用户到底想不想写文件"。

### 为什么是根因

- 自然语言写法上千种，关键词列表注定漏掉大半
- 同一意图被分类到不同路径，后端选不同 prompt、不同 model、不同历史窗口
- 路径一旦选错，下游所有阶段都按错的剧本演
- **关键词分类失败的代价被无声转嫁给下游兜底逻辑**

## 3. 根因 2：System Prompt 在自相矛盾

### 症状映射

- "AI 乱调用工具" —— 没让生成文件却调用 `generate_*`
- "AI 说要更新文件但没真写" —— 调用被代码层丢弃

### 证据 A：项目对话的工具教学 prompt 写得像在吵架

[constants.py:13-31](AriaAI/backend/app/services/context_builder/constants.py) 的 `PROJECT_MARKDOWN_TOOL_PROMPT` 会注入到**每一次项目对话**，无论用户在问什么：

```
CRITICAL: ... you MUST call `update_project_markdown_document` ...
ABSOLUTELY DO NOT output tool_use JSON as plain text ...
BREAK THE PATTERN: After receiving a tool_result, ... you MUST call ...
STOP READING LOOP: If you have already read the target file, do NOT read more files ...
MAXIMUM 2 READS: When asked to correct a file, read AT MOST 2 files ...
```

5 处 ALL-CAPS 警告、7 个 MUST/MUST NOT。每一条都是历史 bug 的化石（模型把 tool_use 当文本输出过、无限读文件过、跨 turn 不调用工具过）。这种 prompt 本身在**反复 prime 模型去用工具**，包括用户根本没要求写文件的场景。

### 证据 B：然后又用代码层压制它

[p1_planning.py:26-34](AriaAI/backend/app/services/chat/phases/p1_planning.py)：

```python
def _should_accept_tool_use(block: dict, req: SendMessageRequest) -> bool:
    if tool_name == PROJECT_MARKDOWN_TOOL_NAME \
       and not _user_requested_project_markdown_write(req.content):
        logger.warning("[P1] ignored unrequested project markdown write tool call ...")
        return False
```

也就是：**prompt 鼓励它调，模型真调了，代码又关键词判定"用户没想写"然后偷偷丢掉**。日志写 "ignored"，用户看到的是"AI 说要写但没写"。

### 证据 C：模型把 tool_use 当文本输出，所以又写兜底解析

[tool_repair.py:8-58](AriaAI/backend/app/services/chat/tool_repair.py) `try_extract_tool_use_json` 和 `extract_tool_use_json_blocks` 专门做"从输出文本里捞 `{"type":"tool_use"...}` JSON 块"。

这是**模型不会区分"该用工具语义"和"该用文本语义"**的典型症状，根因是：
- 用户没明示让生成文件，但 prompt 在催 → 模型纠结之下把 tool 调用写成 markdown 文本
- skill prompt + project prompt + identity prompt + 工具教学 prompt 一叠加，模型 attention 分散

### 证据 D：工具参数也要修补

三个修补层：
- [tool_repair.py:104-122](AriaAI/backend/app/services/chat/tool_repair.py) `repair_project_office_tool_input` 补 `file_type` / `file_name` / `title` / `sheets`
- [p2_tools.py:39-58](AriaAI/backend/app/services/chat/phases/p2_tools.py) `_repair_project_markdown_tool_input` 补 `action` / `mode`
- `chat_artifacts._repair_digital_strategy_ppt_tool_input` 修 PPT 工具输入

模型经常给出不完整的工具参数，代码层在打补丁。

### 为什么是根因

不是模型乱，是系统**同时给它三种相互拉扯的信号**：
- Prompt：你必须用工具
- 关键词过滤：但你又不能在用户没说时用
- 工具 schema：参数复杂，少给一个就废

## 4. 根因 3：5 套 base prompt + 强制清空历史

### 症状映射

- "格式和期待不一样" —— 同一个项目今天表格、明天散文
- "AI 突然忘了上下文" —— 上句聊的事下句被遗忘

### 证据 A：根据关键词在 5 套 system prompt 里切

[claude.py:544-594](AriaAI/backend/app/services/claude.py) 的 `build_system_prompt` 根据 `project_context` 前缀决定 base prompt：

| 触发条件 | base prompt 风格 |
|---|---|
| `# Client Project Portfolio Context` | "MUST use ... as source of truth ... start with exact matched project count, then provide complete inventory table with one row for every listed project" |
| `# Workspace Project Inventory Context` | "do not say only a partial snapshot is available ... Start with the exact project count, then provide a complete inventory table" |
| `# 工作台全局数据` | 中文，要求"如有逾期里程碑或高风险项目，应主动提示" |
| 普通项目 context | "briefly summarize the key project status proactively" |
| 无 context | "elite AI consultant ... provide precise, structured analysis" |

`project_context` 的前缀完全由**根因 1 的关键词分类**决定。用户没办法预期"今天 AI 会用哪套剧本"。

### 证据 B：portfolio 路径会清空整段对话历史

[runtime.py:276-277](AriaAI/backend/app/services/chat/runtime.py)：

```python
if has_client_portfolio_context or has_workspace_inventory_context:
    api_messages = [{"role": "user", "content": req.content}]
```

走 portfolio / inventory 路径时，对话历史**被一次性丢光**，只保留当前这一条消息。

用户感受：刚才让 AI 记住 X，下一句问 Y，AI 完全忘了 X。

### 证据 C：上下文层数过多，模型 attention 被稀释

实际跑一次项目对话，模型看到的 system prompt 大致是 7 层：

```
1. identity_rules                 (~30 行，"我是 AriaAI" 介绍模板)
2. base prompt                    (~5 行，由关键词分类决定的 5 套之一)
3. skill prompt                   (可能 100+ 行，来自 skill 定义)
4. skill briefing 补丁            (~3 行，"Use the project/client context below...")
5. PROJECT_MARKDOWN_TOOL_PROMPT   (~30 行，工具教学，含 7 个 MUST/CRITICAL)
6. project_context                (Scope Guard + 基本信息 + 干系人 + 项目记忆 + 笔记 + 里程碑 + 待办 + 文件清单 + 文件全文 + 财务 + 制品，可达数千字)
7. rag_context                    (RAG 检索片段)
```

7 个层次叠在一起，每层都有自己的格式要求。Claude / Kimi 在长 prompt 里 attention 倾向往末尾移，**真正的用户消息反而是 prompt 里最不显眼的那一行**。

## 5. 根因 4：意图分类失败的代价被堆在 phase 兜底里

整个系统是"先大胆做、错了再修"的策略：

```
关键词分类 (runtime.py)
    ↓ 选错路径会无声切到错误模型/丢历史
build_chat_context (chat_context.py)
    ↓ 选错会触发或漏掉 portfolio context
P1 planning (p1_planning.py)
    ↓ _should_accept_tool_use 丢掉"不该调用"的工具
    ↓ extract_tool_use_json_blocks 兜底"该用工具却写成文本"
P2 tools (p2_tools.py)
    ↓ 三层 _repair_*_tool_input 补参数
P3 followup (p3_followup.py)
    ↓ 再来一轮 tool_use 检测 + 参数修补
```

每一层都在为前一层的错误买单，但用户从外面看就是"AI 怎么时灵时不灵"。

## 6. 最佳实践对照

四个根因对应的工业界做法（详细规范见 [10-对话系统设计规范.md](./10-对话系统设计规范.md)）。

| 根因 | 反模式（现状） | 最佳实践 | 参考来源 |
|---|---|---|---|
| **根因 1：chat-mode 路由仍靠关键词** | `query_classifiers.py` 用 33 个 marker 的笛卡尔积判定 portfolio/inventory；task-type 已是 LLM Router 但 chat-mode 没复用 | **五层管道**：Policy Guards → Rule-First → LLM Router → Schema 校验 → fallback。硬规则给确定性决策，LLM 处理模糊场景，两者并存 | Anthropic Cookbook；本仓库已有的 `route_project_task_request` |
| **根因 2：prompt 逼 + 代码压制工具** | 30 行 MUST/CRITICAL 教学 prompt + `_should_accept_tool_use` 关键词丢弃 | **Tool descriptions + ActionPolicy 双重防护**：调用规则只写在 tool description（消除 prompt 噪声）；权限校验由 ActionPolicy 决定（消除关键词散落）；不再有"prompt 逼 + 代码压制"的拉扯 | Anthropic Function Calling Best Practices；ActionPolicy 双轴模型 |
| **根因 3：5 套 base prompt + 清历史** | `build_system_prompt` 里 5 个 elif 分支 + portfolio 路径 `api_messages = [当前消息]` | **Mode + Policy 双轴显式化**：`ChatMode` 决定"剧本"，`ActionPolicy` 决定"权限"，叠加在已有 P0-P4 架构之上，配置即代码，历史窗口统一保留 | Cursor 的 Cmd-K/Chat/Composer 模式；状态机模式 |
| **根因 4：兜底逻辑分散** | 每个 phase 都有 `_repair_*_tool_input` + 文本兜底解析 | **重构 + 可观测**：散落关键词收敛到 `policy_guards.py` 唯一信源；流式架构下保留中性默认值兜底，但所有 repair 记入 ChatTrace；改动前跑 Golden Set | LangSmith trace；OpenAI evals |

**贯穿性最佳实践 1：Prompts as Data** —— 所有 prompt 从 `.py` 字符串挪到 `prompts/` 目录的独立文件（YAML / Markdown），非工程师可改、可 review、可 A/B、可版本化。参考实现：Anthropic prompt library、LangChain prompt hub。

**贯穿性最佳实践 2：Policy 与 Router 双层** —— Policy（硬规则）和 IntentRouter（软分类）并存。身份问答、危险操作、明确写入意图这些反而需要硬规则给**确定性决策**；模糊的 mode 归类才交给 LLM Router。**关键词不是要被消灭，而是要从散落补丁收敛到唯一 Policy 层。**

**贯穿性最佳实践 3：ActionPolicy 双轴权限** —— 不再用 ChatMode 单一维度决定"能调什么工具"。新增 ActionPolicy 枚举（DIRECT_ANSWER / READ_ONLY_TOOL / WRITE_ARTIFACT / MODIFY_EXISTING_FILE / DURABLE_TASK / DESTRUCTIVE_ACTION），与 ChatMode 形成双轴，工具实际权限 = Mode 工具池 ∩ Policy 允许。这精确解决了"用户问风险结果生成 MD 文件"的核心漏洞（PROJECT_DEEP_DIVE 默认 Policy = READ_ONLY_TOOL，写工具需明确意图升级）。详细矩阵见 [10-§2.5](./10-对话系统设计规范.md#25-actionpolicy)。

**与已有架构的兼容性**：
- 改造不应推倒 P0-P4 Phase 架构（[services/chat/phases/](../AriaAI/backend/app/services/chat/phases/)）
- 改造不应绕过 task_orchestrator 的 Capability Protocol，而是把"是否升级为 Task"作为 ActionPolicy 的一个枚举值（`DURABLE_TASK`）
- 流式 SSE 架构下，"schema 拒绝 + 模型重试"无法纯粹实现，需要保留**中性默认值兜底**（不是关键词推断）

## 8. 验证方法

每个改造完成后，建议以下方法验证收益：

### 7.1 影子模式对比

新分类器/新 prompt 上线时，先在影子模式跑（不影响用户），并行记录新旧路径的：
- 命中的 intent / context_mode
- 是否触发 `_should_accept_tool_use` 拦截
- 是否触发 `extract_tool_use_json_blocks` 兜底
- 输出长度、tool_use 数量

跑 100 条真实对话后看胜率再切换。

### 7.2 黄金集

整理 20-30 条历史对话作为黄金集，包含：
- 应该走 portfolio 但走错的
- 应该写文件但没写的
- 调了工具但没调对的

每次改造跑一次黄金集，看通过率。

### 7.3 用户验证（最重要）

回到 [02-技术债与行动清单.md 第 4 节](./02-技术债与行动清单.md#4-待办事项--产品验证下周开始) 的方案：找 1 个种子顾问连续用 1 周，每周聊 15 分钟，问：

- 这周哪个时刻 AI 对话帮到你？
- 哪个时刻它没理解你？（**这是本次改造要消除的体验**）
- 哪个时刻它做了你没让它做的事？（**这是工具拉扯问题**）

## 9. 一句话总结

**项目对话不是"AI 不行"，而是后端在用脆弱的关键词匹配决定整条对话剧本，且 prompt 在『逼模型用工具』和『代码层压制工具』之间拉扯。** 修法不是再加更多 MUST/CRITICAL，而是把意图识别交给 LLM、把 prompt 模板压扁、把对话历史在所有路径都保留。

**下一步行动**：按照 [10-对话系统设计规范.md](./10-对话系统设计规范.md) 的 **M2 → M1 → M3a → M3b → M4** 路线图执行（注意顺序：Tool description 重构最先做，因为风险最低收益最直接；ActionPolicy 双轴权限在 M3a 引入，是最关键的架构增益）。总周期 5.5-6.5 周。
