## 0. 执行摘要

V0.0.5 的知识库建设应围绕“咨询经验资产化”展开，而不是做一个通用文档聊天工具。

本版建议采用：

```text
PPT/PDF/Word 优先
  + 模块化单体
  + 异步 worker
  + Postgres / pgvector
  + 对象存储抽象
  + Run Harness 接入
```

第一版必须解决：

- 多年咨询资料可以导入。
- PPT/PDF/Word 可以抽取文本。
- 文档可以生成摘要、标签、chunk 和 embedding。
- 项目对话和 Skill 可以按权限召回知识。
- 回答可以展示引用来源。
- 文件处理不阻塞主应用。

第一版不解决：

- 完整知识协作编辑器。
- 完整 AnythingLLM 复刻。
- 知识图谱。
- 自动脱敏。
- 自动写入客户记忆。
- 重型微服务化。

## 1. 文档定位

本文是 AriaAI v0.0.5 的知识库开发方案，目标是定义 Aria 原生知识系统的第一版边界。

这里的知识库不是一个独立的“文档聊天工具”，而是服务于 Aria 的项目、客户、Skill、用户记忆和交付流程。

核心定位：

```text
普通 RAG 工具：跟文档聊天
Aria 知识系统：让知识参与项目工作
```

V0.0.5 不追求复刻 AnythingLLM、Notion 或 Obsidian，而是先建立 Aria 自己的 Knowledge Source / Ingestion / Retrieval / Scope 基础。

## 2. 为什么 v0.0.5 做知识库

v0.0.4 重点是 Run Harness v1 和用户记忆 v1，解决“AI 如何稳定工作”和“AI 如何记住用户偏好”。

v0.0.5 应该继续补上第三块地基：

> AI 在项目中工作时，能稳定使用团队方法论、客户资料、行业研究、历史交付物和个人知识。

当前 Aria 已有：

- 项目文件。
- 项目记忆。
- 客户记忆。
- Skill。
- RAG 演进方案。
- 项目对话。

但还缺少一个统一的知识层来回答：

- 这份知识属于谁？
- 这份知识适用于哪个客户、项目或 Skill？
- 这份知识能不能被项目对话召回？
- 这份知识能不能用于生成 PPT、报告、会前准备？
- 这份知识是否能进入项目记忆或客户记忆？
- 这份知识更新后如何重新索引？

## 3. 产品边界

### 3.1 做什么

V0.0.5 做 Aria 原生知识系统 v1：

- 支持知识源接入。
- 支持 PPT / PDF / Word 优先导入，Markdown 作为方法论和 Obsidian/Git 知识源的补充格式。
- 支持基础 metadata。
- 支持 chunk / embedding / index。
- 支持 user / project / client / workspace / skill scope。
- 支持项目对话和 Skill 按 scope 召回知识。
- 支持引用来源展示。
- 支持手动同步和重建索引。

### 3.2 不做什么

V0.0.5 不做：

- 完整 Obsidian 替代品。
- 完整 AnythingLLM workspace 产品。
- 富文本知识编辑器。
- 双向同步。
- 实时文件监听。
- 复杂知识图谱。
- 自动组织知识沉淀。
- 高级 RAG 调参 UI。
- 多向量库配置 UI。
- 大规模权限矩阵。

## 4. 与外部工具的关系

### 4.1 Obsidian

Obsidian 适合作为个人知识生产工具。

Aria 不替代 Obsidian，而是支持从 Obsidian vault 或 Markdown 文件夹导入知识。

建议边界：

```text
Obsidian：写作、整理、双链、个人知识维护
Aria：导入、索引、召回、关联项目/客户/Skill、用于交付
```

第一版只需要支持：

- Markdown 文件。
- YAML frontmatter。
- `#tag` 标签。
- 文件夹路径。
- `[[双链]]` 保留为文本。

不做实时双向同步。

### 4.2 AnythingLLM

AnythingLLM 适合作为参考实现或 PoC 工具。

可借鉴：

- workspace 隔离。
- 文档上传和索引流程。
- developer API 思路。
- 本地 RAG 体验。

不建议：

- 将 AnythingLLM 作为 Aria 的核心知识层。
- 让 Aria 的客户、项目、Skill、记忆模型依赖 AnythingLLM workspace。

原因：

```text
AnythingLLM 抽象：workspace + documents + chat
Aria 抽象：user + client + project + skill + memory + artifact + permission + source
```

### 4.3 Markdown + Git

Markdown + Git 适合作为 Aria 知识源的长期标准底座。

优点：

- 简单。
- 可版本控制。
- 可 review。
- 与 Skill 文档、方法论文档、模板文档天然兼容。
- 不绑定某个知识工具。

建议 v0.0.5 优先支持 Markdown 文件夹 / Git repo 风格结构。

## 5. 核心概念

> 本节定义概念模型。精确的 SQLModel 字段定义见 [附录 A.2](#a2-数据模型精确定义)。

### 5.1 Knowledge Source

知识源表示一批知识从哪里来。

示例：

```text
Obsidian Vault
Git Repo
Local Folder
Manual Upload
Project Space
Client Document Library
Skill Reference Folder
```

建议字段：

```json
{
  "id": 1,
  "name": "Consulting Playbook",
  "source_type": "markdown_folder",
  "scope_type": "workspace",
  "scope_id": null,
  "owner_user_id": 1,
  "sync_mode": "manual",
  "include_patterns": ["**/*.pptx", "**/*.pdf", "**/*.docx", "**/*.md"],
  "exclude_patterns": [".obsidian/**", "node_modules/**"],
  "tags": ["consulting", "methodology"],
  "status": "active"
}
```

### 5.2 Knowledge Document

知识文档表示被导入和管理的原始文档。

字段建议：

```json
{
  "id": 1,
  "source_id": 1,
  "title": "数字化战略方法论",
  "file_name": "digital-strategy.md",
  "file_type": "markdown",
  "path": "strategy/digital-strategy.md",
  "content_hash": "sha256",
  "metadata_json": {},
  "scope_type": "skill",
  "scope_id": "digital-strategy",
  "status": "indexed"
}
```

### 5.3 Knowledge Chunk

知识块是检索单元。

字段建议：

```json
{
  "id": 1,
  "document_id": 1,
  "chunk_index": 0,
  "heading_path": ["数字化战略", "诊断框架"],
  "content": "......",
  "token_count": 420,
  "embedding_model": "text-embedding-3-small",
  "embedding_ref": "vector-id",
  "metadata_json": {}
}
```

### 5.4 Knowledge Scope

知识必须有业务身份。

建议 scope：

| Scope | 说明 | 示例 |
|---|---|---|
| `user` | 个人知识，只服务当前用户 | 个人笔记、个人方法论 |
| `project` | 项目知识，只服务某项目 | 项目资料、项目专属背景 |
| `client` | 客户知识，服务该客户下项目 | 客户历史材料、复盘 |
| `workspace` | 团队通用知识 | 方法论、模板、行业资料 |
| `skill` | Skill 专属知识 | Skill references、checklist |
| `global` | 系统级通用知识 | 公共说明、产品帮助 |

## 6. 数据流

### 6.1 导入流程

```text
用户创建 Knowledge Source
  ↓
选择文件 / 文件夹 / 上传文档
  ↓
解析 metadata
  ↓
抽取文本
  ↓
生成 Knowledge Document
  ↓
切分 chunk
  ↓
生成 embedding
  ↓
写入向量索引
  ↓
标记 indexed
```

### 6.2 召回流程

```text
用户问题 / Skill 请求 / 会前准备
  ↓
Run Harness 判断 mode / policy / scope
  ↓
Knowledge Retrieval 选择可用 scope
  ↓
向量检索 + metadata filter
  ↓
可选 rerank
  ↓
返回 top chunks + source refs
  ↓
注入 prompt
  ↓
回答中展示引用来源
```

### 6.3 与记忆系统关系

知识库和记忆不是同一件事。

| 类型 | 作用 |
|---|---|
| Knowledge | 外部或团队资料，作为证据和方法论 |
| Project Memory | 当前项目的结构化长期状态 |
| Client Memory | 客户长期经验和关系判断 |
| User Memory | 用户偏好和工作方式 |
| Skill Knowledge | Skill 的方法论和交付标准 |

原则：

- 知识可以成为记忆的来源。
- 记忆必须保留来源。
- 知识更新不应自动重写记忆，除非经过 Memory Candidate 或明确重建。

## 8. 检索策略

> 本节定义产品层面的检索策略。AI 开发代理的强制约束见 [附录 A.6](#a6-检索策略约束)。

### 8.1 第一版策略

第一版采用混合检索：

- 向量相似度（70% 权重）+ PostgreSQL tsvector 全文匹配（30% 权重）
- 查询扩展：使用同义词表扩展 2-3 个查询变体，分别检索后合并去重
- 结果不足 fallback：如果 top_k 中 relevance < 0.6 的结果不足 3 条，自动扩大 scope 到上一级
- metadata filter by scope
- 引用来源返回

建议默认参数（与附录 A.6 一致）：

```text
top_k = 8
chunk_size = 800 tokens（软切分上限，优先按 heading 层级切分）
chunk_overlap = 100 tokens（仅在软切分时使用）
relevance_threshold = 0.6
```

### 8.2 Scope 优先级

项目对话中建议优先级：

```text
explicit selected knowledge
  ↓
project knowledge
  ↓
client knowledge
  ↓
skill knowledge
  ↓
workspace knowledge
  ↓
user knowledge
```

注意：用户记忆不应作为事实知识检索，它影响表达方式和偏好。

### 8.3 引用展示

> 2026-08-23 Harness 基线：项目/Skill 对话已经使用 `KnowledgeEvidenceManifest v1` 为实际进入模型上下文的 chunk 分配稳定 `K*` 引用键；回答只展示实际使用且能回指的来源，未知/缺失引用进入完成质量检查。检索原文不会写入 Message、Trace 或 Run Output 元数据，Artifact 仅保存 Evidence Manifest 摘要。

回答中应至少能展示：

- 文档标题。
- 文件路径。
- scope。
- chunk heading。
- 上传/更新时间。

示例：

```text
引用来源：
1. 数字化战略方法论.md / strategy/digital-strategy.md
2. 客户A历史项目复盘.pdf / client/A/review.pdf
```

## 9. 权限与安全

> 本节定义权限原则。可执行的权限过滤代码见 [附录 A.5](#a5-权限实现必须可执行)。

### 9.1 权限原则

> 2026-08-23 Harness 基线：旧版 `KnowledgeDocument` 的自动检索和显式 `rag_doc_ids` 已共享 `ProjectMember` 范围过滤，猜测其他项目/客户文档 ID 不再能扩大 Prompt 上下文；新知识源模型继续使用 `knowledge_permissions.py` 的 source 级权限检查。

- 用户知识只对本人可见。
- 项目知识继承项目访问权限。
- 客户知识继承客户访问权限。
- workspace 知识对团队可见。
- skill 知识对使用该 Skill 的用户可见，但仍要遵守 workspace 权限。

### 9.2 防污染原则

- 外部文档不能直接写入用户记忆。
- 知识内容不能自动进入客户记忆。
- 项目知识不能跨客户泄漏。
- 客户知识不能默认进入全局知识。
- 检索结果必须按权限过滤后再进入 prompt。

### 9.3 Prompt Injection 风险

知识文档属于非用户输入，应视为不可信内容。

防护：

- 文档内容只能提供事实和上下文。
- 文档不能覆盖系统规则。
- 文档不能授予工具权限。
- 高风险工具仍走 HITAS。
- prompt 中明确标记 retrieved knowledge 为 untrusted source content。

## 13. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 范围膨胀成 AnythingLLM 复刻 | 发布延期 | 坚持只做 Aria 原生知识 v1 |
| 文档解析质量不稳定 | 检索答案差 | v1 先抓 PPT/PDF/Word 的文本、标题、页码/slide，复杂图表后置 |
| 权限过滤遗漏 | 数据泄漏 | scope filter 必须有测试 |
| 知识污染记忆 | 长期记忆错误 | 知识只作为来源，不自动写记忆 |
| Prompt injection | 模型被文档误导 | retrieved content 标记为不可信 |
| chunk 参数不佳 | RAG 召回差 | 保留 reindex，后续评估优化 |
| 用户误以为知识库是编辑器 | 产品预期偏差 | UI 文案明确“导入和检索”，不是协作编辑 |

## 14. 开发建议

建议按 4 个 PR 包推进：

1. **后端数据模型 + ingestion**
   - source/document/chunk。
   - PPT/PDF/Word 抽取。
   - chunk。
   - indexing status。

2. **Embedding + search**
   - embedding provider。
   - vector index。
   - scope filter。
   - citation response。

3. **前端知识库管理**
   - source 列表。
   - 上传。
   - reindex。
   - 搜索测试。

4. **项目对话 / Skill 集成**
   - Run Harness 事件。
   - prompt 注入。
   - 引用展示。
   - 权限测试。

## 15. 成功标准

v0.0.5 成功的标志不是“做了一个知识库页面”，而是：

- Aria 能吃进团队已有知识。
- 知识能按用户、项目、客户、Skill 归属。
- 项目对话能使用知识库并给出来源。
- Skill 能使用方法论知识生成更可靠交付物。
- 知识不会污染用户记忆、客户记忆和项目记忆。
- 后续 Obsidian、Git、Notion、Drive 都可以作为 connector 接入。

最终目标：

```text
知识不是被存起来，而是参与项目工作。
```

## 16. 技术架构设计

### 16.1 架构选择

v0.0.5 建议采用：

```text
AI-Native Modular Monolith
  = 模块化单体
  + 异步任务队列
  + 多 worker 进程
  + 对象存储
  + Postgres / pgvector
  + Run Harness
```

不建议 v0.0.5 直接做完整微服务。

原因：

- 当前用户规模和并发不需要微服务治理。
- 知识库真正的压力来自文档解析、OCR、embedding 和索引，不来自 HTTP API。
- 这些重任务更适合通过 worker 异步执行，而不是服务间 RPC。
- 保持一个代码仓库和一套业务模型，能降低开发、部署和调试成本。

推荐部署形态：

```text
Frontend
  ↓ HTTP/SSE
backend-api
  ├── Project / Client / User / Skill / Memory / Knowledge 模块
  ├── Chat Run Harness
  ├── Retrieval Module
  └── Job Orchestrator

Redis Queue
  ├── extract_document
  ├── understand_document
  ├── chunk_document
  ├── embed_chunks
  ├── generate_preview
  └── cleanup_temp_files

Workers
  ├── knowledge-worker
  ├── embedding-worker
  ├── preview-worker
  └── scheduler-worker

Storage
  ├── Postgres：业务元数据、权限、任务状态
  ├── pgvector：向量检索
  ├── Object Storage：原始文件、抽取文本、预览、中间产物
  └── Redis：队列、锁、短期状态
```

### 16.2 为什么不是微服务

完整微服务会引入：

- 服务发现。
- 服务间认证。
- API versioning。
- 分布式 tracing。
- 跨服务事务。
- 网络超时和熔断。
- 多服务部署编排。
- 本地调试复杂度。

v0.0.5 暂时不需要这些成本。

更轻的方式是：

```text
同一个 backend 代码库
同一个 Postgres
不同运行进程角色
通过队列、数据库和对象存储协作
```

这不是传统单体，因为重任务已经异步化；也不是完整微服务，因为 worker 不暴露 RPC API。

### 16.3 进程角色

建议按角色拆运行进程：

| 进程 | 职责 |
|---|---|
| `backend-api` | HTTP API、项目/客户/对话、权限、状态查询、Run Harness |
| `knowledge-worker` | PPT/PDF/Word 文本抽取、OCR 调度、文档摘要、标签、案例抽取 |
| `embedding-worker` | chunk embedding、向量写入、reindex |
| `preview-worker` | Office/PDF 预览转换，按需生成预览文件 |
| `scheduler-worker` | 定时任务、失败重试、临时文件清理、索引健康检查 |

这些进程可以先部署在同一台服务器，也可以未来分散到多台机器。

关键要求：

- job payload 不传本地绝对路径。
- worker 通过 `document_id` 和 `storage_key` 读取文件。
- 所有状态写数据库。
- 所有大文件和中间产物放对象存储。
- worker 必须无状态、可重复启动、可横向扩展。

### 16.4 进程之间如何通信

进程之间不做频繁 RPC，而通过三类共享基础设施协作：

```text
Redis Queue：分发任务
Postgres：共享状态和权限
Object Storage：共享文件和中间产物
```

文档上传流程：

```text
用户上传 PPT/PDF/Word
  ↓
backend-api 保存原始文件到 object storage
  ↓
backend-api 创建 KnowledgeDocument(status=uploaded)
  ↓
backend-api 投递 extract_document job
  ↓
knowledge-worker 消费 job
  ↓
worker 从 Postgres 读取 metadata
  ↓
worker 从 object storage 读取原始文件
  ↓
worker 抽取文本、生成摘要、标签、chunk
  ↓
worker 写回 Postgres / object storage
  ↓
worker 投递 embed_chunks job
  ↓
embedding-worker 写 pgvector
  ↓
KnowledgeDocument(status=indexed)
```

前端获取进度：

```text
Frontend
  ↓ poll / SSE
backend-api
  ↓
Postgres document status + event log
```

worker 不直接通知前端，也不需要暴露 HTTP 服务。

### 16.5 Job Payload 协议

job payload 应只包含轻量标识：

```json
{
  "job_type": "extract_document",
  "document_id": 123,
  "source_id": 8,
  "requested_by_user_id": 1,
  "trace_id": "trace_abc",
  "attempt": 1
}
```

禁止在 job payload 中传：

- 本地绝对路径。
- 大段文本。
- 文件二进制。
- 用户不可见的权限绕过参数。

### 16.6 状态机

Knowledge Document 建议使用明确状态机：

```text
uploaded
  ↓
extracting
  ↓
extracted
  ↓
understanding
  ↓
chunking
  ↓
embedding
  ↓
indexed
```

失败状态：

```text
failed_extract
failed_understand
failed_chunk
failed_embedding
failed_preview
```

可选状态：

```text
queued
retrying
cancelled
archived
needs_ocr
unsupported
```

每一步应写事件日志：

```json
{
  "document_id": 123,
  "event_type": "extract_completed",
  "status": "extracted",
  "message": "Extracted 48 slides.",
  "duration_ms": 18320,
  "created_at": "2026-05-28T00:00:00"
}
```

### 16.7 存储设计

数据库只存 metadata，不存大文件。

对象存储建议路径：

```text
knowledge/
  originals/{document_id}/{content_hash}.{ext}
  extracted/{document_id}/text.json
  extracted/{document_id}/slides.json
  chunks/{document_id}/chunks.json
  previews/{document_id}/page-{n}.png
  previews/{document_id}/preview.pdf
  temp/{job_id}/...
```

建议字段：

```text
original_storage_key
extracted_text_storage_key
chunks_storage_key
preview_storage_key
content_hash
file_size_bytes
page_count
slide_count
token_count
chunk_count
```

### 16.8 磁盘与资源估算

以 20 个用户、并发不高、10G 原始文档为基准，这套架构可以支撑。

粗略空间估算：

| 类型 | 估算 |
|---|---:|
| 原始 PPT/PDF/Word | 10G |
| 抽取文本 | 0.5G-2G |
| chunk JSON / metadata | 0.5G-3G |
| pgvector 向量 | 1G-5G+ |
| 预览 PDF/图片 | 0G-20G，取决于是否按需生成 |
| OCR / LibreOffice 临时文件 | 需要定期清理 |

建议初始机器：

```text
4-8 vCPU
16-32 GB RAM
500GB SSD
Postgres + pgvector
Redis
backend-api
2-4 个 worker
local object storage 或 MinIO
```

最低也应预留 200G 磁盘，推荐 500G SSD 起步。

### 16.9 资源控制策略

必须控制：

- 首次批量导入限速。
- OCR 只对扫描件或无文本页执行。
- 预览按需生成，不默认全量高清预览。
- embedding 批处理、限流、可重试。
- chunk 不要太碎，避免向量数量爆炸。
- content hash 去重。
- 临时文件定时清理。
- 大文件设置上限。
- 每个 worker 限制并发数。

建议默认参数（与 §8.1、附录 A.6 一致）：

```text
chunk_size = 800 tokens（软切分上限，优先按 heading 层级切分）
chunk_overlap = 100 tokens（仅在软切分时使用）
top_k = 8
relevance_threshold = 0.6
embedding batch size = provider-dependent
OCR concurrency = low
preview generation = on demand
```

### 16.10 多 AI 分工

知识库可以使用不同 AI 处理不同环节，但必须由 Aria 的 pipeline 编排，不让各 AI 直接写核心状态。

建议分工：

| 环节 | 适合模型 | 说明 |
|---|---|---|
| 文档摘要 | 成本较低的通用模型 | 生成文档级摘要 |
| 自动标签 | 成本较低模型 | 行业、服务线、文档类型 |
| 案例抽取 | 推理更强模型 | 提取业务问题、方案、经验、风险 |
| 方法论抽取 | 推理更强模型 | 抽象可复用框架 |
| OCR 纠错 | 多模态或 OCR 专用服务 | 只处理扫描件或图片页 |
| embedding | embedding 专用模型 | 不使用聊天模型 |
| rerank | rerank 模型或轻量 LLM | 后续版本再做 |

模型调用原则：

- 每一步产出结构化 JSON。
- 每一步保存 raw output 和 parsed output。
- 每一步可重试。
- 每一步有 token 和成本记录。
- 高成本模型只用于高价值环节，不用于所有 chunk。

### 16.11 检索架构

v0.0.5 第一版不拆 `retrieval-service`，做成 backend 内部模块。

```text
Chat / Skill
  ↓
Retrieval Module
  ↓
Postgres metadata filter
  ↓
pgvector similarity search
  ↓
permission filter
  ↓
citation builder
  ↓
prompt context
```

检索必须带 scope 和权限：

```text
workspace_id
owner_user_id
client_id
project_id
skill_id
source_id
confidential_level
document_type
industry
service_line
```

禁止先召回所有 chunk 再依赖 prompt 约束模型不泄漏。

### 16.12 多机部署能力

虽然 v0.0.5 可以单机多进程部署，但架构必须天然支持多机。

单机形态：

```text
Server A
  backend-api
  knowledge-worker
  embedding-worker
  preview-worker
  scheduler-worker
  postgres
  redis
  object storage
```

多机形态：

```text
Server A：backend-api
Server B：knowledge-worker
Server C：embedding-worker
Server D：Postgres / pgvector
Server E：Redis
Server F：Object Storage / MinIO
```

迁移条件：

- API 请求变慢。
- 文档处理堆积。
- OCR/preview 占用 CPU。
- embedding 成本和限流需要独立治理。
- 检索 QPS 上升。

### 16.13 未来拆服务顺序

如果未来确实需要拆服务，建议顺序：

1. `knowledge-worker` 独立部署。
2. `embedding-worker` 独立部署。
3. `retrieval-service` 从 backend 内部模块拆出。
4. `knowledge-service` 从主 backend 拆出。
5. pgvector 迁移到 Qdrant/Milvus。
6. 对象存储迁移到 S3/云厂商 OSS。

不要一开始引入 Kubernetes、Kafka、服务网格或复杂微服务治理。

## 17. 技术验收补充

除第 12 节验收外，v0.0.5 还应满足：

- [ ] 上传大文件不会阻塞 HTTP 请求。
- [x] worker 挂掉后过期 lease 可由 scheduler 回收并重试。
- [x] 重复 job 不会生成重复 chunk 或重复模板提取记录。
- [ ] 同一 content hash 的文件可以去重。
- [ ] job payload 不包含本地绝对路径。
- [ ] object storage 可以从本地实现平滑切换到 MinIO/S3。
- [ ] 10G 原始文档导入可以分批执行，不影响普通项目对话。
- [ ] 临时文件有自动清理策略。
- [ ] OCR 和 preview 默认限流。
- [ ] 检索只使用 `indexed` 状态的知识。
- [ ] 权限过滤在 prompt 注入前完成。

## 18. 咨询经验知识库专项设计

本节用于说明 Aria 知识库如何服务“多年咨询案例、客户资料、PPT、PDF、Word 和团队经验”的真实场景。

### 18.1 专项定位

用户本地已有大量客户案例、项目资料、历史 PPT、PDF、Word 报告和多年咨询经验。知识库的目标不是简单把这些文件上传后做文档问答，而是让 AI 理解这些资料，抽取其中的方法论、案例结构、风险经验、交付模板和客户洞察，并在小伙伴日常工作中自动调用。

核心目标：

```text
把多年咨询资料
  ↓
转化为可检索、可引用、可复用、可治理的经验资产
  ↓
服务项目对话、Skill、会前准备、方案生成和客户记忆
```

一句话定位：

> Aria 知识库不只是资料仓库，而是咨询经验引擎。

### 18.2 典型资料类型

| 类型 | 格式 | 典型内容 | 主要价值 |
|---|---|---|---|
| 历史项目 PPT | PPT/PPTX/PDF | 客户汇报、方案、路线图、价值测算 | 复用故事线、页面结构、案例经验 |
| 咨询报告 | Word/PDF | 诊断报告、评估报告、实施建议 | 复用分析框架、判断逻辑、结论表达 |
| 客户案例 | PPT/Word/PDF | 行业背景、问题、方案、结果 | 找相似案例、提炼经验 |
| 方法论资料 | PPT/Word/PDF/MD | 框架、模型、工具、checklist | 支撑 Skill 和交付物生成 |
| 会议与访谈材料 | Word/PDF/MD | 纪要、访谈提纲、行动项 | 补充风险、客户偏好、后续动作 |
| 行业研究 | PDF/PPT | 行业趋势、政策、标杆 | 项目分析、论证依据 |
| 交付模板 | PPT/Word/Excel | SOW、提案、汇报、计划表 | 快速生成交付物 |

这些资料通常具备几个特点：

- 格式复杂，PPT/PDF/Word 占主流。
- 信息密度高，但结构不一定标准。
- 含大量客户敏感信息。
- 很多价值隐藏在经验、判断、故事线、风险提示中，而不是显式关键词。
- 需要能按行业、服务线、客户类型、项目阶段和交付物类型复用。

### 18.3 用户场景

知识库建成后，小伙伴应能在 Aria 中完成：

- 问：“有没有类似客户案例？”
- 问：“过去做会员体系项目时有哪些坑？”
- 问：“这个项目有没有可参考的 PPT 结构？”
- 问：“做数字化战略方案，过往有哪些方法论？”
- 问：“这个行业客户通常关心什么？”
- 问：“帮我参考历史案例生成一份提案大纲。”
- 问：“给我找 3 个和当前项目最像的案例。”
- 在 Skill 中自动调用历史案例、模板和方法论。
- 在会前准备中召回客户历史资料和相似项目经验。

AI 不只是读取文档文本，还要理解：

- 这是什么类型的资料。
- 属于哪个行业。
- 属于哪条服务线。
- 是哪个项目阶段的材料。
- 解决了什么问题。
- 用了什么方法。
- 交付了什么成果。
- 有哪些风险和经验教训。
- 哪些内容可以复用。
- 哪些内容涉及客户敏感信息。

### 18.4 咨询知识对象

在第 5 节的 `Knowledge Source / Knowledge Document / Knowledge Chunk` 基础上，咨询经验知识库还应逐步引入两个高价值对象：`Knowledge Case` 和 `Knowledge Method`。

#### Knowledge Case

`Knowledge Case` 表示从历史资料中抽取出的案例资产。

示例：

```json
{
  "case_title": "某文旅集团会员体系数字化项目",
  "industry": "文旅/商旅",
  "service_line": "数字化战略",
  "project_type": "会员体系设计",
  "client_stage": "lead/opportunity/delivery",
  "business_problem": "会员数据分散，运营转化低，缺少统一增长体系。",
  "solution_summary": "设计会员生命周期运营体系、数据中台蓝图和自动化运营流程。",
  "deliverables": ["数字化平台蓝图", "会员标签体系", "运营标准作业手册"],
  "methods_used": ["会员生命周期运营", "数据中台架构", "标签画像体系"],
  "key_risks": ["数据质量不足", "组织协同弱", "业务口径不统一"],
  "lessons_learned": ["前期必须先统一会员口径和数据责任。"],
  "reusable_assets": ["诊断框架", "路线图", "价值测算模型"],
  "source_document_ids": [1, 2],
  "confidential_level": "client_sensitive",
  "anonymized": false
}
```

第一版可以先把这些结构放在 `metadata_json` 中，等抽取规则稳定后再拆成独立表。

#### Knowledge Method

`Knowledge Method` 表示从资料中抽取出的咨询方法论。

例子：

- 数字化成熟度诊断框架。
- 会员生命周期运营模型。
- 财务共享中心建设路径。
- 内控风险评估矩阵。
- 客户访谈提纲。
- SOW 编写框架。

方法论应能被 Skill 调用，用于方案生成、PPT 大纲、风险诊断和交付模板复用。

### 18.5 PPT / PDF / Word 解析重点

#### PPT / PPTX

PPT 是咨询经验里最重要的格式之一，应作为优先级最高的解析对象。

解析目标：

- 提取每页 slide 标题。
- 提取正文文本。
- 提取备注。
- 提取表格文本。
- 尽量提取图表标签和图中文本。
- 保留 slide 编号。
- 生成每页 slide summary。
- 判断整份 PPT 的 storyline。

PPT chunk 策略：

```text
1 slide = 1 chunk
必要时相邻 2-3 页合并为 storyline chunk
```

AI 理解重点：

- 这页在故事线中的作用。
- 是背景、诊断、洞察、方案、路线图、价值、风险还是附录。
- 是否可复用为模板页。

#### PDF

PDF 分两类：

- 原生文本 PDF。
- 扫描件 PDF。

处理策略：

- 优先文本抽取。
- 如果无文本或文本质量差，进入 OCR。
- 按页码、标题、章节切分。
- 对长报告生成章节摘要。
- 保存页码，便于引用。

#### Word / DOCX

Word 适合按标题层级处理。

解析目标：

- heading path。
- 段落文本。
- 表格。
- 页眉页脚可选。
- 批注和修订第一版可暂不处理。

Word chunk 策略：

```text
按 Heading 1 / Heading 2 / Heading 3 分段
段落过长再按 token 切分
表格转为 Markdown table 或结构化文本
```

### 18.6 咨询知识理解流程

导入文件后，不应只做 embedding。建议加入结构化理解流程：

```text
文件导入
  ↓
文本抽取
  ↓
文档类型识别
  ↓
生成文档摘要
  ↓
抽取标签和元数据
  ↓
抽取案例 / 方法论 / 风险 / 经验 / 模板
  ↓
切 chunk + embedding
  ↓
进入知识索引
```

建议文档类型：

| 类型 | 说明 |
|---|---|
| `case_ppt` | 历史客户案例 PPT |
| `proposal` | 提案/建议书 |
| `delivery_report` | 交付报告 |
| `methodology` | 方法论资料 |
| `template` | 交付模板 |
| `meeting_notes` | 会议纪要 |
| `research_report` | 行业研究 |
| `sow` | 工作说明书 |
| `training_material` | 培训材料 |

建议自动标签维度：

- 行业。
- 服务线。
- 项目类型。
- 客户阶段。
- 交付物类型。
- 方法论。
- 风险主题。
- 是否客户敏感。
- 是否可脱敏复用。

### 18.7 混合检索策略

咨询知识检索不能只靠向量相似度。

建议组合：

| 检索方式 | 用途 |
|---|---|
| 语义检索 | 找相似案例、相关方法论、类似问题和经验 |
| 元数据过滤 | 行业、服务线、客户范围、项目类型、保密级别 |
| 全文检索 | 客户名、术语、框架名、报告标题 |
| 案例检索 | 面向 `Knowledge Case` 找相似案例 |
| 方法论检索 | 面向 `Knowledge Method` 支撑 Skill |

典型问题：

- “有没有类似案例？”
- “这个客户类型过去怎么做？”
- “这个方案以前在哪些项目用过？”
- “这个项目有什么类似风险？”

### 18.8 保密、脱敏与复用

咨询资料通常包含客户敏感信息，权限和保密必须早设计。

建议保密等级：

| 等级 | 说明 | 使用范围 |
|---|---|---|
| `public_internal` | 内部公开方法论 | 团队可用 |
| `team_restricted` | 限定团队资料 | 指定团队可用 |
| `client_sensitive` | 客户敏感案例 | 仅授权项目/人员可用 |
| `do_not_generate` | 不允许进入生成内容 | 只能检索查看，不可用于生成 |

同一份资料可形成三层资产：

```text
原始客户案例
  客户敏感，严格权限

脱敏案例
  去除客户名、金额、人名，可跨项目参考

方法论抽象
  提取可复用框架和经验，可进入团队知识
```

防泄漏原则：

- 检索前必须做权限过滤。
- prompt 注入前再次校验权限。
- 客户敏感资料默认不跨客户使用。
- 未脱敏案例不能用于泛化生成。
- 引用来源要能显示保密等级。

### A.5 权限实现（必须可执行）

AI 必须在每次检索时执行以下权限过滤逻辑。禁止跳过或简化。

```python
from app.models.db import User, Project, ClientRecord
from app.database import get_session
from sqlmodel import Session


def has_project_access(user_id: int, project_id: Optional[int], session: Session) -> bool:
    """复用现有项目权限检查。

    实现说明（安全关键）：本函数是 ``filter_chunks_by_permission`` 的上游闸门，
    任何"项目存在即允许访问"的实现都是越权漏洞。**禁止**直接返回 True。
    必须复用 ``app/routers/projects_deps.py`` 或等价 helper 中已有的成员/角色
    校验，并对结果做单元测试覆盖（拒绝/允许两个分支都要有）。
    """
    if project_id is None:
        return False
    project = session.get(Project, project_id)
    if not project:
        return False
    # 必须在合并前替换为真实权限检查（如 projects_deps.require_project_access）。
    # 保留为硬错误，防止 Coding Agent 把 placeholder 误判为可发布实现。
    raise NotImplementedError(
        "has_project_access: wire to projects_deps before merging — "
        "must not return True unconditionally"
    )


def has_client_access(user_id: int, client_id: Optional[int], session: Session) -> bool:
    """复用现有客户权限检查。

    实现说明（安全关键）：见 ``has_project_access``。必须复用
    ``app/routers/clients_deps.py`` 中已有的所有权/共享校验，禁止直接返回 True。
    """
    if client_id is None:
        return False
    client = session.get(ClientRecord, client_id)
    if not client:
        return False
    raise NotImplementedError(
        "has_client_access: wire to clients_deps before merging — "
        "must not return True unconditionally"
    )


def filter_chunks_by_permission(
    user: User,
    chunks: list,  # list[KnowledgeChunk]
    session: Session,
) -> list:
    """
    按用户权限过滤 chunks。
    这是安全关键函数，禁止跳过。
    """
    allowed_chunks = []

    for chunk in chunks:
        doc = session.get(KnowledgeDocument, chunk.document_id)
        if not doc:
            continue

        source = session.get(KnowledgeSource, doc.source_id)
        if not source:
            continue

        # user scope：只返回自己的
        if source.scope_type == "user":
            if source.owner_user_id != user.id:
                continue

        # project scope：检查项目权限
        elif source.scope_type == "project":
            if not has_project_access(user.id, source.scope_id, session):
                continue

        # client scope：检查客户权限
        elif source.scope_type == "client":
            if not has_client_access(user.id, source.scope_id, session):
                continue

        # workspace / skill / global：对团队成员可见
        # 如需更细粒度，后续扩展

        allowed_chunks.append(chunk)

    return allowed_chunks
```

> ⚠️ **安全红线**：
> - 权限过滤必须在 **prompt 注入前** 完成。
> - 禁止在 SQL 查询中直接拼接 user_id（使用参数化查询）。
> - 禁止通过 `scope_id` 遍历猜测其他用户/项目/客户的数据。

### A.6 检索策略约束

第一版必须实现：

```
1. 混合检索：向量相似度（70% 权重）+ PostgreSQL tsvector 全文匹配（30% 权重）
2. 查询扩展：使用同义词表扩展 2-3 个查询变体，分别检索后合并去重
3. 结果不足 fallback：如果 top_k 中 relevance < 0.6 的结果不足 3 条，
   自动扩大 scope 到上一级（project → client → workspace）
4. Markdown 切分策略：
   - 优先按 heading 层级切分（h1/h2/h3 作为 chunk 边界）
   - heading 下内容超过 900 tokens 时，按 800 tokens 软切分
   - chunk_overlap = 100 tokens（仅在软切分时使用）
```
