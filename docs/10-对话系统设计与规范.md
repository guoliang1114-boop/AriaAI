> **与已有架构的兼容承诺**：

> 2. **不重复造 Router**。已有的 `task_orchestrator.route_project_task_request` 是 LLM Router + Rule-First 的完整实现，本规范要做的是把它**抽象成通用 IntentRouter**，让 chat-mode 路由和 task-type 路由共用一个服务。

## 核心架构 TL;DR

```
User Message
   ↓
Policy Guards          ← 身份拦截 / destructive 词识别 / 明确写入意图
   ↓
IntentRouter           ← Rule-First short-circuit + LLM Router + fallback
   ↓
(ChatMode, ActionPolicy, task_route?)
   ↓
Prompt / Context / Tool Scope    ← Mode 决定剧本，Policy 决定权限
   ↓
P0-P4 Phase 执行（SSE 流式）
   ↓
HITAS 拦截（MODIFY / DESTRUCTIVE → PendingToolAction）
   ↓
Direct Answer  或  Task Orchestration（升级到 task_orchestrator）
   ↓
UI Progress Contract
   ↓
ChatTrace + Golden Set 防回归
```

**关键区分**：
- **ChatMode**：对话的"剧本"。决定 prompt 模板、context 范围、historic window、可用模型。**6 种枚举**。
- **ActionPolicy**：对话的"权限"。决定本次消息能调哪类工具、是否需要确认。**6 种枚举**。
- **Mode × Policy** 共同决定本次请求的完整契约。

## 1. 核心架构：Intent → Mode → Action

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│   Intent     │───▶│    Mode      │───▶│   Action     │
│              │    │              │    │              │
│ LLM Router   │    │ 不可变枚举   │    │ 装配 prompt  │
│ + fallback   │    │ 决定一切下游 │    │ 选 model     │
│              │    │              │    │ 选 tools     │
└──────────────┘    └──────────────┘    └──────────────┘
   单次决策            状态机              纯函数
```

**关键不变量**：
- Intent 决策有且仅有一次，结果是 `ChatMode`
- Mode 决定 prompt / model / tools / history window，下游不再做"局部判定"
- 任何"根据 X 改写 Y"的逻辑，要么挪到 Intent 决策层，要么挪到 Mode 配置表

## 2. ChatMode 枚举

6 种模式，覆盖所有 chat 主路径 + 与 Capability Protocol 的交界。

```python
class ChatMode(str, Enum):
    STANDALONE_QA = "standalone_qa"
    PROJECT_DEEP_DIVE = "project_deep_dive"
    CROSS_PROJECT_PORTFOLIO = "cross_project_portfolio"
    WORKSPACE_INVENTORY = "workspace_inventory"
    SKILL_EXECUTION = "skill_execution"
    TASK_ORCHESTRATION = "task_orchestration"   # 已升级为 task_orchestrator 处理
```

**`TASK_ORCHESTRATION` 的特殊性**：这个 Mode 不直接装配 prompt，而是**把控制权交给 task_orchestrator**：当 `route_project_task_request` 返回 `response_mode ∈ {artifact, orchestrated, edit}` 且置信度足够时，进入这个 Mode。

## 3. ActionPolicy 与 HITAS

### 3.1 ActionPolicy 枚举

```python
class ActionPolicy(str, Enum):
    DIRECT_ANSWER = "direct_answer"            # 仅直接回答，不调任何工具
    READ_ONLY_TOOL = "read_only_tool"          # 允许调读类工具
    WRITE_ARTIFACT = "write_artifact"          # 允许创建新交付物
    MODIFY_EXISTING_FILE = "modify_existing_file"  # 允许修改/覆盖已有文件，需二次确认
    DURABLE_TASK = "durable_task"              # 升级到 task_orchestrator 处理
    DESTRUCTIVE_ACTION = "destructive_action"  # 删除/破坏性操作，必须用户确认
```

> 状态：枚举定义在 `services/chat/mode_registry.py` 中**已存在**。`policy_allows_tool` 函数**已在 P2 中运行**，用于拦截需确认的工具。

### 3.2 Policy → 工具权限映射

| Policy | 可调工具类型 | 确认级别 | HITAS 状态 |
|---|---|---|---|
| `DIRECT_ANSWER` | ∅ | N/A | — |
| `READ_ONLY_TOOL` | read-only tool | 无 | — |
| `WRITE_ARTIFACT` | read + create/append | 无 | — |
| `MODIFY_EXISTING_FILE` | 工具池所有 + replace | **HITAS Action Preview 确认** | ✅ 已落地 |
| `DURABLE_TASK` | 移交 task_orchestrator | 任务级确认 | ✅ 已落地 |
| `DESTRUCTIVE_ACTION` | delete 类工具 | **HITAS Action Preview 确认** | ✅ 已落地 |

## 5. Intent → Mode + Policy 决策（目标态）

### 5.1 五层管道（目标态）

```
User Message
   ↓
[1] Policy Guards        → 硬规则给确定性决策（identity/destructive/write intent）
   ↓
[2] Rule-First Short-Circuit → 高置信度规则路径直接返回
   ↓
[3] LLM Router           → 语义理解兜底
   ↓
[4] Schema + Clamp       → 校验 LLM 输出，防止权限升级
   ↓
[5] Conservative Fallback → 默认从严
   ↓
IntentDecision(chat_mode, action_policy, task_route, confidence, method)
```

> 状态：🔄 **部分落地**。
> - ✅ `prepare_chat_runtime_async` 是 API 主入口
> - ✅ `classify_chat_intent_async` 包含 Rule-First + LLM Router
> - ✅ Policy Guards（`policy_allows_tool`）已在 P2 运行
> - 📋 `IntentDecision` 五层管道尚未完全抽象为独立 `services/intent_router.py`
> - 📋 `services/policy_guards.py` 尚未独立，身份/写入意图识别仍散落在各文件中
> - 📋 Conservative Clamp 尚未完全实现（LLM 可能静默升级权限）

### 5.2 当前实际决策链路

```python
# prepare_chat_runtime_async 实际流程
1. classify_chat_intent_async(req) 
   → 返回 (chat_mode, action_policy, intent_task_route)
2. 根据 chat_mode 装配 prompt / context / model

```

### 5.3 Fallback 策略（目标态）

- LLM Router 超时/失败/低置信度（<0.55）→ 用 Rule-First 结果
- 高置信度规则路径（≥0.9）直接 short-circuit
- 所有分歧记录到 `ChatTrace`

> 状态：🔄 **部分落地**。Trace 记录已有，但分歧检测和 override 逻辑尚未完全独立。

## 7. System Prompt 装配


- `PROJECT_MARKDOWN_TOOL_PROMPT` → **整体删除**：内容拆到各 tool 的 description

> 状态：📋 **规划中**。当前 prompt 装配仍在 `prepare_chat_runtime_async` 和各 provider 文件中。

### 8.1 数据结构（目标态）

```python
class ChatTrace(BaseModel):
```

### 8.2 当前实际 Trace

当前 `trace.py` 已提供 `build_chat_trace_payload()` 和 `persist_chat_trace()`，Trace 数据结构包含：
- `trace_id`, `conversation_id`, `message_id`
- `prompt_layers_json`（每层名字 + token 数）
- `tool_decisions_json`
- `stage_timings_json`
- `fallback_events_json`

> 状态：🔄 **部分落地**。Trace 已持久化到 DB，但前端开发模式下的 Trace 展示按钮和周报告警尚未实现。

### 8.3 已知问题

**HITAS / legacy 状态同步**：HITAS confirm 后写入的 message metadata 使用 `tool_action_result` / `tool_action_batch_result` 作为执行结果事实源。旧 `resolved_action_confirmations` 只服务历史 token 流，不再作为新 HITAS 的必需字段。

**当前策略**：前端 `findPendingAction` 识别 `tool_action_result` / `tool_action_batch_result` 后，不再重新合成 legacy Action Preview，避免“确认执行后又弹确认”的回环。后端结果 message 不恢复旧 token 字段，防止两套确认状态继续耦合。
